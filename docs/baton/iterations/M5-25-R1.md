# M5-25-R1 — Go package-qualified calls, and generic, slice and map literals of imported types

## Identification

Milestone: M5; priority: P2; risk: low; estimate min/expected/max: 2/4/6 h; role: parser and resolver engineer.

## Objective

`domain.NewOrder()` and a method called on a qualified literal (`domain.Order{}.Run()`) link the declaration in the imported project package; `domain.Box[int]{}`, `[]domain.Item{{}}` and `map[K]domain.Item{}` make an instantiation edge to the imported type.

## Dependencies

M5-25 (hard, DONE): qualified composite literals, the parser's `goPackage` metadata and the scanner's `resolveGoQualifiedType`.

## Cause

Recorded in `reports/M5-25.md` (Limitations):

- `queries/go/references.scm` captures the field of every `pkg.F()` call as a plain call, and the parser attaches `goPackage` to `extends` and `instantiation` references only, so the scanner resolves the call by name: a homonym in the calling package, or in any other package, can win.
- The composite-literal patterns match a `type_identifier` or a `qualified_type` directly under the literal; a `generic_type`, `slice_type`, `array_type`, `implicit_length_array_type` or `map_type` wrapping the type is not matched, so no edge is made.

## Scope

- `queries/go/references.scm`: composite literals whose type is a generic instantiation of a (qualified or local) type, or a slice, array or map whose element (map: value) is one, directly or through a pointer.
- `src/parsers/generic-wasm-parser.ts`: a `pkg.F()` call whose qualifier names an import of the file carries that import path (`goPackage`); a method called on a qualified composite literal (`pkg.T{}.M()`, `(&pkg.T{}).M()`) carries the literal's import path and its type (`goType`). The qualified-type lookup takes the qualifier text so calls and types share it.
- `src/core/scanner.ts`: `resolveGoQualifiedType` resolves these: a call to the function (or a type, for a conversion) declared in the imported package's directory; a method to the method of that type in that directory. A library package links nothing. A literal's method that the type does not declare (a promoted method) resolves by name as before.
- `tests/go-qualified-instantiation.test.ts`: a synthetic multi-package workspace where the calling package and another package declare the same names.
- `src/core/extractor-version.ts`: version bump (unchanged files index differently), per the batch-3 lane rule.
- After the independent review of 796c927: `src/core/import-resolvers.ts` follows go.mod local `replace` directives and go.work modules, and tells imports known to be outside the project; the parser skips qualifiers shadowed by locals and literal element types that are type parameters, and unwraps any nesting of literal types; the scanner resolves promoted methods through same-package embedded types and falls back to by-name (outside the calling package) when no go.mod tells where an import lives; `docs/adding-languages.md` describes it.

## Out of scope

- Calls on a variable of an imported type (`o := domain.Order{}; o.Run()`): needs local type inference.
- Chained calls (`domain.NewOrder().Run()`).
- The `CHANGELOG.md` entry: the integration owner writes it (lane rule); the report carries the sentence.
