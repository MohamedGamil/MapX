# M7-05 — GitHub Pages deploy workflow and CI build check

## Identification

Milestone: M7; priority: P1; risk: low; estimate min/expected/max: 3/4/6 h; role: CI.

## Objective

A workflow builds the site and deploys it to GitHub Pages from `main` (and on manual dispatch), and a CI job builds and tests the site on every run, so a broken site never reaches `main`.

## Dependencies

M7-01 (hard, DONE). It also uses the site tests of M7-02 and M7-03.

## Decisions

- **Official actions only, pinned to a major tag:** `actions/checkout@v4`, `actions/setup-node@v4`, `actions/upload-pages-artifact@v3`, `actions/deploy-pages@v4`. Node 20, as `ci.yml`. `actions/configure-pages` is not used: the base path comes from `SITE_BASE`, and leaving it out keeps Pages permissions out of the build job.
- **Least privilege:** workflow permissions are `contents: read`. The build job runs `npm ci` lifecycle scripts and the repository's code, so it must not be able to deploy; only the deploy job, which runs no repository code, has `pages: write` and `id-token: write`. It runs in the `github-pages` environment and needs the build job. Found by the independent review. `concurrency: pages` with `cancel-in-progress: false`, so a deploy in progress finishes.
- **Deploy from `main` only, enforced:** the deploy job has `if: github.ref == 'refs/heads/main'`, so a manual run from `develop` builds the site (a dry run) and stops. (The environment's branch rule is the platform's own guard; this does not rely on it.)
- **Deploy from `main`.** Releases are owner-initiated (D007), so the live docs track `main`, not `develop`. No `paths` filter: the landing page reads `src/` and `README.md`, so almost any change can alter the site.
- **The build installs both package trees.** `npm ci --legacy-peer-deps` at the root, because `site:sync` runs the repository's code (`tsx`); `npm ci --prefix site` for VitePress. Then `npm run site:build`, with `SITE_BASE` and `SITE_URL` unset (the defaults for the project page).
- **The CI Site job runs on every run,** in parallel with the others after `lint`. A path filter would need a third-party action (not allowed) or fragile git-diff scripting, and would miss `src/` and `README.md` changes that break the landing facts. It sets `REQUIRE_SITE=1` for the three site vitest suites and runs the site Playwright config.
- **`yaml` (ISC) as a dev dependency**, exact version, to parse the workflows in tests. Nothing in the repo parsed YAML before.
- **Proof without running Actions:** the workflow is checked statically; `npm ci --dry-run --offline` (exit 0 in sync, 1 on a drifted lockfile; verified) shows both lockfiles satisfy their `package.json`; the build is the one the site tests already run.

## Scope

- `.github/workflows/pages.yml` (new); a `site` job in `.github/workflows/ci.yml`.
- `tests/site-workflow.test.ts`.
- `package.json` / `package-lock.json`: `yaml`.

## Out of scope

- Enabling Pages in the repository settings (Source: GitHub Actions), pushing to `main`, a custom domain and the `CNAME` file: the owner's actions, listed in M7-98.
- Sitemap, canonical URLs, budgets: **M7-06**. Running Actions itself: not possible here; the first real run is the owner's push.

## Acceptance criteria

See `TASKS.json` (M7-05).

## Verification

- `npx vitest run tests/site-workflow.test.ts`
- `npm run site:build`
- `npm run check`

## Recovery

Revert the task commit. Nothing is deployed until the owner pushes to `main` and enables Pages.
