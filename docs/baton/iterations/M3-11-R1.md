## Objective

Common navigation and route-module forms give `navigate` edges, each to the component of the exact route record it names (by name or path, never by similarity).

## Dependencies

- M3-11 (hard): navigation from plain JS/TS modules. DONE (disputed for M3-08-R1's scope, not for this).
- M3-08-R1 (hard): route tables scoped per Vue app (`vueScope`, `vueRouterActive`, `vueScopeMoves`). In the baseline (`base11.patch`).

## Scope

Parser side only (`src/parsers/languages/vue-navigation.ts`, `vue.ts`); the scanner's route table and matching are unchanged.

- **Destructured router functions.** `const { push, replace: go } = useRouter()` (also from `this.$router` or another router receiver): calls to those locals are navigations. Not a member call (`list.push(`, `list. push(`) and not a `function push(` declaration.
- **Script-setup template.** A template expression sees the router bindings of `<script setup>` (`router.push(…)`, a destructured `push(…)`); a plain `<script>`'s bindings are not the template's.
- **Guard redirects.** In a guard, `next(target)` (its third parameter, also from a callback inside it) and a returned target (`return { name }`, `return '/path'`, not the returns of a nested function). Guards: the function given to `beforeEach` / `beforeResolve` on a router receiver or a `…router` / `…Router` local (a router parameter, an `./index` import), `onBeforeRouteLeave` / `onBeforeRouteUpdate`, a record's `beforeEnter` (function, same-file function name, or array), in-component `beforeRouteEnter` / `Update` / `Leave`, and any function with the `(to, from, next)` signature (a guards module).
- **Pinia `this.router`.** `this.router.push` in a file that calls `defineStore` (the router a store plugin adds); nowhere else.
- **Route modules.** `export default [ … ]` (also `export default <RouteRecordRaw[]>[` and `… satisfies …`) is a route array when one of its records has a component. The router file's `...adminRoutes` element needs nothing: the module's own records are in the route table (per file, as sync records them). A relative-path record there is a child of a parent elsewhere; its full path is unknown, so it is left out.
- **`<script setup generic="…">`.** A shared `scriptBlocks` (in `vue-template.ts`) reads the opening tag with quoted attribute values, so `>` inside `generic` no longer cuts it. Used by `vue.ts` (symbols and references), `navigationReferences` and `scriptBindings` (the template's view of `<script setup>` imports).
- **Pre-filter.** `mayNavigate(source)` replaces the `push(` + `router` test in `moduleNavigationReferences` and `navigatesTo`: guard files may name neither.

## Out of scope

- A router passed as a parameter for `push` (`function go(router) { router.push(…) }`), and `next` / guards whose name is shadowed: recorded limitations of M3-11.
- The vue-router detector's own `route` edges for `export default [ … ]` modules (`src/frameworks/detectors/vue-router.ts`, a separate parser of route arrays): navigate edges use `routeRecords`, the detector does not.
- Children spread into a parent's `children` from another file (relative paths, see above).
- `src/core/scanner.ts`: its `vueScopeMoves` filter misses guard redirects that name no `router.push` / `useRouter` (`next('/x')`, `return { name }` in `router.beforeEach`); the change (use `mayNavigate`) is a separate companion patch with its own e2e test (`M3-11-R1-scanner-companion.patch`), as the lane instructs.
