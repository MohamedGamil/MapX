# M0-02-R5 — git sync drops deleted untracked/staged files; blob hashes for re-indexed files

## Identification

Milestone: M0; priority: P2; risk: low; role: scanner / incremental indexing.

## Objective

A file that git sync indexed while it was untracked or only staged leaves the index when it is deleted, as `scan --force` would have it; files that git sync re-indexes record their blob id, so an unchanged file is skipped on the next sync.

## Dependencies

M0-02-R4 (hard: workspace-path blob keys, `gitBlobId`, the blob skip in git sync).

## Scope

- **Deleted files git does not list.** `git diff <last_scan_commit>` compares two trees that both lack a file that was never committed, and `git ls-files --others` stops listing it once it is deleted. Git sync therefore also takes as removed every indexed file of the repo that is missing from HEAD's tree (one `git ls-tree`, already wrapped by `getGitBlobHashes`) and missing on disk. A listed change whose file is gone (a staged-only file deleted in the working tree is still listed by `git diff --cached`) is removed too, not skipped.
- **Blob ids on sync.** Git sync stores `gitBlobId` of the bytes it indexed, for listed files and for re-parsed referrers, in place of `null`. The skip compares the same in-process id, so it stays exact.

## Out of scope

- The full scan keeps M0-02-R4's rule (HEAD's blob only for clean content).
- Content filters (autocrlf): the in-process id is `git hash-object` without filters; under filters it differs from git's id, which only means no skip.
