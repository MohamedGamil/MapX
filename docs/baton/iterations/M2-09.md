# M2-09 — JS/TS member-assigned functions are symbols

## Identification

Milestone M2; priority P2; risk low; estimate min/expected/max: 2/4/6 h; role: JS/TS extraction.

## Objective

`obj.method = function () {}`, `obj.method = () => {}` and `Foo.prototype.bar = function () {}` in JS/TS give one method symbol named for the member, with scope `obj` / `Foo`, so calls `obj.method()` link to it and `mapx node obj.method` and the dashboard open it.

## Dependencies

- M2-08 (hard, DONE): import-bound call resolution, whose `findExport` and export signature (M2-08-R1) this must not break.

Source: `reports/M4-26.md` (a scan of `api.get = function () {}` gives only `api`).

## Scope

Reproduced on develop `1e1da86` with a real scan: `api.get = function`, `api.post = () =>`, `Foo.prototype.bar = function` and `exports.ping = function` give no symbol; the calls in their bodies have `source_symbol = null`, and `api.get()` in another file has no edge.

Rules (decided here; there is no spec text on member assignments):

1. **Member function.** `X.m = <function>` where `X` is a plain identifier, the statement is at module level, and the value is a function expression, arrow function or generator function: a `method` `m` with scope `X`. Its body's calls get `source_symbol = 'X::m'`.
2. **Prototype method.** `Foo.prototype.bar = <function>` at any depth (prototype code is often wrapped in an IIFE): a `method` `bar` with scope `Foo`.
3. **CommonJS export.** `exports.f = <function>` and `module.exports.f = <function>` at module level: a `function` `f` with scope `exports`. It is reached through its module (`findExport`: `const m = require('./m'); m.f()`, `const { f } = require('./m')`), never as a lexical `f` (revised after review P1-a).
4. **Not symbols** (precision):
   - a member assigned a non-function: `obj.count = 1`, `module.exports.x = y`, `exports.limit = helper`, `obj.handler = other.fn`;
   - `this.x = () => …` (in a constructor or anywhere): an instance value, not a declaration; class fields already give properties;
   - `module.exports = function () {}`: the module's single export, not a member named `exports`;
   - a deeper receiver `a.b.c = function` other than `Foo.prototype.bar`, a computed key `obj[k] = …`, and a non-prototype member assignment inside a function or block (a local object, as with `const f = () => 1` inside a function: M0-17-R3).

Resolution (added after the review, `src/core/scanner.ts`): every such symbol is marked `assigned` in its metadata; name lookup ranks member-assigned functions below declared functions and methods; a receiver bound by import to a module's object (`import { api }`, `const hooks = require('./hooks')` with `module.exports = hooks`) resolves to the member that module assigns. A member-assigned symbol whose scope and name the file already has is dropped. The export signature lists every member assigned a function, at any depth.

The rules live in the JS and TS symbol queries (`queries/javascript/symbols.scm`, `queries/typescript/symbols.scm`), so the worker fallback walk sees them too. The JS and TS parsers give these symbols a signature `obj.m = function (a)` / `obj.m = (a) =>`.

## Out of scope

- Object-literal members `const obj = { m() {} }` and `module.exports = { m() {} }`: existing behaviour.
- `this.x = …` instance members: rule 4.
- Receiver types for name lookup (`map.get()` may link to any `get` method, as it already does for class methods): a resolution change, not an extraction one.
- `CHANGELOG.md`: edited by the integration owner (lane brief); the report gives the line.
