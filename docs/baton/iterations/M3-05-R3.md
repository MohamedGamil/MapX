# M3-05-R3 — Store-library gate follows package.json changes and monorepo roots

## Identification

Milestone: M3; priority: P2; risk: low; estimate min/expected/max: 1/3/4 h; role: parser and scanner maintainer.

## Objective

Adding or removing `pinia` or `vuex` in a package.json makes sync re-parse the JS/TS modules it governs, as `scan --force` would. A store library declared at a monorepo root counts for its packages.

## Dependencies

M3-05-R2 (hard, DONE). No approval gate.

## Scope

- **Sync follows the gate.** The gate is the package.json `storeDependencies` reads at parse time (M3-05-R2). Sync must end with the edges `scan --force` gives after that file gains or loses `pinia`, on the git and the hash sync paths. The design constraint is to reuse the scanner's existing tracking of manifest inputs rather than invent a new trigger. Before coding, check what that tracking already re-parses: `configReferrers`, M0-02-R8, hashes every package.json above an indexed JS/TS/Vue/Svelte file.
- **Monorepo roots.** When the nearest package.json with dependencies lacks a store library, the first workspace root above it lends the library when that root declares it and its workspace globs list the package's folder. A workspace root is a package.json `workspaces` field (an array, or yarn's `{ packages }`) or a `pnpm-workspace.yaml` `packages:` list. A folder the globs do not list gets nothing from the root.
- A change to `pnpm-workspace.yaml` must re-parse like a change to package.json, so sync follows it too.
- **Review round (2026-11-03).** Four P2 findings:
  1. Track the manifests above the workspace root that the search reads, up to the same end.
  2. Read `pnpm-workspace.yaml` in flow and quoted styles.
  3. Pass roots that do not list the package.
  4. Bound the search at `.git`, else `.mapx`, with the lookups cached per folder.

## Out of scope

- Narrowing the existing M0-02-R8 re-parse on package.json edits. Today it re-parses every JS/TS/Vue/Svelte/Python file below the folder, on any edit. Narrowing it would change npm-package resolution (M0-17-R4), app roots (M3-09-R1) and alias tracking, which other tasks own.
- Counting a `defineStore` / `createStore` elsewhere in the repo as the gate (the alternative noted in M3-05-R2).
- Workspace roots beyond `.git` (or, outside a repository, beyond the MapX workspace root): not consulted.

## Implementation plan

- `src/parsers/languages/vue-stores.ts`, `storeDependencies`: after the nearest manifest with dependencies, keep walking up to the first workspace root. Merge its store libraries when its globs (matched with picomatch, `!` negations honoured) list the package's folder. Workspace facts are cached per file by mtime, like the manifest's.
- `src/core/scanner.ts`, `configReferrers`: hash `pnpm-workspace.yaml` with the folder's package.json and bundler configs. This is one name in the list, away from `resolveSymbolToFile`.
- `src/core/extractor-version.ts`: bump, since a monorepo package that lists other dependencies now indexes differently.
- `tests/vue-stores.test.ts`: e2e tests for git and hash sync (add pinia, then remove it: sync equals `scan --force`), a monorepo-root test, a test for a folder outside the globs, and a sync test for adding pinia at the root.

2. A package whose root package.json declares pinia (workspaces) gets the Pinia handling (test "a store library declared at a monorepo root").
