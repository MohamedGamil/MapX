# M2-08-R11 — A bare import resolves under the module roots a project configures

## Identification

Milestone: M2; priority: P2; risk: medium; estimate min/expected/max: 3/5/8 h; role: resolution engineer.

## Objective

`import x from 'models/user'` and `require('lib/a')` link their project file again when the project says, in a config MapX can read, that the folder is a module root: webpack `resolve.modules`, jest `moduleDirectories` and `modulePaths`, or `NODE_PATH=` in a package.json script. Such a specifier is a project module, not an npm external candidate. A bare package import with no such evidence still links no project file (M2-08-R6).

## Dependencies

M2-08-R6 (hard, DONE, commit 0bed26b): removed the root-relative probe for bare JS/TS specifiers, and left this follow-up for the root-level module folders it also cut.

## Cause (probe, 2026-11-04)

Reviewer cases from the M2-08-R6 review, scanned with the real CLI on the working tree (`develop@0bed26b`) and on `3afa180`, the commit before M2-08-R6, as the oracle:
- **G** (package.json `jest.moduleDirectories: ["node_modules", "<rootDir>"]`, `test/api.test.js` importing `services/api`): `3afa180` had the import edge and the call edge; now only a by-name call edge, no import edge.
- **J** (type-only `import type {User} from 'models/user'`, a constant `LIMIT`, a side-effect `import 'config/settings'`): `3afa180` had 5 import edges (3 files); now none, and `external_ref_candidates` rows for `models/user`, `components/Btn`, `config/settings` with `external = 1`.
- **K** (`NODE_PATH=. node main.js`; `require('lib/a')`, `require('models/user')`, colliding `save` and `find` in `models/user.js` and `models/post.js`): `3afa180` had the 3 import edges and the call edges `go call models/post.js#find`, `go call models/user.js#save`, `go2 call models/post.js#save`; now the by-name edges for the unambiguous names only, and every specifier an `npm`, `external = 1` candidate.

Cause: `resolveImportPath` (`src/core/scanner.ts`) has no source of module roots. After `paths`, aliases, `baseUrl` and workspace packages, a bare specifier names an npm package, whatever webpack, jest or `NODE_PATH` say. `jsExternalSpecifier` asks the same function, so an unresolved specifier is also an external candidate, and the M2-08-R3 gate (`outsideProject`) only spares the by-name lookup for names that are also project folders.

## Scope

New `jsModuleRootTargets` (`src/core/js-aliases.ts`) returns the module paths a bare specifier may name under the roots configured for the importing file. `resolveImportPath` probes them. Sources of positive evidence, each read statically (nothing is run), each scoped to the folder that declares it. The nearest webpack-family config and the nearest jest config decide even when they declare no root (a package with its own `jest` key, or a nearer `webpack.config.js` without `resolve.modules`, does not inherit an enclosing config's roots); `NODE_PATH` comes from the nearest package.json script that sets it. Only top-level keys are read (not `globals: { moduleDirectories }`, not webpack `externals: { resolve: { modules } }`), a jest key set in two top-level objects is ambiguous and ignored, and a jest `projects` config (text or object) declares none:
- **webpack `resolve.modules`**: `resolve: { modules: [...] }`, `config.resolve.modules = [...]`, `config.resolve.modules.push(...)` and `.unshift(...)` (the Next.js `webpack(config)` hook and CRACO) in webpack.config.{js,cjs,mjs,ts,mts,cts}, webpack.{common,dev,prod}.js, vue.config.{js,cjs}, webpack.mix.js, craco.config.{js,cjs,ts}, next.config.{js,mjs,cjs,ts} in the importing file's folder or an ancestor. Entries: a string literal is a folder NAME searched under every ancestor of the importing file (webpack's relative form, like `node_modules`); `__dirname`, `path.resolve(__dirname, 'src')`, `path.join(__dirname, 'src')`, `path.resolve('./src')` are one fixed folder; `'node_modules'` is the marker, not a root. `resolveLoader.modules` is not read. Scope: the config's folder.
- **jest** `moduleDirectories` and `modulePaths` of the package.json `jest` key, jest.config.json and the literal values of jest.config.{js,ts,mjs,cjs,mts,cts}. `<rootDir>` is substituted (a literal `rootDir`, default the config's folder); a `moduleDirectories` entry containing `<rootDir>` is one fixed folder, any other is a folder name walked under the ancestors, `modulePaths` entries are fixed folders. `roots` is not read: it names where jest looks for tests, not module resolution (jest-resolve builds its lookup paths from `moduleDirectories` and `modulePaths` only). A config with `projects` is skipped (each project has its own). Scope: files under the rootDir.
- **`NODE_PATH=` in a package.json script** (`NODE_PATH=. node main.js`, `cross-env NODE_PATH=src:./shared jest`, `export NODE_PATH=…`): `:`-separated folders relative to the package, a leading `$PWD/` accepted. Entries with another variable, an absolute path or a Windows path are skipped. Scope: the package folder.

A list element MapX cannot read (a spread of jest's `defaults`, a variable, a call, a template with `${}`) stands for what it may hold, `node_modules` among it, so the roots after it are searched after `node_modules`; a list followed by `.concat(…)` or `+ …`, and a list given by a variable, is ignored. Walked folder names look only at ancestors inside the declaring folder (webpack and jest search above it too, but a root outside the declaring app is not evidence for it).

**Order** inside `resolveImportPath`: tsconfig `paths`, bundler aliases, `baseUrl` (all unchanged) → roots searched before `node_modules` → workspace packages → roots searched after `node_modules`, and only when no package supplies the name.
- Node searches `NODE_PATH` after `node_modules`; jest's `modulePaths` come after its `moduleDirectories` chain; a webpack `modules` list is in order. A workspace package sits in `node_modules` (a symlink), so it wins over a root listed after `node_modules` or when `node_modules` is not listed at all, and a root listed before `node_modules` wins over it. This is the order an entry's position in the list gives; jest's ancestor-by-ancestor interleaving is not modelled.
- A name `node_modules` supplies shadows a late root: when an enclosing package.json lists the specifier's package with a registry version or `node_modules/<name>` exists (`isNpmPackage`), the late roots are not probed; Node's built-ins never are.
- Early roots are positive evidence from the list's order and are never gated.
- Cost (review): a root searched after `node_modules` is neither probed nor recorded as unresolved for a name `node_modules` supplies, `isNpmPackage` is memoized per folder and package for the resolution phase, and root discovery and the roots of each folder and specifier are cached, so a scan with roots configured costs what one without does and the index does not grow with a key per ancestor per package.

**External candidates and the M2-08-R3 gate**: nothing new is needed there. `jsExternalSpecifier` and `outsideProject` call `resolveImportPath`, so a specifier a root resolves is neither an external candidate (`external = 0`) nor outside the project. The tests assert it.

**Sync**: `configReferrers` (`src/core/scanner.ts`) hashes the module-root config files too (`MODULE_ROOT_CONFIGS`), per folder like package.json and the bundler configs, so a jest/webpack config or package.json script edited, added or removed re-parses the JS/TS files below it as `scan --force` would. A bare import that resolves nowhere but would under a root is recorded as unresolved (M2-08-R2), so a module added under the root later re-parses its importers.

**`EXTRACTOR_VERSION` 27**, so an index built before gets its edges again.

## Out of scope

- **`cd sub && NODE_PATH=. node x`** governs the whole package, not `sub`. **A higher-priority root file added later** (`NODE_PATH=src:lib` with `lib/x.js` linked, then `src/x.js` added) is picked up by `scan --force` and not by sync, as tsconfig `paths` arrays are at HEAD (inherited; a later task).
- **Deno `deno.json` import maps** (niche; a different file format and mapping semantics, `"imports": {"x/": "./src/"}` is an alias, not a module root): not read. No task opened.
- **`.env` `NODE_PATH`** (create-react-app before 4), Dockerfile `ENV NODE_PATH`, `.npmrc`: not read; only package.json scripts are in the task.
- **jest `moduleNameMapper`**, babel `module-resolver`, `vite` / `rollup` resolve options: aliases, a different mechanism, owner M3-09 (aliases); not read here.
- **Jest `projects`** with per-project `moduleDirectories`, a config in a non-standard path (`--config`), and a webpack config built from variables: only literal values are read.
- **M2-25-R1**: the destructured one-segment `baseUrl` call.
- By-name lookup for an import MapX cannot place (M2-08-R3's "unknown" rule): unchanged.

4. **No evidence, no edge** (tests "jest `roots` and the default moduleDirectories…", "resolveLoader.modules and modules: ['node_modules']…", "a bare package import with no such configuration…", "a root belongs to the folder that declares it…"): `roots`, the default `moduleDirectories`, `resolveLoader.modules`, `modules: ['node_modules']`, a jest `projects` config, another app's config and an unconfigured project link no file.
5. **Order** (tests "a package, a built-in and a workspace package beat a root searched after node_modules", "a root listed before node_modules beats…", "tsconfig baseUrl is tried before a module root").
6. **No npm external candidate** for a specifier a root resolves (test "a specifier a module root resolves is no npm external candidate"); the unconfigured project's candidates are unchanged.
7. **Sync equals scan** (tests "sync agrees with scan --force when a module root is configured later", and four cases in `tests/external-refs.test.ts`): a NODE_PATH script, jest.config.js and webpack.config.js added, edited and removed; a module added under the root later.
8. **Review fixes** (tests "a list the reader cannot see through stands for node_modules…", "the nearest jest or webpack config decides…", "only top-level keys are read…", "a name node_modules supplies is not recorded as unresolved under a late root"): a spread, call, variable or concat list never lets a root beat a listed package; the nearest config decides; `globals`, `projects` and `externals` are not read; gated late roots leave no `unresolvedImports` key. 10. **The self-scan** of MapX's JS/TS cross-file edges, import and require edges included, changes by nothing but the edges of the new code.
