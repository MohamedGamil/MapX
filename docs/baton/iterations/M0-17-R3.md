# M0-17-R3 — Extraction: generic bases, exported let/var, local arrows, callable constants in other languages

## Identification

Milestone: M0; priority: P2; risk: low; estimate min/expected/max: 3/5/8 h; area: remediation. Role: tree-sitter extraction, static analysis, test design.

## Objective

Inheritance through generic bases and JS exported bindings are extracted; local arrows stay local.

## Dependencies

M0-17-R2 (hard), DONE.

## Scope

Limitations recorded by M0-17-R2 (`docs/baton/reports/M0-17-R2.md`), each reproduced with a parser probe before any change:

- **Generic bases.**
  - Java `class A extends Base<String>` makes no extends reference; `implements Run<T>` and `interface I extends J<T>` lose their generic entries too.
  - TypeScript `extends Base<T>` is already captured, but `implements Run<T>` is not.
  - Kotlin `: Base<String>()` is already captured. A test pins it.
- **Exported `let` / `var`.** JavaScript `export let x` and `export var y` make no symbol, although `export const` does. TypeScript has no top-level `const`/`let`/`var` symbols at all.
- **Local arrows.** `function outer() { const f = () => 1 }` yields a top-level `function:f`. Inside a class method it becomes `method:Foo::f`.
- **C# base kinds.** The parser decides extends vs implements by the `I` prefix. When the target type is indexed, its kind (class or interface) should decide.
- **Callable constants in other languages.** C function-like macros, Rust tuple variants, Lua function values and Bash aliases stay call targets by design. This gets documented in `docs/adding-languages.md`.

## Out of scope

- TypeScript `interface I extends J` (no `extends_type_clause` pattern exists at all) and qualified bases such as `extends ns.Base` in TypeScript or `: p.Base()` in Kotlin. These are separate gaps, not generic-argument defects.
- Nested `function` declarations inside functions, which remain function symbols. This behaviour predates M0-17-R1.
- Name resolution that respects local scope. Calls to a local arrow resolve by name like any other call.

## Implementation plan

- `queries/java/references.scm`: `superclass`, `super_interfaces` and `extends_interfaces` entries accept `generic_type` (capturing its type name) and `scoped_type_identifier`.
- `queries/typescript/references.scm`, `references-tsx.scm`: `implements_clause` accepts `generic_type`.
- `queries/javascript/symbols.scm`: `export let` and `export var` patterns.
- `queries/typescript/symbols.scm`: the function-valued declarator patterns carry their kind on the declarator, as in JavaScript, so a name binds to the same node whichever pattern claims it; top-level `const`/`let`/`var` patterns as in JavaScript.
- `src/parsers/generic-wasm-parser.ts`: a function-valued `variable_declarator` inside a function body or method is skipped.
- `src/core/scanner.ts` (minimal, localized): a C# `extends`/`implements` edge whose owner is a class and whose target is indexed takes its type from the target's kind: interface → implements, class → extends.
- `docs/adding-languages.md`: which constants are call targets, and `VALUE_SYMBOL_LANGUAGES`.
- `tests/legacy-language-accuracy.test.ts`: parser cases per language, with exact symbol and reference lists, and an end-to-end C# workspace (real `init` + `scan`) asserting exact edges.

## Expected outputs

The changes above, the extended test file, and `docs/baton/reports/M0-17-R3.md`.

## Acceptance criteria

1. `class A extends Base<T>` (Java, Kotlin, TypeScript) yields an extends edge to Base. Tests: `legacy-language-accuracy` "generic bases" per language.
2. `export let x` / `export var x` yield a JS/TS symbol. Test: `legacy-language-accuracy` "exported let/var".
3. A `const f = () => …` declared inside a function is not a top-level function symbol. Test: `legacy-language-accuracy` "local arrows".
4. C# extends vs implements uses the resolved target kind when it is indexed. Test: `legacy-language-accuracy` end-to-end C# case.
