# M5-05-R1 — Staleness in status, MCP and the other commands finds new files as check does

## Identification

Milestone: M5; priority: P2; risk: low; estimate min/expected/max: 2/3/4 h; role: CLI and MCP maintainer.

## Objective

`mapx status`, the MCP staleness warning and the other commands' staleness warning count a new file in a non-git workspace or in a nested repo as stale, as `mapx check` does (M5-05).

## Dependencies

M5-05 (hard, DONE): `findStaleFiles(store, dir, { walk: true })` and the walk with the scanner's rules. M5-26 (interface, delivered): the older-index warning printed by the same CLI and MCP helpers must keep working.

## Scope

- `src/core/staleness.ts`: the walk becomes the only way new files are found. `findStaleFiles(store, dir)` walks by default; `{ newFiles: false }` checks only the indexed files (no walk, no git), for callers that use only `changed` and `deleted` (`indexableChanges`, the UI server). The git `ls-files --others` listing goes. The walk skips an unregistered nested git repository, as the scan walk does (otherwise, now that every command walks, its files would be reported new forever). `indexableChanges` takes an optional precomputed report, and a new `unlistedStale` gives what a status shows beyond git.
- `src/cli.ts`: `mapx status` computes the stale report once (one walk) and prints the stale files git did not list (all of them in a non-git workspace; a nested repo's new files; gitignored ones); `status --all` attributes new files to the repo that owns them; `mapx check` uses the default; `checkAndPrintStaleness` keeps the M5-26 warning first.
- `src/mcp.ts`: `getMcpStalenessWarning` computes the report once (it computed it twice); `mapx_status` counts the same files as `mapx status`.
- Tests in `tests/legacy-impact-staleness.test.ts`, with a synthetic preload `tests/fixtures/staleness/count-walks.mjs` that counts walks of the workspace root.

## Out of scope

- An MCP tool for `mapx check` (M5-14); baselines (M5-06).
- User-defined languages in the staleness file rules, and registered repos reached through a symlink (pre-existing false negatives; noted in the report).
- The root `CHANGELOG.md` is the integration owner's (lane brief); the changelog line is in the report.
