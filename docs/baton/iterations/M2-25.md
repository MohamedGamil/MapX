# M2-25 — A called loop variable never links a same-named function elsewhere

## Identification

Milestone: M2; priority: P1; risk: medium; estimate min/expected/max: 2/4/6 h; role: parser and resolver engineer.

## Objective

A call through a local binding (a for-of / for-in loop variable, a destructured local of a provably external source, a catch parameter, a parameter) gets no by-name edge to a same-named function in another file, including a Vue SFC `<script setup>` function or a plain script's function. A local destructured from a call given a package specifier (`const { Database } = load('bun:sqlite')`) is such a binding too: this also delivers M2-26, which shares the mechanism.

## Dependencies

M2-08-R3 (hard): the global-scope rule that lets a bare name in an ES module reach a script. Builds on M0-17-R5 (`boundLocally`).

## Scope

- `boundLocally` (`src/parsers/generic-wasm-parser.ts`) also treats as local: the variable of a `for … of` / `for … in` or C-style `for` statement (and a Python `for` or comprehension), a `catch` parameter, a `var` hoisted out of a nested block. The iterable of a loop is not in the loop's scope.
- A destructured local (`const { f } = <source>`) is local, with no edge, only when its source is provably not a project symbol (the principle of M2-12): an object or array literal, a name imported from a package or builtin, a call given a package or builtin specifier (`load('bun:sqlite')`). A `require(…)` or `import(…)` and a name imported from the project stay the scanner's. Any other source (`this.service`, a local variable, a function of the file, `new X()`) keeps the by-name edge, marked inferred.
- The file's imports are read once per parse, not once per call.
- `EXTRACTOR_VERSION` → 22.

## Out of scope

- Counting a Vue SFC `<script setup>` as a global script in the scanner (the M5-18-R1 report's second cause): a real, unbound bare call still reaches it, as before.
- Destructured parameters (`({ f }) => f()`), which the existing comment keeps for dynamic-import callbacks.
- Python module-level destructuring, and `with … as f`.
