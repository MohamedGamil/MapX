# M0-10-R4 — Multi-repo resolution independent of repo order; cross-repo edges after delete/restore and re-add

## Identification

Milestone: M0; priority: P1 (review 2026-10-31); risk: medium; estimate 4/6/9 h; role: scanner / multi-repo.
Sources: `docs/baton/reviews/REVIEW-2026-10-31-2db08bd25e13.md` (reviewer C's P1-5 and P1-6), `docs/baton/reports/M0-10-R3.md` (limitations), `specs/features/F18-git-workspace-submodules.md`.

## Objective

Cross-repo edges are the same whatever the repo order, and they come back after a target file is deleted and restored, or a repo is removed and re-added, without `--force`.

## Dependencies

M0-10-R3 and M0-02-R2 (hard), both DONE.

## Scope

All four defects were reproduced with reviewer C's probes (`p4-order.sh`, `p3-xrepo.sh`, `p12-readd.sh`) and the M0-10-R3 report's dashboard limitation, then rewritten as tests.

1. **Order.**
   - `meta resolution_repos:<repo>` recorded the repos whose files had been *discovered*. On the first `scan --all`, the primary repo is resolved before the other repo's symbols exist, yet it records that repo as seen, so it is never resolved again.
   - The record now holds the repos with *indexed* files (`store.getRepoNames()`), written by full and incremental scans alike.
   - After every repo of a multi-repo `scan` or `sync`, a second pass processes once more any repo for which a repo of the run is newly visible, or which has queued referrers.
2. **Delete and restore.**
   - When a restored file's recorded referrers belong to another repo, the re-parse loops skipped them, so cross-repo inbound edges never came back.
   - Referrers of another repo are now queued in `meta pending_referrers:<repo>`, and that repo's next scan or sync (or the second pass) re-parses them. This applies to restored files, renames, moved targets and Vue registry users.
3. **Remove and re-add.** `store.deleteRepo` now removes the repo from every other repo's `resolution_repos` record, and deletes its own scanner meta. When it is added back, it is newly visible to the others, which are re-parsed once.
4. **Duplicate collapse.** The dashboard server (`src/ui-server.ts`) loaded the config without applying the collapse, as the M0-10-R3 report noted. If it loaded first, the dropped entry's rows stayed. It now uses a `loadConfig` that applies `applyCollapsedRepos` and reports on stderr, like the CLI and MCP loaders. `/api/status` loads the config before counting.

Blast radius: private scanner methods (`_scanFullForRepo`, `_scanIncrementalForRepo`, `_scanIncrementalByHash`, `scan`, `scanIncremental`), plus `Store.deleteRepo`, whose callers are `workspaces remove` and `applyCollapsedRepos`.

## Out of scope

- Sync sequences within one repo: M0-02-R7.
- Cross-repo staleness that git does not report, such as a new symbol in repo B that unchanged files of repo A could now resolve to. That is a general incremental limit, not a repo-order defect, and is listed under Limitations.

## Acceptance criteria

1. The first `scan --all` of a two-repo workspace gives the cross-repo instantiation edge in both repo orders, and equals `scan --all --force` (e2e).
2. Deleting and restoring a file another repo imports, followed by `sync --all` or `scan --all`, restores the cross-repo inbound edges (e2e).
3. `workspaces remove` then `workspaces add` of a repo, followed by `scan --all` or `sync --all`, restores its cross-repo edges without `--force` (e2e).
4. Collapsing duplicate repo entries on `Config.load` deletes the dropped entry's rows and reports it, also when the dashboard server loads first (test).
