# M3-01 — Vue SFC fixture set (2.7 and 3.x)

## Identification

Milestone: M3; priority: P1; risk: low; estimate 4/6/8 h; area: quality, vue.
Sources: report §3 items 10–11 and §4 items 8–11; probe of 0.3.5+ behaviour (below).

## Objective

A labelled set of Vue SFCs in both Vue 2.7 and Vue 3.x syntax, with the graph edges MapX should produce for them, and a scorer that measures recall and precision of those edges. M3-02 … M3-06 raise its floors.

## What MapX does today (probe, 2026-10-30)

- **Already works:** methods in `methods: {}` become symbols (kind `method`, no scope), and `this.load()` inside one resolves to a same-file `call` edge (existing `this.method()` tracking).
- **Missing:**
  - a component symbol;
  - any `<template>` edge (handlers, component tags, `v-model`);
  - mixin members;
  - `<script setup>` symbols (defineProps / defineEmits / composables);
  - Vuex and Pinia links;
  - router links.

## Scope

- **`tests/fixtures/vue-sfc/vue2/` and `vue3/`.** Each pattern appears at least once per Vue version where it exists:
  - template event handler (`@click="save"`), method call in a binding (`:title="format(x)"`);
  - component tag, locally registered and globally registered (`Vue.component` / `app.component`);
  - `v-model` on a child component;
  - Options API: `this.x()` across `methods`, `computed` and `watch`, and a method from a mixin;
  - `<script setup>`: `defineProps` / `defineEmits`, and a composable `useX()` from `composables/`;
  - Vuex `mapActions` / `mapGetters`, `this.$store.dispatch('ns/ACTION')`;
  - Pinia `useCartStore().checkout()`;
  - `router.push({ name })` / `<router-link :to="{ name }">`.
  - Added at delivery: `component-symbol` (one class symbol per SFC) and `script-setup-call` (calls to `<script setup>` function constants such as `emit`), so that `script-setup-macro` measures only the macros' interface metadata. Vuex is scored as `vuex-map-helpers` and `vuex-dispatch`; router navigation as `router`.
- **`expected.json`:** `{ scoredTypes, labels: [{ id, pattern, version, expect?, edge?: { source_file, source_symbol, target_file, target_symbol, edge_type }, symbol?: { file, name, kind, metadata? }, note? }] }`. `"expect": "absent"` marks a negative: that exact edge must not exist, e.g. a same-named method in an unrelated component. (Planned as `edge: null`, changed at delivery because a null edge cannot name the edge that must be absent.) `symbol` labels score the component symbol and its `<script setup>` interface, which are symbols rather than edges.
- **`scripts/eval/score-edges.ts`:** a generic edge scorer that copies a fixture, runs the real `init` + `scan`, and compares the store's edges with `expected.json` per pattern. It reports recall, precision over edges between fixture files of the scored types (`call`, `render`, `navigate`; `navigate` is the new M3-06 navigation edge type, see the Edge contract). With `roots` in `expected.json` it scans each listed sub-folder as its own project, so each app's `package.json` enables framework detection as in a real project (with one scan of the parent folder, `vue-router` detection never ran and its ignore list never applied), and false positives on negatives. Edge types and symbols are matched exactly; files by path.
- **`tests/vue-sfc.test.ts`:** expected entries are well-formed and point at existing files and symbol names; a real-scan floor test records the current baseline (today's recall, not 0, since same-file `this.x()` already works).

## Edge contract

Decided at delivery (2026-10-31). M3-02 … M3-06 implement against it; `expected.json` encodes it, and changing it means relabelling. It reuses what the store already holds (`edges.source_symbol` / `target_symbol` are plain strings; there is no scope column on edges) and adds only the representations Vue needs.

1. **Component symbol (new, M3-02).** Each `.vue` file gets exactly one symbol: name = the file's basename without `.vue` exactly as written (`TicketRow.vue` → `TicketRow`, not the `name:` option), kind `class`, scope `null`, spanning the whole file. Its `metadata` carries `props: string[]` and `emits: string[]` when the component declares them (M3-04 for `<script setup>` macros; Options API `props:` may fill it too, but is not scored).
2. **Who owns a reference (`source_symbol`).** Code inside a named function or member belongs to that member's bare name (`save`, `discounted`, `created`, `saveForLater`). The template, top-level `<script setup>` statements, code directly in an Options API `setup()` (the two are the same thing) and component-level options (`components`, `mixins`, `mapGetters` / `mapActions` spreads) belong to the component symbol. Today such code gets `null` (top-level statements, and `setup` once `vue-router` detection puts `setup` on its ignore list) or the declared constant (`const prefs = …` → `prefs`). The `components` and `mixins` options produce no edge by themselves: components give render edges through their tags (rule 5) and mixins give call edges through `this.x()` (rule 6).
3. **Member naming (`target_symbol`).** Bare names, as the store holds them today. Options API `methods` / `computed` / `watch` / lifecycle members are `save`, not `methods.save`; Vuex actions, mutations and getters are `FETCH_ALL`, not `actions.FETCH_ALL` (even where the symbol's scope is `actions`); Pinia actions are `checkout`, not `useCartStore.checkout`; setup-store actions and composable return values are the inner function's name (`add`, `format`). The file (`target_file`) disambiguates same-named members, which the fixture's negatives test.
4. **Template calls → `call`.** `@event="save"`, `@event="save(x)"`, `v-on:`, modifiers (`.prevent`, `.native`), calls inside bound attributes (`:title="format(x)"`) and interpolations (`{{ format(x) }}`) give a `call` edge from the component symbol to the function: a member of the same SFC, a `<script setup>` function, a function returned from `setup()`, a mixin member (in the mixin's file), or a function returned by a composable (in the composable's file). Property reads (`{{ total }}`, `v-for="x in items"`) and the instance helpers (`$emit`, `$router`, `$event`) are not edges.
   - A call to a `<script setup>` constant that holds a function, such as the `defineEmits` result (`emit('saved')`, in the template or the script), is a `call` edge to that constant in the same file, as the TypeScript parser already does (pattern `script-setup-call`).
   - A function returned by a composable and destructured from its result (`const { persist } = usePreferences()`; `persist()` or `{{ format(x) }}`) resolves to the inner function in the composable's file. Value flow is followed no further than that destructuring.
5. **Component tags → `render`.** A tag naming a registered component (PascalCase or kebab-case, self-closing or paired, with or without `v-model`, `v-for` or listeners) gives one `render` edge from the parent's component symbol to the child's file, `target_symbol` = the child's component symbol. Local registration is the `components` option or a `<script setup>` import; global registration is `Vue.component('Name', X)` / `app.component('Name', X)` resolved through the import of `X`. Tags in HTML comments, native elements, `router-link`, `router-view`, `transition` and other built-ins are not render edges. `v-model` on a component adds no other edge (its prop/event pair is the child's interface, rule 1).
6. **`this.x()` and mixins → `call`.** `this.x()` resolves in this order: a member of the SFC itself; a member of a mixin listed in that component's own `mixins: []`, in the mixin's file; a name mapped by that component's Vuex or Pinia map helpers (rules 7 and 8). It never resolves to another file merely because that file defines `x`.
7. **Vuex → `call`.** `mapActions` / `mapGetters` / `mapState` / `mapMutations('ns', [...])` give one edge per mapped name from the component symbol to that member in the module registered as `ns` (`modules: { ns }` in the store root, followed through the import). `this.NAME()` for a mapped action also gives an edge from the calling member. `this.$store.dispatch('ns/NAME')` / `commit('ns/NAME')` give an edge from the calling member; `dispatch('NAME')` / `commit('NAME')` inside a module stay in that module.
8. **Pinia → `call`.** `useXStore()` gives an edge to the exported `useXStore` constant in the store file; `store.action()` and `useXStore().action()` give an edge to the action in that store's file (options store `actions: {}` or a setup store's inner function), never to a same-named function elsewhere, including the caller itself.
9. **Router → `navigate` (a new `ReferenceType`, M3-06).** `router.push` / `replace({ name })`, `router.push('/path')`, `this.$router.push(...)` and `<router-link :to="{ name }">` / `to="/path"` give a `navigate` edge from the caller (a member, or the component symbol for the template) to the route record's component file, `target_symbol` = that component symbol. Lazy `() => import('./X.vue')` components count. The edge does not target the route record (it has no symbol); its name and file may go in edge metadata. A route's name never selects a component by name similarity (`name: 'Dashboard'` renders `HomeView`).
   - Not `route`: `route` means a backend endpoint to the CLI and MCP (they count `route` edges as controller endpoints, and scanner route edges carry `httpVerb` / `uri`), and `deleteFrameworkEdgesForRepo` (src/core/store.ts) deletes every `route` edge in the detect phase, so parser-emitted `route` edges would not survive a real scan. M3-06 adds `navigate` to `ReferenceType` (src/types.ts) and keeps it out of that deletion (or emits it from the vue-router detector after it).
   - The vue-router detector's existing `route` edges (router file → route component) are not scored. Today they resolve statically imported components to the router file itself (`router/index.js#- -route-> router/index.js#HomeView`), a detector defect recorded in reports/M3-01.md.

## Out of scope

Implementing any of the missing behaviour (M3-02 … M3-06).

## Acceptance criteria

1. At least 30 expected edges covering every pattern above in both versions where the pattern exists, plus at least 3 negatives.
2. `score-edges.ts tests/fixtures/vue-sfc --json` exits 0, and the baseline per pattern is recorded in reports/M3-01.md.
3. Scorer unit tests: exact edge-type and symbol matching, negatives counted as false positives, unscored edge types ignored.
