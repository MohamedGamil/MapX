# M2-08-R8 — Sync re-resolves Java and Python importers when an imported project package goes away

## Identification

Milestone: M2; priority: P2; risk: medium; estimate min/expected/max: 2/4/6 h; role: resolution engineer.

## Objective

M2-08-R5 made a Java or Python name bound by an import from outside the project link nothing. Whether an import is "outside" depends on other files, so adding, deleting or moving those files changes the importer's links without changing the importer. Sync re-parses the importers whose decision such a change may flip, so sync equals `scan --force`.

## Dependencies

M2-08-R5 (hard, DONE): `javaExternalBindings`, `javaImportOutsideProject`, `jvmProjectDeclares` and `importBoundOutside`. M2-08-R2 (DONE): the recorded `unresolvedImports` and `newModuleReferrers`, the model for a record that a later sync reads.

## Cause (probe, 2026-11-04, `develop@2f33090`)

Workspace: `com/acme/Invoice.java` (class `Invoice`, `total`), `com/thirdp/Marker.java` (`package com.thirdp`), `com/use/Use.java` with `import com.thirdp.Invoice;`, `Invoice x = new Invoice(); new Invoice().total();`. Scanned with the real CLI, hash mode and git mode alike.
- Scan: `com.thirdp` is a project package (its folder holds a Java file), so the import of the missing class `Invoice` may be generated or unindexed: the decision is "unknown", name lookup applies, and `Use::run` gets `call total` and two `instantiation Invoice` edges into `com/acme/Invoice.java`.
- `rm -rf com/thirdp; mapx sync .` (hash sync; the same after a git commit, with the folder deleted from the working tree): "0 symbols updated, 0 edges updated". The three edges stay.
- `mapx scan . --force`: no edge from `Use.java`. The import is now certainly outside.

The cause is that the decision reads three things in other files, and no sync mechanism re-parses an importer for them:
- `resolveJvmImport`: a file whose path ends with the import's path;
- `javaImportOutsideProject`: a folder of JVM sources for the package;
- `jvmProjectDeclares`: a file declaring that `package` with a class of that name, whatever its folder.

`importerReferrers` follows the edges of a changed JS/TS/Python module, and `newModuleReferrers` the `unresolvedImports` record, JS/TS only (`JS_MODULE_FILE`). Python has the same gap for the top-level-name rule (`pythonNameInProject`): `from vendorlib.models import Order` with `vendorlib/other.py` in the project is unknown and links by name, and no edge leads from the importer to `other.py`, so deleting `vendorlib/` leaves the links.

## Scope

- **A record at parse time** (`files.metadata`, written beside `unresolvedImports`):
  - every JVM file (`java`, `kt`, `kts`, `scala`): `jvmDecl`, its `package` and the type names it declares;
  - a Java file: `jvmImports`, the dotted names of its single-type and single static imports;
  - a Python file: `pyImports`, the top-level names of its absolute imports no indexed file satisfies, star imports (`from x import *`) included (`pythonScope` reads the same decision).
- **Referrers**, found by one metadata pass per kind, only when a JVM or Python file is added, removed or edited:
  - an added or removed JVM file contributes the dotted trailing runs of its path without extension (`stems`, the class's own file), the qualified names of the types it declares (`types`; stored `jvmDecl` for a removed file), and the trailing runs of its folder **only when the folder set flips** (`folders`): no other remaining JVM file lies in the folder, and the run is none of the remaining files' folder runs (`ImportDecisionBaseline`, read lazily from `Store.getJvmAndPythonPaths()`; for a removal the removed paths are left out);
  - an edited JVM file contributes the types its `package` or declarations gained or lost; a body edit contributes nothing;
  - an added or removed Python file contributes the folder and module names of its path that no remaining Python file has (`pythonNameInProject` flips);
  - a Java importer is re-parsed when a recorded import's own or one-up name is a stem, its one- or two-up name (a class's package, a static member's) is a flipped folder, or a prefix of it (outer classes included) is a declared type (`jvmImportAffected`); a Python importer when a recorded top-level name is one of the names.
- **The JSON graph export** leaves `jvmDecl`, `jvmImports` and `pyImports` out of a file's `metadata` (other sync records, such as `exportSig`, were already exported and are unchanged).
- **Wired at every place sync computes referrers:** `removeFiles` (the removal queue, so hash sync, git sync and `scan` all see it) and, for added and edited files, beside `newModuleReferrers` in `_scanFullForRepo`, `_scanIncrementalForRepo` (git) and `_scanIncrementalByHash`.
- **`EXTRACTOR_VERSION` 29:** an index built before has no record, so it re-parses once.
- Cost (review of the first version, which keyed every folder run and every Python name): a body edit re-parses 1 file; a file added beside others, none of its importers; a file deleted or a class added, the importers of that class; a package folder deleted, the importers of that package. Measured in the report.
- Over-inclusive on types: a deleted or added declaration re-parses the importers of that class even when its package folder survives (a nested import's folder is a class folder, so the folder cannot stand in).

## Out of scope

- Which target an import resolves to when several files could be it (a moved or added module of the same path): M2-08 resolution itself, unchanged.
- Kotlin and Scala importers' outside decision (no gate for them since M2-08-R5): the follow-up there would also record `jvmImports` for them.
- Java files being edited so their own `import` lines change: already re-parsed as changed files.
- Unresolved relative Python imports (`from .models import X`) when the target is added later (`newModuleReferrers` is JS/TS only), and an absolute import whose top-level package exists but whose module is added (its import edge): as at HEAD.
- Adding a second same-named declaration does not re-link importers already linked by name: as at HEAD.
- Calls on variables whose type is a package class (M2-14).

## Acceptance criteria

1. **Java, delete** (hash and git, test "deleting the project package an import names"): `Use.java` importing `com.thirdp.Invoice` beside `com/thirdp/Marker.java`; after deleting `com/thirdp` and syncing, `Use.java` has no edge and is the only file re-parsed; all edges equal those of `scan --force`.
2. **Java, add:** `com.extlib.Invoice` imported with no `com/extlib` folder gives no edge; after adding `com/extlib/Marker.java`, the importer links `Invoice` (`call total`, `instantiation Invoice`), equal to `scan --force`; so for a file elsewhere declaring `package com.extlib` with a class `Invoice`, and for a class added to an existing file of that package.
3. **Java, declaration and move:** editing `misc/Ledger.java` from `package com.books` to `package com.other` drops the link of `import com.books.Ledger;`, and back restores it; deleting `misc/Stamp.java` (`package com.stamps`, folder not its package) drops the link of `import com.stamps.Stamp;`; moving a declaring file out of its package folder keeps the link; each equal to `scan --force`.
4. **Python:** `from vendorlib.models import Order` beside `vendorlib/other.py` links by name; deleting `vendorlib/` drops the links and re-creating it restores them; `from newlib.models import Order` with no `newlib` links nothing, and adding `newlib/other.py` (or `newlib.py`) links it; each equal to `scan --force`.
5. **No world re-parse:** a body edit of a class an importer names, a new file in a package no importer names, a file added beside others in an imported package (and its deletion), and a new Python file inside an existing top-level package re-parse no importer of other classes or names.
6. **Star imports, static imports, nested classes, Kotlin and Scala** (review): `from nslib.models import *` links once `nslib/models.py` is added, and `from vendorlib.models import *` unlinks when `vendorlib/` is deleted; `import static com.statlib.Util.helper` links when `com/statlib` gains a file; `import com.nested.Outer.Inner` links when `misc/Outer.java` declares `package com.nested`; a Kotlin file added and a Scala file deleted flip a Java import; each equal to `scan --force`; a static import of a member of a class links when the class's file is added to a package folder that exists (the stem rule alone, no package line).
7. **A plain `scan .`** (no `--force`) gives the same results as sync for an added and a deleted package.
8. **Cost** (3000 Java files, 100 packages, 10 imports each; hash and git sync): a body edit re-parses 1 file; a file added beside others in an imported package, 1; a package folder deleted, the importers of that package (253); never the 294 to 308 files the first version re-parsed for a file added to or deleted from a busy package.
9. **JSON export:** `jvmDecl`, `jvmImports` and `pyImports` are not in a file's exported `metadata`.
10. The registered commands pass; `npm run check` last.
