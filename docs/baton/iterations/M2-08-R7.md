# M2-08-R7 — Python: an unimported name (a builtin such as open) never links a function in another module

## Identification

Milestone: M2; priority: P2; risk: medium; estimate min/expected/max: 2/4/6 h; role: resolution engineer.

## Objective

Python resolves a bare name in its own module: what the module defines, what it imports, what a star import brings; anything else is a builtin or an error. A bare call, instantiation, base, decorator or annotation of such a name never links a same-named function or class of another module.

## Dependencies

M2-08-R3 (hard, DONE): `resolveSymbolToFile`'s `allowFile` filter and the "which files can this name see" principle (`globalScopeFilter` for JS/TS). M2-08-R5 (DONE, commit b6a7103) added the Python import-bound gate this builds on.

## Cause (probe, 2026-11-04)

Found by the review of M2-25: in MapX's own index `scripts/gen-python-stdlib.py` links `tests/fixtures/arch-rules/python-vendor/app/infrastructure/database.py#open` (2 edges, `header` and `merge`) for the builtin `open()`, and `…/python-ambient/…/shadow.py#read` for `f.read()` (a receiver call, not this task). A synthetic workspace scanned with the real CLI on `develop@a189eda` (the e2e fixture of this iteration) showed, for a module that imports nothing of the project:
- `open(path)`, the decorator `@helper`: edges to `db/database.py#helper` and to a nearer file's `open`;
- `Model()`, `def f(m: Model)`, `class Child(Model)`, `Model().save()`: edges to `db/database.py#Model` (and `#save` through `resolveNewReceiverCall`);
- `from os.path import *; open()` linked a project `open`.

Cause: after `resolveImportedCall` finds no binding for the name, the reference falls to `resolveSymbolToFile`, a by-name lookup over every project file of a compatible language. Nothing says a Python name is visible only through the module's own scope.

## Scope

- **Rule:** a bare Python reference (any kind except `import`; a call, instantiation, base, decorator or annotation) resolves by name only to (a) the module itself, (b) a module an import of the file binds the name from (as before, through `resolveImportedCall`, then name lookup when that finds nothing), (c) a module the file star-imports. Everything else gives no edge.
- **Bare** is read from the reference's line (`bareOnLine`): the name is on the line and no use of it there is an attribute (`x.name`). A line that does not show the name (a call spread over lines) or shows it as an attribute too keeps name lookup, as before. A reference with a `receiver` is not decided here.
- **Names an import binds** (`pythonScope`; `stripPythonComments` also reads `from . x import y` as `from .x import y`): every identifier of every `import` / `from … import` statement of the file (comments and docstrings stripped; `TYPE_CHECKING`, in a function, in `try`, over parenthesised or backslash lines, after a `;`, relative ones included), over-inclusively. Such a name keeps its previous resolution.
- **Star imports:** `from m import *` of a project module makes the module's files visible, recursively with what its own star imports reach, and, per name, the declaration a name the module imports resolves to through any chain of re-exports (`findExport`; a package `__init__` passing names on). A star import no file satisfies: outside the project (top-level name is no project folder or module) brings no project name, so nothing is added; relative, or named like a project folder or module, may be the project's (generated, not indexed), so the file keeps name lookup.
- **Python analogue of `globalScopeFilter`:** `pythonScopeFilter` returns the `allowFile` predicate for `resolveSymbolToFile`; `resolveClassName` (`Model().save()`, bases) applies it for a bare class name.
- **`EXTRACTOR_VERSION` 28:** unchanged files link differently.

## Out of scope

- **Calls on a receiver** (`conn.open()`, `f.read()`, `self.m()`): name lookup stays. M2-14 owns calls on variables; the `read` edges of gen-python-stdlib.py remain.
- **A dotted base** (`class Sub(models.Model)`): R5 limitation, not gated.
- **A decorator or name imported from the project that `resolveImportedCall` cannot place** (`@helper` after `from db.database import helper`: no `(`, so no line receiver): keeps name lookup as before; found, not fixed.
- **Sync after a relative-imported Python module appears** (`from .gen import *` then `gen.py` is added): sync does not re-parse the importer after a plain `scan`; the same on the base commit. Found, not fixed.
- **Notebooks:** `.ipynb` is not indexed.
- **Builtins as external references:** `pythonBuiltin` names stdlib modules, not builtin functions; a builtin gives no external row either.

## Changed by the independent review (see the report)

- **Star imports follow re-export chains:** the first version added only the files a starred module imports from, one level. Now the filter adds, for the name looked up, the declaration `findExport` reaches from each starred module's binding of it, through any number of re-exporting modules.
- **`from . transform import *`** (whitespace after the dots) is recognised: `stripPythonComments` closes the gap, so star imports and named relative imports both resolve.
- **Tests:** comments and docstrings, a long-lived scanner (`scanFull` then two `scanIncremental` on one `Scanner`), re-export chains of one and two `__init__` levels, spaced relative imports. The `!ref.metadata?.receiver` guard was redundant with `bareOnLine` and is removed.
- **Not added:** a positive shebang-call test. `import ops` or `from ops import ops_entry` of an extensionless `bin/ops` links nothing on HEAD or here (the module is judged outside the project, and a script with no `.py` cannot be imported); bare `ops_entry()` after `import ops` is a NameError and now links nothing.
