# M0-02-R4 — Incremental scans re-resolve references to moved files; blob-hash keys for non-root repos

## Identification

Milestone: M0; priority: P2; risk: low; estimate min/expected/max: 2/4/6 h; role: scanner / incremental indexing.

## Objective

A plain `scan` or a non-git `sync` after a referenced class moves to another file restores the reference edge to the new path, as `scan --force` does; non-root repos store the right git blob hashes, and an unchanged file that git lists is not re-parsed.

## Dependencies

M0-02-R3 (hard: rename handling, `removeFiles` ledger), M0-10-R3 (hard: re-parse when what resolution could see has changed). No approval gate.

## Scope

- **Moved targets.** The removed-files ledger (M0-02-R2, `meta removed_files:<repo>`) records the referrers of each removed file. It gains the names those referrers resolved into it (`meta removed_names:<repo>`, the trailing identifier of each edge's `target_symbol`). When a scan parses a new or changed file whose text names one of them, the recorded referrers are re-parsed, as M0-10-R3 re-parses when a repo becomes visible, but limited to those referrers. The names are dropped once a parsed file defines one of them. All three paths (full scan, git sync, content-hash sync) use it.
- **Full scan removes deleted files before parsing,** so a rename within one scan records the old path's referrers, and neither the file map nor the symbol index still holds the old path while they are re-resolved.
- **Blob hashes.** `getGitBlobHashes` takes the directory its keys are relative to; the full scan passes the workspace root, so a repo at `libs/ui` stores `libs/ui/x.ts → <blob>`. The hash is stored only when the indexed content is that blob. Git sync skips a listed file whose stored blob hash is the id of its current content (a mode-only change, for example).
- **normalizePattern `./`.** The existing normalisation test also asserts that two spellings of one exclude (`./app/Services/**`, `app\Services\**`) do not trigger a filter-change re-parse.

## Out of scope

- References whose target moves into another repo (the ledger is per repo, as before).
- Edges with no `target_symbol` (path-based imports): moving the target breaks the import path, so the referrer changes and is re-parsed anyway.
- Git sync storing blob hashes for the files it re-indexes (it stores null, as before).

## Implementation plan

- `src/core/scanner.ts`: `removeFiles` records names; `takeReferrers` drops names of returning paths; new `movedReferrers` and `settleMovedNames`; wire into `_scanFullForRepo`, `_scanIncrementalForRepo`, `_scanIncrementalByHash`; move deletion before parsing in the full scan; blob-hash keys and skip.
- `src/core/git-tracker.ts`: `getGitBlobHashes(repoRoot, relativeTo)`, `gitBlobId(content)`.
- `tests/legacy-globs.test.ts`: e2e tests for moved targets (scan, sync without git, same-scan and cross-scan), non-root blob hashes and skip, `./` normalisation.
- Docs: `docs/cli-reference.md`, `docs/mcp-integration.md`.

## Acceptance criteria

1. After moving a referenced class to a new file, plain `scan` and non-git `sync` restore the reference edge to the new path, matching `scan --force` (e2e test).

3. normalizePattern `./` stripping has a test that fails when the stripping is removed.
