# M5-20-R1 — npm attribution: a nested lockfile that cannot be read gives manifest-only attribution

## Identification

Milestone: M5; priority: P2; risk: low; estimate min/expected/max: 1/1.5/3 h; role: scanner and package manifests.

## Objective

A nested `package-lock.json` (or `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`) that is there but cannot be read (a folder, a file without read permission) ends the lockfile walk, so the manifests answer, flagged `manifest`, and a parent folder's lockfile is never used. This is what the Composer attributor does since the M5-21 review.

## Dependencies

M5-20 (hard, DONE): `NpmAttributor`. The `exists` probe of the decision pass's workspace (M5-21 review) is already there. No approval gate.

## Cause

Found by M5-21 (`reports/M5-21.md`, "Findings outside this task"). `NpmAttributor.lockFor` (`src/core/manifests/npm.ts`) marks a folder as holding a lockfile only when one of its lockfiles reads as text (`this.read(...) !== null`). A lockfile that exists but cannot be read is treated as absent, so the walk goes on to the parent folder and attributes with that folder's lock.

## Scope

- `src/core/manifests/npm.ts`: `NpmWorkspace` gains the optional `exists(path)` probe (moved from `ComposerWorkspace`, which now picks it from there). `lockFor` stops at the first folder where a lockfile reads or exists. In that folder, the first readable, parseable lockfile answers, as before; if none does, the answer is the manifests', flagged `manifest`.
- `tests/external-refs.test.ts`: a nested `package-lock.json` that is a folder or a file without read permission, below a readable root lock, gives manifest-only attribution. A nested folder with a `package.json` and no lockfile still uses the root lock.

## Out of scope

- Any other npm attribution change. pip/Poetry/uv attribution is M5-22.
- The `CHANGELOG.md` entry: the integration owner writes it (lane rule); the report carries the sentence.
