## Objective

Every git sync sequence ends with the index that `scan --force` gives.

## Dependencies

M0-02-R4 and M0-02-R5 (hard), both DONE.

## Scope

All five scenarios were reproduced with reviewer C's probes against `develop@00407d6`, then rewritten as e2e tests.

1. **Folder repo.** Git sync of the primary repo lists the files of a registered folder repo that has no `.git` of its own (`packages/web`) and takes them over (`repo = <primary>`). The same happens when the repo is registered through a symlink (`web-link` → `packages/web`), which indexes it twice. The walk skips such folders by canonical path; git sync now drops listed paths under another registered repo nested in this one, compared the same way.
2. **Moved targets.** `settleMovedNames` dropped the whole record of a removed file as soon as any one of its names (`find`) was declared anywhere, so `UserService` re-added elsewhere did not re-link its referrers. Names now settle one at a time.
   - The re-link then exposed an order dependence: of two files declaring `find`, a bare-name call resolved to the first in symbol-index order. A fresh scan indexes in walk order, while a sync appends the files it re-parses, so the two could disagree.
   - The pick is now the declaring file nearest the caller (most shared leading folders), with ties broken by path.
3. **Rename plus copy.** `git mv a b` followed by an identical untracked copy at `a` removed `a`, because the rename's old path was taken as gone. An old path that still exists is now kept.
4. **Export pruning.** The CLI and MCP exports filtered with the file matcher only, so `--exclude '**/Http'` kept `app/Http/…` in the memberships. A shared `buildPathFilter` (matcher plus the walk's folder pruning) replaces it in both.
5. **Gitignored files.** Scan's walk ignores `.gitignore`, so it indexes gitignored files, while git sync never sees them: new or edited files are never indexed.
   - Git sync now asks git for the ignored entries (`git ls-files --others --ignored --exclude-standard --directory`), walks them with the scan rules, and lists the files whose content is not the indexed content. Deletions were already caught by the HEAD-tree check.
   - This keeps scan's behaviour (no gitignored file is dropped from existing indexes) and is documented in `docs/configuration.md`.

Blast radius: `resolveSymbolToFile` serves every bare-name reference (calls, instantiations, extends) in every language. All three scorers give identical totals before and after, and the full suite passes. `mapx impact` was not run, because this checkout has no MapX index. Grep shows the callers: `resolveReferencesWithMap`, the detectors' `ScanContext.resolveSymbolToFile` (framework scans), and route-middleware resolution.

## Out of scope

- Cross-repo edges after a delete/restore or a re-add, and repo order: M0-10-R4.
- `mapx status` listing raw git changes: M0-11-R3.

## Acceptance criteria

1. A registered folder repo inside the primary checkout keeps its files under its own repo after a plain sync of the primary, and a repo registered through a symlink is not indexed twice. Both are e2e tests and equal `scan --all --force`.
2. Remove `UserService.php`, add an unrelated file declaring `find()`, then re-add `UserService` elsewhere: the import, `param_type` and call edges of its referrers come back. This is an e2e test and equals `scan --force`.
3. `git mv a b` with an identical untracked copy left at `a` keeps both files indexed (test).
4. `export --format json --exclude '**/Http'` prunes the folder as scan does (test).
5. Scan and git sync agree on gitignored files: edits, additions and removals in ignored files and folders (test). Documented in `docs/configuration.md`.
