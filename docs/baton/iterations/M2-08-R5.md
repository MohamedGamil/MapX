# M2-08-R5 — Python and Java names imported from packages never link to same-named project symbols

## Identification

Milestone: M2; priority: P2; risk: low; estimate min/expected/max: 3/6/10 h; role: resolution engineer.

## Objective

M2-08-R3's rule for JS/TS, applied to Python and Java. A class, function or module that an import from outside the project binds is that package's. It never links a same-named project symbol, by any reference kind. Imports from project modules still link.

## Dependencies

M2-08-R3 (hard, DONE): the JS/TS import-bound gate (`boundOutside`) and its "positively outside" principle.

## Cause (probe, 2026-11-04)

A synthetic workspace was scanned with the real CLI on `develop@08aab1c`.

**Python.** `app/order.py` declares `class Order` with `total`, and `app/util.py` declares `join`. In `app/use_pkg.py` all 7 cross-file edges are false:
- `from stripe import Order`: `Sub(Order)` extends `order.py#Order`, and `Order()` gives a call and an instantiation edge to it;
- `Order().total()` and `stripe.Order().total()` link `order.py#total`;
- `import os.path as osp; osp.join()` links `util.py#join`.

**Java.** The project declares `com/acme/Invoice.java` with `total` and a static `helper`. In `com/acme2/UsePkg.java` all 6 cross-file edges are false:
- with `import com.vendor.Invoice`: `extends Invoice`, `new Invoice()` (twice), `new Invoice().total()`, and `i.total()` on a parameter of that type;
- `import static com.vendor.Util.helper; helper()` links `Invoice#helper`.

The reason is that the import-bound gate in `resolveReferencesWithMap`, and its use in `resolveClassName`, are JS/TS only. Python names fall through to name lookup: M5-19's `pythonExternalBindings` feeds the external-reference rows, but not the gate. Java has no binding map at all.

## Scope

- **Python:** a reference of any kind except `import` is gated when its bare name or its dotted receiver is bound by an import of a module that is positively outside the project:
  - **Positively outside** means no indexed file satisfies the module (`pythonModuleCandidate`), and its top-level name is no module or Python folder on any root the import searches (`pythonImportOutsideProject`). This is the `decideExternal('pypi', …)` rule M5-19 already uses.
  - **The receiver** comes from the reference's metadata when present (dotted bases, `new` classes), else from the call's line (`pythonReceiver`), as `externalRowsFor` reads it.
  - **A name the file itself declares** at module level is not gated; name lookup applies as before.
  - A gated reference gives no edge and goes to `noteExternal` (the existing pypi external rows).
- **Java:**
  - A single-type import `import a.b.C;` binds `C`, and a single static import `import static a.b.C.m;` binds `m`. The binding holds only when the import is positively outside:
    - `resolveJvmImport` resolves the class to no indexed file;
    - the package path (`a/b`) is no folder holding `.java`/`.kt` files, at any depth.
  - A reference whose bare name or receiver head such a binding holds gives no edge. Java has no external-reference ecosystem yet, so nothing is recorded.
- **`new X().m()`:** `resolveClassName` applies the same gate for Python and Java, so `resolveNewReceiverCall` gives no edge for a class bound outside the project.
- **`EXTRACTOR_VERSION` 24.**

### Changed by the independent review (see the report)

- **Python "positively outside":** the top-level name must also be no Python folder and no module stem anywhere in the project (`pythonNameInProject`), not only on the roots the import searches. A src/ layout seen from tests/ and a second source root are therefore unknown. This makes `decideExternal`'s root check redundant, so it was dropped.
- **Python name also imported from the project** (`try: from stripe import Order / except ImportError: from .local import Order`): not gated.
- **Java package declarations:** an import is outside only when no project JVM file declares that package with a class of that name, whatever its folder (`jvmProjectDeclares`). This covers flat layouts and nested classes at any depth.
- **One name called on two receivers on one line:** the line cannot say which reference is which, so `lineReceiver` returns null and name lookup applies, as before.
- **Declared-name check:** for Python it applies to module-level names only, so a method `json` does not ungate `import json`. For Java any member counts, since a member shadows a static import.

## Out of scope

- **A method called on a variable or parameter** whose type is a package class (Java `i.total()` with `Invoice i`, Python `o = Order(); o.total()`): name lookup stays. A variable's type is not tracked; M2-14 owns calls on variables holding a new instance.
- **Wildcard imports** (`import com.vendor.*;`, `from x import *`): which names they bind is unknown, so they bind nothing.
- **Kotlin and Scala imports:** same resolver, different syntax. Follow-up if wanted.
- **Unimported Python names (builtins such as `open`):** M2-08-R7.
- **Java implicit `java.lang` names** (`String`, `Object`): no import to bind them.
