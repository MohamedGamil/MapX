# M0-32-R1 — Architecture analysis: iterative SCC, no stack overflow on large cyclic graphs

## Identification

Milestone: M0; priority: P1; risk: low; estimate min/expected/max: 2/4/6 h; role: graph algorithms.

## Objective

`mapx scan` completes on large cyclic dependency graphs; strongly connected components are computed without recursion.

## Dependencies

M0-32 (hard), DONE.

## Scope

- **Iterative Tarjan.** `detectCycles` in `src/core/architecture-analyzer.ts` ran Tarjan's algorithm through a recursive `strongConnect`, one JavaScript frame per node on the DFS path. A generated 6,000-file TypeScript import chain closing into a cycle already fails `mapx scan` with `RangeError: Maximum call stack size exceeded` (reproduced before any change; M0-12-R3 hit it at 10,000 Java files). The DFS becomes an explicit stack of `(node, next neighbour index)` frames that visits nodes, updates low-links and pops SCCs in exactly the recursive order, so SCC membership, SCC order and member order are unchanged.
- **Cycle path for each SCC.** The breadth-first search that picks the reported path copied the whole path into every queue entry, dequeued with `Array.shift()` and tested membership with `scc.includes()`, which is quadratic on a 20,000-node SCC, and `cyclePath.push(...path)` spreads one argument per node. It becomes a parent-pointer BFS with a `Set` and a head index, visiting nodes in the same order, so it returns the same path.
- No other walk in the file is recursive: hub, layer-violation and cluster-smell detection are single loops over edges and metrics.

## Out of scope

- Recursive walks in other modules (clusters, PageRank, metrics). If the scan of the generated graph overflows in one of them after this fix, it is reported as a finding for a new task, not fixed here.
- Scan time growth on very large repositories (outside this task; noted in M0-12-R3).
- The dedup in `analyze()` sorts `involvedFiles` in place, so the stored `involved_files` of a cycle smell are sorted rather than in path order. Pre-existing; the acceptance criteria require unchanged smells.

## Implementation plan

- `src/core/architecture-analyzer.ts`: iterative `detectCycles`; Tarjan extracted as an exported pure function `stronglyConnectedComponents(adj, order)` so it can be tested directly against a small known graph.
- `tests/architecture-scc.test.ts`:
  - identity assertions on a small known graph (several SCCs, a self-loop-free singleton, nested back edges, a cross edge into a finished SCC), comparing the iterative function with a verbatim copy of the old recursive one and with hand-written expected components;
  - the cycle smells (description and involved files) for small graphs are pinned;
  - the analyzer on a 20,000-node in-memory cycle (no RangeError, one SCC with all 20,000 files);
  - an end-to-end `mapx init` + `mapx scan` on a generated TypeScript import chain closing into a cycle, then `arch_smells` queried for the one cyclic-dependency smell containing every file. The test uses 8,000 files (the recursive version fails from about 5,000) so that it runs in minutes; a 20,000-file real scan is run by hand and recorded in the report.
