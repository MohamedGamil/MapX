# M5-25 — Go package-qualified composite literals resolve to the type in the imported package

## Identification

Milestone M5; P1; risk low; estimate 2/3/5 h. Registered 2026-11-02 while planning M5-04, from the resolver gap recorded in `reports/M5-01.md`: only 4 of 23 Go dependency rows had an edge. It is a hard dependency of M5-04, so M5-04's fixture criterion can hold for Go without narrowing its scope.

## Objective

`domain.Order{}` in Go is an `instantiation` edge to `Order` in the imported project package.

## Cause

`queries/go/references.scm` captured composite literals of unqualified types only. `GenericWasmParser` attached the import path (`goPackage`) only to embedded qualified types (`extends`, M0-17-R5). The scanner's `resolveGoQualifiedType` already resolves a `goPackage` reference to the type in that package's directory, and to nothing for library packages.

## Scope

- `queries/go/references.scm`: `(composite_literal type: (qualified_type name: (type_identifier)))` as an instantiation.
- `src/parsers/generic-wasm-parser.ts`: `goPackage` metadata for qualified `instantiation` references too.
- `tests/go-qualified-instantiation.test.ts`.

Out of scope:
- **Package-qualified calls** (`domain.NewOrder()`, `pkg.Func()`) and method calls on qualified literals. They still resolve by name; any follow-up would be registered separately.
- **`src/core/scanner.ts`:** unchanged.

## Acceptance criteria

1. A real scan of the M5-01 Go app has an instantiation edge for each labelled cross-package literal (go-05..08, go-16, go-17, go-22, go-23) to the labelled file and type.
2. `d.Order{}` through an aliased import resolves to its package, not to a homonym `Order` in another package. `time.Time{}` and a third-party `money.Amount{}` make no edge, even though the workspace declares types with those names.
3. `npm run eval` edge recall and precision do not drop.
