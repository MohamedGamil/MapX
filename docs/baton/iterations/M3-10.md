# M3-10 — Case-sensitive symbol name lookup in resolution

## Identification

Milestone: M3; priority: P2; risk: medium; estimate min/expected/max: 2/3/5 h; role: graph resolution.
Sources: `docs/baton/reports/M3-06.md` ("Fixture changes" and "Limitations": `component: Cart` resolved to `const cart` in `CartView.vue`).

## Objective

Name-only resolution (`Scanner.resolveSymbolToFile`, used for calls, instantiations, type references and by every framework detector's `ctx.resolveSymbolToFile`) matches a declaration only under its language's case rules. `Cart` never resolves to `cart` in a case-sensitive language; PHP class-like, function and method names, and Pascal identifiers, still match across case.

## Dependencies

- M3-06 (hard, DONE): found the defect.
- Parallel lanes M3-08, M3-09 and M3-11 edit `src/core/scanner.ts` and `vue*.ts`: the change stays inside `resolveSymbolToFile` plus one helper.

## Scope

- **Where the lookup ignores case today** (`src/core/scanner.ts`):
  - `buildSymbolIndex` files every declaration under its lowercased name (and its exact name when that differs);
  - `resolveSymbolToFile` looks up the exact name, then the lowercased name, and when no candidate has the exact name falls back to the first language-compatible candidate, so `Cart` takes `cart`;
  - without a symbol index it calls `store.searchSymbols`, a case-insensitive substring `LIKE`, with the same first-candidate fallback.
- **Rule** (`matchesName(name, candidate, targetLanguage)`): a candidate matches when its name equals the looked-up name, or, ignoring case, when the target language is PHP and the candidate is a class, interface, trait, enum, struct, record, function or method (PHP's own rule: its constants, variables and properties are case-sensitive), or when the target language is Pascal (identifiers are case-insensitive).
- Both lookup paths (index and store) filter candidates by this rule before picking one. An exact-case candidate still wins over a case-folded one; the same-file preference is kept.
- Untouched: PHP namespace matching (already case-insensitive and correct), `resolvePhpFunction` (PHP functions, already case-insensitive), `fileDefines` / C# base kinds / Vue rules (already exact), the symbol index itself.

## Out of scope

- `mapx query` / `mapx search` and other user-facing searches stay case-insensitive (a search, not resolution).
- Vue component name conversions (kebab-case ↔ PascalCase) are the Vue rules' own matching (M3-02).
- Qualified names (`Foo::bar`, `a.b.c`) keep their current splitting.

## Implementation plan

- `src/core/scanner.ts`: a module-level `matchesName` helper; `resolveSymbolToFile` applies it in the index path (candidates from the lowercase bucket, which holds every case variant) and the store path.
- `tests/scanner-coverage.test.ts`, `tests/scanner.test.ts`: three unit assertions encoded the old fallback (`myfunc` → `MyFunc`; a store hit named `User` or `helperFn` taken for `UserController` / `helper`); they now assert no match, plus a PHP case-fold same-file case for the store path.
- `tests/legacy-language-accuracy.test.ts`: one e2e workspace (real `init` + `scan`), one `Cart` → `cart` look-alike per case-sensitive language (JS, TS, a `.vue` `const cart`, Python, Go, Rust, Java, Kotlin, Swift, Ruby, C#), and PHP / Pascal references across case.

## Expected outputs

## Acceptance criteria

1. In a real scan, `Cart` in a JS, TS, Python, Go, Rust, Java, Kotlin, Swift, Ruby or C# file (and in TS next to a `.vue` `const cart`) gives no edge when only `cart` is declared (e2e test, one case per language).

3. The routes, HTTP and edges scorers do not drop; MapX self-scan edge counts by type are reported before/after, with every vanished edge explained.
