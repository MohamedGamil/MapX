# M0-02-R11 — A sync killed before its upserts commit keeps restored files

## Identification

Milestone: M0; priority: P2; risk: medium; estimate min/expected/max: 2/3/5 h; role: incremental scanning.

## Objective

A sync killed after it read the `removed_files:` / `removed_names:` records of restored files, or the `pending_referrers:` queue, but before its upserts commit, leaves those records in place. The next sync then equals `scan --force`. The 2026-11-02 review found this window in M0-02-R10.

## Dependencies

M0-02-R10 (hard, DONE).

## Scope

- **`Scanner.takeReferrers` and `takePendingReferrers`:** return what they read, but defer deleting the consumed entries.
- **When the deletions run:** inside the transaction that writes the null-hash upserts of the files they re-index, in both the git and the hash sync, and in the full scan's write path. A run that returns early, before any upsert, also applies them.
- **How a deletion runs:** each re-reads the record when applied and removes only the taken keys or paths. Entries written in between (another repo's `queueReferrers`) survive.
- **On failure:** if the run throws before the transaction, nothing is consumed.

## Out of scope

The other record consumers (`movedReferrers` and the Vue registry), which the review did not report.

## Acceptance criteria

1. **Git and hash sync, restored file:** after `b.ts` is deleted, synced and restored, a sync that throws inside `upsertFile` is followed by syncs whose files and edges equal `scan --force`, including `a → b` (`tests/sync-interrupt.test.ts`).
2. **Git and hash sync, queued referrer:** after a crashed sync, a queued pending referrer is still queued; the next sync parses it and empties the queue (`tests/sync-interrupt.test.ts`).
3. **No regression:** the existing interrupt, skip and sync tests still pass.

## Verification

- `npx vitest run tests/sync-interrupt.test.ts`
- `npm run check`

## Recovery

Revert the task commit.
