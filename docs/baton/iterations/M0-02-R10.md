# M0-02-R10 — An interrupted sync loses the symbols of the files it started re-indexing

## Identification

Milestone: M0; priority: P1; risk: medium; estimate min/expected/max: 2/4/6 h; role: scanner, incremental sync.

## Objective

A sync interrupted after it started re-indexing files (SIGINT in `mapx sync`, or `abort()`) leaves the index so that the next sync re-parses those files, and the result equals `scan --force`.

## Dependencies

M4-04 (hard), DONE. Found by the M4-04 independent review (2026-11-01), and reproduced on the pre-M4-04 scanner.

## Current behaviour (`develop@e1d5da0` plus M2-08)

- **Git sync (`_scanIncrementalForRepo`).** Before parsing, it deletes each listed file's symbols and edges and upserts the file with its new `git_blob_hash` and `content_hash`. Parse results are written afterwards, in the resolve loop, which stops on abort. The next sync sees the same files listed, compares their blob with the stored one, finds them equal and skips them. Their symbols and edges stay missing until `scan --force`.
- **Hash sync (`_scanIncrementalByHash`).** The same, with `content_hash`: the next hash sync finds the content unchanged.
- **M4-04's effect.** That next git sync also skips the post-scan analysis.

## Scope

- **New `Store.setFileHashes(path, contentHash, gitBlobHash)`,** an `UPDATE` that leaves `metadata` and `namespace` as they are.
- **Both sync paths:**
  - the pre-parse upsert stores `content_hash` and `git_blob_hash` as null;
  - the resolve loop sets each file's hashes right after its parse result is written, in the same transaction.

  A file whose result was never written keeps null hashes, so the next sync re-parses it: the git path's blob comparison fails, and the hash path sees the file as new.
- **Test mocks** of the store gain `setFileHashes`.

## Out of scope

- The full scan path, which has its own resume state and incomplete-file detection (M4-03).

## Acceptance criteria

1. **Git sync.** In a git repo after a scan, edit two files, then sync with `abort()` called from the first `resolve` progress. The next sync re-parses both files, and its symbols and edges equal `scan --force`. E2e in process, `tests/sync-interrupt.test.ts`.
2. **Hash sync.** The same for a non-git workspace.
3. **No extra work.** An uninterrupted sync still skips unchanged files: a second sync parses nothing and emits no `cluster` progress (test).
4. **Hashes are only reset where they are written.** After a completed sync, the re-indexed files' `content_hash` and `git_blob_hash` are set, and their `metadata`/`namespace` match `scan --force`. Tested with a PHP file, whose namespace is stored.
