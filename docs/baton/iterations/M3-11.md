# M3-11 — Vue Router navigation from plain JS/TS modules (stores, guards, composables)

## Identification

Milestone: M3; priority: see TASKS.json; risk: low; role: parser / graph resolution.
Sources: `docs/baton/reports/M3-06.md` ("Limitations": navigation from plain `.js` / `.ts` modules is not read); edge-contract rule 9 in `iterations/M3-01.md`.

## Objective

Navigation written outside SFCs becomes part of the graph. `router.push` / `router.replace` in a store action, a navigation guard or a composable gives a `navigate` edge from that function to the route's component, exactly as M3-06 does for `.vue` files.

## Dependencies

- M3-06 (hard, DONE): the `navigate` type, `vue-navigation.ts` (target parsing, route table, `matchRoute`) and the scanner's `resolveNavigation`.
- Parallel lanes: M3-09 (import aliases) and M3-10 (case-insensitive lookup). Their fixes are not part of this task.

## Scope

- **Parser side:** `moduleNavigationReferences(source, symbols)` in `src/parsers/languages/vue-navigation.ts`, called from the JS and TS parsers for non-`.vue` files (a `.vue` file's script blocks go through the TS parser too and are already covered by M3-06's hook).
  - Receivers, as in M3-06: a local bound to `useRouter()` or `this.$router`, `useRouter()` itself, `$router`, and an import from the router module (`import router from '@/router'` or `'../router'`). New for modules: a local bound to the router being created (`const router = createRouter(…)` / `new VueRouter(…)` / `new Router(…)`), which guards in the router file call.
  - Owner (rule 2 for modules): the narrowest enclosing function or method symbol, by its bare name; otherwise none (the scanner's usual fallback).
  - An object that is not one of these receivers (`items.push('/x')`) gives nothing.
- **Scanner:** no change. `navigate` references already resolve through the route table, whatever the source file.
- **Fixture (`tests/fixtures/vue-sfc`), new pattern `router-module`:**
  - vue2: a Pinia store action (`stores/session.js`, `logout`) and a guard (`router/guards.js`, `requireTicketId`), both through the router module's import;
  - vue3: a composable (`composables/useCheckoutFlow.ts`, `finish`) through `useRouter()`, and a Pinia store action (`stores/cart.ts`, `checkout`) through the router module's import;
  - negatives: a plain array's `push('/orders')` next to the composable's navigation, and the `Dashboard` route name never selecting `Dashboard.vue`.

## Out of scope

- Guard return values and `next('/x')` / `next({ name })` (navigation without `push` / `replace`).
- A router injected into Pinia stores as `this.router` by a plugin.
- `@/` aliases (M3-09), case-insensitive name lookup (M3-10), and route renames on `sync` (M3-08).

## Implementation plan

- `src/parsers/languages/vue-navigation.ts`: `moduleNavigationReferences`; routers created in the file become receivers.
- `src/parsers/languages/javascript.ts`, `typescript.ts`: a one-line hook each, skipped for `.vue`.
- Fixture files and labels above; a `router-module` floor in `tests/vue-sfc.test.ts`.
- `tests/vue-navigation.test.ts`: a unit test of owners and receivers, and an e2e scan with a store action, a guard (including one in the router file itself) and a composable.

## Acceptance criteria

1. `router.push({ name })` / `router.replace(path)` in a store action, a navigation guard or a composable (with `router` imported from the router module, or from `useRouter()`) gives a `navigate` edge from that function to the route component: fixture `router-module` labels in both apps, plus the e2e test.
2. An unrelated object with a `push()` method gives no edge: a negative label and an e2e assertion.
3. (Lane) Precision does not drop; no floor is lowered.
