# M3-08 — Vue global registry: re-link on sync, scope per manifest folder

## Identification

Milestone: M3; priority: P2; risk: medium; estimate min/expected/max: 2/4/6 h; role: scanner / Vue resolution.

## Objective

The Vue global component registry (M3-02) and the Vue Router route table (M3-06) stay correct without `scan --force`. On the next `sync` or plain `scan`:

- adding or removing `app.component('X', X)` in a JS/TS file re-links the render edges of the components that use `<X/>`;
- renaming a route, or giving it another component, in the router file re-links the navigate edges of its callers.

Two Vue apps in one repo, each with its own `package.json`, keep separate registries.

## Dependencies

- **M3-02 (hard):** the registry (`globalRegistrations`, `Scanner.vueGlobalComponents`) and the render hint (`metadata.vue.global`).
- **M3-06 (scope added during the lane):** the route table (`routeRecords`, `buildRouteTable`, `matchRoute`) and the `navigate` references.
- **M3-07 (hard):** manifest-folder scopes for detectors (`frameworkScopes(repoRoot)`); the `vue-router` detector's `manifestDependencies` list `vue`.
- **M0-02-R4 (mechanism reused):** referrers recorded in `meta`, merged into the re-parse set of all three scan paths before parsing, and settled after a completed parse.

## Scope

**Scope per manifest folder.**

- A file's Vue scope is the `vue-router` detector's M3-07 folder that contains it. It is `''` when Vue is active for the whole repo (root manifest), or when the file is in no such folder.
- `vueGlobalComponents` builds one registry per (repo, scope), from the registrar files and `.vue` files of that scope.
- A render reference looks only in its own scope's registry.

**Re-link on sync.** `meta vue_registry:<repo>` keeps, for each JS/TS file that has any, its raw registrations (`globalRegistrations()`) and its route records (`routeRecords()`, without lines). Before parsing, every scan path compares the stored record with the new or changed files' text and with the deleted files:

- a `named` entry added, removed or retargeted affects its name;
- a changed `require.context` / `import.meta.glob` affects the names of the `.vue` files under the old and new glob folders;
- a `.vue` file added or deleted under a recorded glob folder affects its own name;
- a route record added, removed or changed affects that record, and so do the records whose redirect reaches it.

When something is affected, the unchanged `.vue` files of the repo join the re-parse set, exactly like M0-02-R4's referrers, if either:

- their tags name an affected component (`toPascal(tag)`), or
- their navigations an affected record may answer (by name, path or pattern).

Nothing else is re-parsed. The new record is stored only after the parse completes, as `settleMovedNames` does. A missing record (a first scan, or an index built before this task) is initialised from the current text and gives no diff.

## Out of scope

- `<component :is>`, barrel re-exports, Nuxt auto-imports and the other unhandled registrations listed in M3-02's report.
- Props / emits (M3-04) and Vuex / Pinia (M3-05). Navigation parsing and route matching belong to M3-06; this task only re-links them.
- Scoping by a root manifest that also lists `vue` alongside nested apps: M3-07 then reports the detector whole-repo, and the registry is whole-repo too. The route table stays per repo (M3-06).

## Acceptance criteria

1. Adding or removing `app.component("X", X)` in main.js and running sync (no .vue file changed) adds or removes the render edges from every component using `<X/>`, matching `scan --force`. Shown by an e2e test of git and non-git sync, which also checks that a component not using the tag is not re-parsed.
2. Two Vue apps in one repo (two package.json folders) keep separate global registries: a tag registered globally only in app A gives no render edge in app B (e2e test).
3. Renaming a route, or changing its component, in the router file alone and running sync updates the navigate edges of every caller, matching `scan --force`. Shown by an e2e test of git and non-git sync, which also checks that a component without navigation is not re-parsed.
