# M4-03 — Scanner: remove quadratic phases (name resolution, resume state, fileMap rebuilds)

## Identification

Milestone: M4; priority: P2; risk: low; estimate min/expected/max: 6/8/12 h; role: scanner performance.

## Objective

Scan time grows linearly with the number of files sharing a common name, without changing a single stored edge. The resume state writes a constant amount per batch, and no resolution path rebuilds `workspaceFileMap` from the whole database.

## Dependencies

All hard dependencies are DONE: the 2db08bd remediation tasks (D015). M5-19 has an interface dependency on this task, through `src/core/scanner.ts`.

## Measurement before planning (2026-11-01, `develop@a4bd752`, load average 2–10, 16 cores)

**Generated TypeScript workspace.** Each file `src/d<i%50>/m<i>.ts` imports and calls two other files' functions, and declares a class `C<i>` with methods `run` and `helper`. Real `mapx init` + `mapx scan`:

| Files | First scan |
| --- | --- |
| 2,000 | 5.5 s |
| 4,000 | 8.6 s |
| 8,000 | 17.9 s |
| 16,000 | 70.5 s (×3.9 for ×2 files) |

A CPU profile of a forced 16,000-file scan (85.6 s with the profiler) attributes 52.7 s inclusive to `resolveSymbolToFile`, of which 13.7 s is `languageOf`. The resume-state writes and the `fileMap` rebuilds do not appear in the profile.

**Cause.** Every call to a name declared in k files does O(k) work before it checks the caller's own file:
- filters the candidates by name;
- computes `languageOf` for each candidate and checks language compatibility;
- builds and sorts the list of candidate files;
- runs `closest()` over that list.

Here `helper` and `run` are declared in all N files and called from all N files, so this phase is O(N²). Real code has the same shape with names such as `get`, `handle`, `render` and `toString`.

**The spec 10 items.**
- **Resume state:** it rewrites the whole completed list after every 100-file batch, so O(N²/100) bytes. This is small next to resolution, but quadratic.
- **`workspaceFileMap` rebuilds:** the full-database rebuilds in `_scanFullForRepo`, `writeParseResult` and `resolveReferences` only run when the map is empty. Both public entry points (`scanFull`, `scanIncremental`) fill it first, so the rebuilds are unreachable, and `resolveReferences` has no caller.

## Scope

1. **`resolveSymbolToFile`, symbol-index path.**
   - The name-only part of a lookup is memoised once per resolution phase, keyed by name, source language and `callableOnly`: the case-matched candidates, the language-compatible candidates, the exact-case candidates, and their sorted file lists. The memo is cleared wherever the symbol index is rebuilt.
   - Each call then does only the work that depends on the caller:
     - a same-file check (a `Set` lookup);
     - the nearest file, from a directory-prefix map built lazily per memo entry. The map holds, for each directory prefix, the first file under it in sorted order. That gives exactly `closest(files, sourcePath)`: most shared leading directories, ties broken by sorted order.
   - Results are unchanged by construction. The PHP namespaced branch reads `phpNamespaces`, which fills during writing, so it is not memoised.
2. **Resume state.**
   - `scan_resume_state:<repo>` is written once per scan with the initial completed set.
   - Each batch appends one record, `scan_resume_batch:<k>:<repo>`, holding its own paths and its symbol and edge counts.
   - Loading concatenates the records. Clearing deletes them, through a new `Store.deleteMeta(key)`. The key ends in `:<repo>`, so removing a repo deletes the records too.
3. **`workspaceFileMap`.** The unreachable full-database rebuilds are removed, and so is the dead `resolveReferences`.
4. **Benchmark script.**
   - `scripts/bench/scan-scaling.ts` generates the workspace above at two sizes, runs real init + scan on each, and prints the times and their ratio.
   - `--max-ratio X` makes it exit 1 when the larger scan takes more than X times the smaller.

## Out of scope

- The parallel directory walk and post-scan steps: M4-04. That includes `discoverFiles` running twice in `scanFull` (once to fill the map, once in `_scanFullForRepo`), which is noted for M4-04.
- Resolution semantics, such as which candidate wins: M2-08 and M0-17-R6. Every edge must stay byte-identical.
- The other name-resolution users of the symbol index (`symbolIndex.get` in Vue and Go helpers): they did not show up in the profile.

## Implementation plan

**Files:**
- `src/core/scanner.ts`: memo and nearest index, resume records, removed fallbacks;
- `src/core/import-resolvers.ts`: export `nearestIndex` / `nearestFile` next to `closest`, sharing `sharedDirs` semantics;
- `src/core/store.ts`: `deleteMeta`;
- `scripts/bench/scan-scaling.ts`;
- `tests/scan-scaling.test.ts`: resume bytes, resume round-trip, the resolution scaling probe, and a property test of nearest against `closest`.

**Blast radius.** MapX's graph is not initialised in this checkout. Callers by grep:
- `resolveSymbolToFile` has 9 call sites in `scanner.ts`, all through `resolveReferencesWithMap` and the Vue and Go helpers;
- `closest` is used by `resolveSymbolToFile` and the import resolvers (`import-resolvers.ts`). The import resolvers are unchanged.

## Expected outputs

## Acceptance criteria

1. **Identical results.** Edges and symbols are byte-identical before and after on three workspaces: a MapX self-scan of `git archive HEAD` (3,762 edges), the generated 8,000-file workspace (48,000 edges), and the three fixtures (`npm run eval` floors hold, with the same totals). Shown by sorted dumps diffed in the report.
2. **Linear scaling on shared names.** Resolving N calls to a name declared in N files, with N = 20,000, completes in under 20 s, through the real `resolveSymbolToFile` on a symbol index (`tests/scan-scaling.test.ts`). It measured 0.6 s alone and about 4 s under the full suite's parallel load; before the change the same probe took 876 s. The limit was first written as 2 s and was raised so that load cannot make the test flaky.
3. **Benchmark.** `scripts/bench/scan-scaling.ts` at 8,000 and 16,000 files gives a ratio of at most 2.5, down from 3.9. Measured and recorded in the report; it depends on machine load, so it is not a CI test.
4. **Nearest file.** For random path sets and source paths, the nearest-file index returns exactly `closest(sortedFiles, source)` (property test, 2,000 cases).
5. **Resume writes.** On a 1,500-file in-process scan, every per-batch resume write has the same size within 10%, and the largest is under 4 KB (`tests/scan-scaling.test.ts`).
6. **Resume round-trip.** A scan aborted after some batches resumes without reparsing the completed files, and the edges then equal a fresh scan's. When the scan completes, `scan_resume_batch:*:<repo>` rows are deleted (`tests/scan-scaling.test.ts`).
7. **No full-database rebuild.** No code path calls `store.getAllFiles()` to rebuild `workspaceFileMap` outside `scanFull` / `scanIncremental` (grep in the report), and `resolveReferences` is removed.
