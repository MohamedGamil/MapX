# M3-05 — Vuex and Pinia resolution

## Identification

Milestone: M3; priority: P1; risk: medium; estimate min/expected/max: see `docs/baton/TASKS.json`; role: parser / resolution engineer (Vue).
Sources: `docs/reports/2026-10-30-laravel-vue-coverage-findings.md` §3 item 11 and §4 item 10; edge contract rules 2, 3, 7 and 8 in `docs/baton/iterations/M3-01.md`.

## Objective

Vuex map helpers, `$store.dispatch/commit('ns/NAME')`, in-module `dispatch/commit('NAME')`, Pinia `useXStore()`, `store.action()` and `useXStore().action()` link to the member in the right store file, never to a same-named function elsewhere or to the caller itself.

## Dependencies

- M3-03 (hard, DONE): `THIS_MEMBER_STEPS` and the recorded map-helper names; this task replaces step 3.
- M3-01 fixture and scorer (`tests/fixtures/vue-sfc`, `scripts/eval/score-edges.ts`).
- Parallel: M3-02 (template pass, component symbol) touches `vue.ts` and maybe `scanner.ts`. This task keeps its hooks out of `vue.ts`.

## Scope

1. **Parse side (`src/parsers/languages/vue-stores.ts`, called from the JavaScript and TypeScript parsers, which also parse `.vue` script blocks).**
   - Vuex store model per file, in `fileMetadata.vuex`:
     - a root (`new Vuex.Store({ … })`, `new Store`, `createStore`);
     - or a module (`export default { … }` with `namespaced` / `state` / `getters` / `mutations` / `actions` / `modules`, directly or through `const actions = { … }`);
     - its member names per kind, and `modules: { ns }` with each module's import specifier (or the inline module).
     - Arrow-function getters, actions and mutations that the generic extraction skips become `method` symbols scoped to their kind, so edges to them have a symbol.
   - Vuex calls:
     - `this.$store.dispatch/commit('ns/NAME')` (also `store.` / `$store.`) adds a `call` reference to `NAME` with the namespace and kind (actions / mutations);
     - `dispatch/commit('NAME')` on the action context inside a module stays in that module, when the module declares `NAME`.
   - Vuex / Pinia map helpers in an Options API component add one reference per mapped name from the component symbol (rule 7). `this.NAME()` for a mapped name goes through `THIS_MEMBER_STEPS` step 3, now namespace-exact.
   - Pinia, for a store hook `use…Store` imported (or defined in the file):
     - `useXStore()` → the hook in its file;
     - `x.action()` where `x` is bound to `useXStore()` in an enclosing scope, and `useXStore().action()` → the action in that store's file.
     - Existing name-only references at those calls are re-targeted, and missing ones (`clear`, `add` are skipped as JS built-in method names) are added.
   - Ownership (rule 2) for these references: top-level `<script setup>` statements and code directly in `setup()` belong to the component symbol (file basename); code in a member belongs to the member's bare name (`FETCH_ALL`, not `actions::FETCH_ALL`).
2. **Resolution side (`resolveStoreTarget`, same module).**
   - Pinia: the store file from the import, and only if it declares the member. No fallback, so never a same-named function elsewhere or the caller.
   - Vuex: the namespace path walks the root's `modules` through namespaced modules, followed through imports, and the member must exist in that module for its kind. Without a namespace, the root and its non-namespaced modules are used. In-module calls target the module file.
   - The scanner keeps the per-phase file → store-model map next to the PHP namespaces (stored metadata, replaced by this phase's parse results).

## Out of scope

- `<script setup>` / `setup()` ownership for references other than store ones, and the composable pattern: M3-04.
- Template calls and the component symbol: M3-02.
- `mapStores` (`this.cartStore.x()`), actions destructured from a store (`const { add } = useStore()`), `createNamespacedHelpers`, `$store.getters['ns/x']`, dynamic `registerModule`, and `@/` aliases in store files: recorded as limitations.

1. `this.$store.dispatch('users/FETCH')` links to `FETCH` in `store/modules/users.js`, not to a same-named action in another module (e2e test plus `vuex-dispatch` on the fixture).

3. Precision does not drop, and no floor of another pattern falls.
