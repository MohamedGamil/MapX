# M3-05-R1 — Vuex map-helper path forms and Pinia outside SFCs

## Identification

Milestone: M3; priority: P2; risk: medium; estimate min/expected/max: 3/5/8 h; role: Vue store resolution.

## Objective

Every documented Vuex helper form links to the module member. Pinia stores resolve in plain TS composables, and whatever their hook is named. Each new link names the exact store member, never a same-named function elsewhere.

## Scope

- **Map-helper path forms (`mapHelperEntries`).** A Vuex name with a path (`'users/activeCount'`, array or object value) names `activeCount` in namespace `users`. With a helper namespace as well (`mapActions('a', ['b/X'])`), the paths are joined (`a/b`).
- **`createNamespacedHelpers` (imported from `vuex`).** Helpers bound at the top level are recognised in three forms:
  - destructured: `const { mapActions } = createNamespacedHelpers('users')`;
  - renamed: `{ mapActions: mapUserActions }`;
  - as members: `const users = createNamespacedHelpers('users'); users.mapActions(…)`.
  Each carries its namespace. The Options API pass gets this through `mapHelperEntries`, so `this.NAME()` follows (M3-03 rule 6, step 3).
- **Members in imported objects.** In a store root or module, an imported binding as a kind's value (`actions`, `import * as mutations`), or spread into it (`actions: { ...auditActions, FETCH() {} }`), is recorded in `VuexModuleInfo.parts`. Resolution looks for the member in that file (`ctx.defines`) after the module's own members. `state` is not looked up in parts: state properties are not symbols.
  - Files of members (`getters.js` / `actions.js` / `mutations.js`, or `export const getters = { … }`) give their arrow-function members a symbol scoped to the kind, as M3-05 does in module files. Such files pass the store pass's gate by name.
- **Pinia outside SFCs.**
  - `const { checkout, add: addItem } = useXStore(); addItem()` in a JS/TS module gives a store reference to `add`. In SFCs the M3-04 composable pass already resolves these through the import (with re-exports), so it is left to that pass.
  - A binding is shadowed by a function declaration or a parameter of the same name in between.
  - `store.dispatch('x')` / `store.commit('x')` with a string argument is Vuex, whatever `store` is bound to.
- **Hooks of any name.**
  - A hook defined in the same file with `defineStore` is a store, whatever its name.
  - A store file records the hooks it defines in `files.metadata.vuex.piniaHooks`.
  - Pinia's own map helpers (`mapActions(useWish, …)`, the helper imported from `pinia`) accept an imported hook of any name. Resolution confirms the hook from its module's `piniaHooks`; a hook not confirmed gives no edge (`mapActions(useLegacy, …)` with a composable).
  - **Needs the scanner (companion patch, not applied here).** Member calls and destructured calls on an *imported* any-name hook (`const wish = useWish(); wish.checkout()`) need "not a store after all → default resolution". `resolveStoreTarget` can only return a target or no edge, so without the scanner change every member call on a plain composable (`const api = useApi(); api.fetchAll()`) would lose its default edge. A probe measured 3 lost correct edges. The companion patch adds a `fallback` flag to `VueStoreTarget`, an `undefined` result for an unconfirmed `fallback` target, and a scanner branch that then falls through to the default resolution.
