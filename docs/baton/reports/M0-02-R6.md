# M0-02-R6 — git sync re-parses a file whose working-tree edit was reverted to HEAD

Date: 2026-10-31. Base: `develop@00407d6`. Owner: maintainer. Iteration: `docs/baton/iterations/M0-02-R6.md`.

## Delivered

- **`src/core/scanner.ts` `_scanIncrementalForRepo`.** Git sync already reads HEAD's tree once (`getGitBlobHashes`) to find removed files. The same loop now also lists, as modified, every indexed file of the repo that meets three conditions:
  - git does not list it;
  - its stored blob id is not HEAD's blob;
  - it still exists.

  The blob comparison that follows re-parses the file only when its bytes are not the indexed ones. Before this, an edit reverted to HEAD while HEAD was still the last scanned commit appeared in no diff, so the edited symbols stayed in the index. `mapx status` also reported the file as stale forever.
- **Tests.** In `tests/legacy-globs.test.ts`, the describe block "git sync: an edit reverted to HEAD" holds two e2e tests. Each compares files, edges and symbols with the fresh scan and with `scan --force`:
  - a working-tree edit (adding a symbol and a `param_type` edge), synced, reverted with `git checkout --`, then synced;
  - a staged edit, synced, reverted with `git reset` and `git checkout`, then synced.

## Mutation check

With the fix removed (the develop `scanner.ts`), **each** of the two tests fails when run alone (`-t`). The staged-revert test was run on its own so that the first test's state could not cause its failure.

## Limitations

- Gitignored indexed files are not in HEAD's tree, so this check does not cover them. M0-02-R7 handles them.
- The check reads only files whose stored blob differs from HEAD's. A full scan stores `null` for a file that was modified when it was scanned, so the first sync after such a file is reverted re-parses it once.

## Independent review and fixes

Reviewer G (fresh agent, diff and criteria only) reproduced one P1 in this task:

- **P1-3, eol=crlf / autocrlf checkouts.** A full scan stores `null` blob ids when the working tree differs from HEAD's blobs. The HEAD-blob comparison then made every sync re-list and re-read every file.
- **Fix.** The comparison was replaced. Git sync records, in `meta dirty_paths:<repo>`, the paths git listed as changed when they were indexed, and a full scan records the same set. Once git stops listing one of them, it is read again once, and the blob comparison skips it if nothing changed.
- **Test.** "re-parses nothing on a no-op sync of an eol=crlf checkout, and still re-indexes a real edit" fails on the pre-fix scanner.
- **Mutation.** "re-indexes an edit that a full scan indexed, once it is reverted" fails when full scans stop recording the dirty set.
- **Measurement.** Reviewer G's `p1-crlf.sh`, re-run on the fixed code: `last_scanned` is unchanged across two no-op syncs.

Last review round (reviewer L): R6 behaviour was not questioned. A pre-existing gap was found and registered as M0-02-R8: after renaming a symbol, its unchanged callers keep their old edge after sync, on base as well.
