## Delivered

**Ancestry in the three framework presets.** Each keeps its path selectors as the fallback, and adds:
- `laravel`:
  - Models: `extends` `Illuminate\Database\Eloquent\Model`, `Illuminate\Foundation\Auth\User` and `…\Relations\Pivot`. External bases are leaves, so the Authenticatable user and Pivot are named.
  - Jobs: `implements Illuminate\Contracts\Queue\ShouldQueue`, except under `app/{Listeners,Mail,Notifications}`, whose classes queue for their own reasons.
  - Http: `extends App\Http\Controllers\Controller` (Laravel 11's base) or `Illuminate\Routing\Controller` (before 11).
- `nestjs` (M5-10's decorators and the Nest interfaces):
  - Enhancer: `implements` `CanActivate`, `NestInterceptor`, `PipeTransform`, `ExceptionFilter` or `NestMiddleware` from `@nestjs/common` (a regex on the qualified name).
  - Provider: `@Injectable`, except a class that is an enhancer by suffix or interface, so an `@Injectable` guard is in Enhancer only.
  - Entity: `@Entity`.
- `django`:
  - Models: `extends django.db.models.Model`.
  - Views: `inherits` any base under `django.views`, `rest_framework.views`, `.generics` or `.viewsets`.

## Limitations and findings

- **External bases are leaves (M5-09).** A class that extends a vendor subclass the preset does not name is placed by its folder only. For example, Laravel's `Authenticatable` and `Pivot` are named for that reason, and a Rails model reaches `ActiveRecord::Base` only through a workspace `ApplicationRecord`. Decorators are stored for PHP, TS/JS, Python, Java, Kotlin and C# only, so Dart and Ruby presets use ancestry and paths.
- **Multi-layer by design.** A class placed by ancestry in a folder another layer selects is in both layers, which gives a `multi-layer` warning, not an error. Since the review, a Laravel model in `app/Services` is in Models only. The docs say so.
- **Laravel's default `mapx init` excludes `database/**` and `resources/views/**`.** On a real Laravel index, Database and Views are therefore empty-layer warnings. The test fixture is initialised the way the e2e helper does it.
- **Finding outside this task (parsers, Lane B's area; since registered as M2-20).** A CommonJS `require('../x')` of a local module produced no file-to-file edge in a probe; only an inferred call edge appeared. An Express app written in CommonJS therefore shows few dependencies. The Express fixture uses TS ES imports.
- **Finding (C# name resolution; since registered as M2-21).** C# calls resolve by bare method name. In a first draft of the ASP.NET fixture, `orders.First()` on a service linked to a controller's `First()`, which gave false violations. The fixture uses unique method names. In real code this inflates C# violations.
- **Finding (review round, the scanner or PHP parser, Lane B's area).** In the Laravel 11 fixture, PHP files under `database/` and `resources/views/` get no edges at all: no `import` edge for `use App\Models\Order;`, no instantiation edge for `new Order(...)`, and no external candidate. The same lines in `app/` give edges. Database's and Views' rules (both on Models) therefore cannot be exercised, which is why the reviewer's emptying of them goes unnoticed. The probe is `scratchpad/laneD-review/work/mut-laravel`.
- **Ruby calls resolve by method name.** Only a call to a method the app defines (`Order.lookup`, `OrderMailer.receipt`) or `X.new` makes an edge. `Order.find`, from ActiveRecord, makes none. The rails fixture calls app-defined methods for that reason.
- Express, FastAPI, Next.js, Vue and the generic presets are path-only, since those frameworks define no base types for their layers.
