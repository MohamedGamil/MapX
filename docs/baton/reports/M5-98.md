### What the scorer does not cover

- **`violation` is one bucket.** `disallowed-layer`, `private-layer`, `internal-element` and the package rules all score as `violation`. The rule must match exactly, so each is checked, but there is no per-rule line in the output.

- A requirement is VERIFIED only where a test in this run exercises it. Report claims alone did not promote anything.
- REQ-ARCH-014 and REQ-ARCH-022 are PARTIAL because a part of their own text is unmet and is already named by a BACKLOG task. REQ-ARCH-017, -019 and -020 keep the VERIFIED verdict even though follow-ups exist, because those follow-ups extend past the requirement's text.
- REQ-ARCH-020: the verdict rests on API tests I ran and a Playwright suite that I did not (the M5-15 report records 7 passed). If you want a stricter reading, treat it as "VERIFIED on the report's evidence" until the Playwright run is repeated.
- `REQUIREMENTS.json` has no status validation: `scripts/baton/model.ts` `Requirement` has no `status` field, and `validate` only checks ids and task mappings. Every existing entry says `PLANNED`. The follow-up ids M5-98-R1 to R3 are proposals: they are not in `TASKS.json`. The proposed file uses `VERIFIED`, `PARTIAL` and `PLANNED`; the `PARTIAL` and `VERIFIED` values are new vocabulary the validator tolerates.
