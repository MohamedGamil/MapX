# M4-13 — Parse pool sizing from the work and the machine

Decision D025.

## Before

Any batch of more than 10 files got `min(files, cpus, 8)` workers, whatever its size or the memory available. Measured after M4-10 and M4-11:
- **Small work:** a generated 3,000-file project (small, simple files) parsed on 8 workers at 902 MB peak RSS, no faster than one thread at 300 MB.
- **Tiny scans:** a 20-file scan started 8 workers, at 717 MB and 1.1 s against 156 MB and 0.7 s on one thread.

## Measurements behind the constants (Node 26.13, 16 cores)

`$S/cost.mts` used a scratch copy of MapX's own `src`, `tests` and `scripts` (383 files, 3.4 MB of source, real code):

| Measure | Value |
| --- | --- |
| Main thread, warm grammars | 3,263 ms for all files: 1.1 KB/ms, 8.5 ms per file |
| Pool of 1: start to first result | 262 ms |
| Pool of 1: all files | 3,473 ms (0.94×) |
| Pool of 2 | 285 ms; 1,940 ms (1.68×) |
| Pool of 4 | 377 ms; 1,207 ms (2.70×) |
| Pool of 8 | 562 ms; 905 ms (3.61×) |
| Memory per worker | +60 to +110 MB RSS (215 MB with 1 worker includes the main thread's own growth) |

One worker never pays off. A cold worker repays its startup (about 300 ms) after about 350 ms of parsing, which is about 384 KB of real source. The constants in `POOL_SIZING` (`src/core/worker-pool.ts`):

| Constant | Value |
| --- | --- |
| `coldBytesPerWorker` | 384 KB |
| `warmBytesPerWorker` | 48 KB (no startup to repay) |
| `perWorkerBytes` | 128 MB (conservative) |
| `memoryShare` | 0.5 |
| `maxWorkers` | 8 |

## Delivered

- **`poolSize`:** for each batch, a pure function of files, bytes, CPUs, available memory, warm workers and the setting.
  - **"auto":** `n = min(8, cpus − 1, files, ⌊0.5 × available ÷ 128 MB⌋, max(⌊bytes ÷ 384 KB⌋, min(warm, ⌊bytes ÷ 48 KB⌋)))`, and 0 when `n < 2`.
  - **A number** is used as given, at most one worker per file. `0` means one thread.
- **`parseWorkersSetting`:** `MAPX_PARSE_WORKERS` first, then `settings.parseWorkers`. Each is `"auto"` or a whole number ≥ 0; anything else gives a warning and "auto".
- **Scanner:**
  - `workerLanes` sizes each batch from its files' `sizeBytes`, `process.availableMemory()` (falling back to `os.freemem()`) and the pool's live workers.
  - `--no-parallel` still forces one thread.
  - The pool's `size` is now an upper bound (`max(cpus, 8)`). Workers start only as batches need them, through `parse(…, maxLanes)`.
- **Tests opt in:** `useParseWorkers(n)` in `tests/helpers/e2e.ts`. Tests that exercise workers set `MAPX_PARSE_WORKERS` for their file and restore it afterwards:
  - `binary-workers`, `worker-pool`, `legacy-languages`, `legacy-php-resolution`, `legacy-php-worker`, `svelte` and `vue-sfc`;
  - `scanner-coverage`, inside its worker test;
  - the `package.sh` smoke scan.

  Without it, their small projects would now parse on the main thread, and their worker assertions would pass without testing anything.
- **Bench:** `scripts/bench/workers.ts --corpus <dir> --copies K` scans copies of a real directory. Generated files parse much faster per byte than real code.
- **Docs:** `docs/configuration.md` (Settings table and Parallel parsing) and the CHANGELOG.

## Results

| Project | Auto | One thread | Fixed counts |
| --- | --- | --- | --- |
| Generated, 3,000 files | one thread: 2,972 ms, 307 MB | 3,103 ms, 300 MB | 8 workers: 3,146 ms, 902 MB |
| Generated, 15,000 files | 8 workers: 13,503 ms, 1,539 MB | 13,775 ms, 868 MB | 8: 13,079 ms |
| MapX sources ×1 (276 files) | 5 workers: 2,679 ms, 800 MB | 3,332 ms, 342 MB | 2: 2,699 ms, 531 MB; 4: 2,561 ms, 724 MB; 8: 2,526 ms, 996 MB |
| MapX sources ×3 (829 files) | 8 workers: 6,061 ms, 1,348 MB | 9,142 ms, 514 MB | — |

Every index is identical to `--no-parallel`. On real code, end-to-end wall time gains less than the parse speed-up, because resolution, graph analysis and storage run on the main thread. Past 2–4 workers, extra workers buy little wall time for their memory. M4-12 (fewer grammars per worker) and M4-14 (fewer messages) reduce what each worker costs.

## Independent review (fresh agent)

The review was run on a loaded host (load average 6–15).

Confirmed:
- **The model holds up.** Auto was never clearly worse than both 0 and the best fixed count. For example, on MapX ×4, auto chose 8 workers: 7.1 s against 11.8 s on one thread; fixed 4 gave 7.7 s.
- **Memory per worker:** 95–105 MB, within the claimed range.
- **`sizeBytes`** is real at every parse call site.
- **The warm pool** has no small-sync regression.
- **Every test that relies on workers opts in.**

Findings:
- **P1, fixed:** Bun's `process.availableMemory()` reports the host's free memory inside a cgroup limit: 11 GB under `MemoryMax=600M`. The compiled binary would then pick 8 workers and get killed for memory, as a forced 8-worker scan was in a 700 MB cgroup (exit 137). Node's 0 at the limit also fell back to the host's free memory.
  - `availableMemory()` now takes the lowest of the host's free memory, the runtime's figure, and `constrainedMemory() − RSS`.
  - It moved to `worker-pool.ts` with an injectable probe, tested with the Bun-in-cgroup, Node-at-limit, no-limit, unlimited-sentinel and no-API cases.
- **P2, fixed:** 19 MB of JSON got 8 workers and 1 GB for a 6% gain. Static-tier files (JSON, YAML, Markdown, CSS, HTML) now weigh a twentieth of code bytes; tested.
- **P2, fixed:** the invalid-setting warning repeated per batch. It now prints once per value per process.
- **P2, fixed:** parsing was lenient. `" "`, `"1e1"`, `"0x10"`, `true` and `[4]` were accepted. Now only `"auto"`, digit strings and non-negative integers are; tested.
- **P2, fixed:** `scanner-coverage.test.ts` restored `MAPX_PARSE_WORKERS` outside a `try/finally`.
- **P2, fixed:** `docs/cli-reference.md`, the `--no-parallel` help text and the MCP `parallel` description now describe the automatic sizing. `docs/configuration.md` states the `max(CPUs, 8)` bound on explicit counts.
- **Accepted:** the eval and e2e scans of small fixtures now parse on the main thread. Parity between workers and the main thread is covered by the opted-in tests and by the bench's index comparison.

**Mutation checks of the fixes:**
- Ignoring the container limit fails 2 cases.
- Removing the static weighting fails the JSON test.
