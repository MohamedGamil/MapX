# M5-07-R1 — CI reporters locate files from the repository root when the workspace is a subfolder

Planned in `iterations/M5-07-R1.md`. Source: `reports/M5-07.md` (Limitations: "Paths are workspace-relative"). Rebased on develop `f0fc004` and revised after the coordinator's review (see Review 1).

## Delivered

- **`src/core/git-tracker.ts`:** `getRepoPrefix(dir)` runs `git rev-parse --show-prefix` through `execFileSync` with an argument array (and `core.quotePath=false`, as the other calls there). It returns the folder's path from the repository's top level (`sub/`), `''` at the top level, or null when git cannot tell (outside git, or a git that refuses the folder). `inGitCheckout(dir)` tells whether a `.git` exists at the folder or above it.
- **`src/arch/reporters/context.ts`:**
  - `ReportContext.pathPrefix`;
  - `reportPathPrefix(format, dir)`: `''` for `table` and `json`, which never ask git. For a CI format it returns git's prefix. When git fails in a folder inside a checkout, it warns on stderr (one line: `Warning: git could not locate <dir> in its repository (git rev-parse --show-prefix failed), so report paths are relative to the workspace, not the repository root.`) and returns `''`. Outside git there is no warning (review 1);
  - `repoPath(p, ctx)` puts a workspace-relative path under the prefix and normalises it, so the baseline `../bl.json` of a workspace in `sub/` is `bl.json`;
  - `locate` uses it for every location: a source file, a stale entry's baseline file and the configuration file. With no prefix, paths are exactly as before.
- **`src/arch/reporters/sarif.ts`:** the `targetFile` property follows the prefix too, and the header comment says `%SRCROOT%` is the repository root.
- **`src/cli.ts` (outside `affectedFiles`, 2 lines):** `reportPathPrefix` added to the existing reporters import, and `pathPrefix: reportPathPrefix(format, dir)` in the check's report context. The report carries no workspace root, so the reporters cannot learn the folder any other way. Nothing else in `cli.ts` changed, which keeps the merge with other lanes small.
- **Docs:**
  - `docs/cli-reference.md` (CI formats): paths are relative to the root of the git repository that holds the workspace, with a monorepo example. At the root or outside git they are workspace-relative. When git refuses the folder (a wrong `GIT_DIR`, or "dubious ownership", fixed with `safe.directory`), a stderr warning says the paths are workspace-relative. `table`, `json` and messages are unchanged.
  - `docs/architecture-rules.md` (CI reports): the same. It replaces the old advice to "run `mapx check` at the repository root".
- **`tests/arch-reporters.test.ts`:** a new describe with 3 tests, using real `git init` repositories and the real CLI:
  - a workspace in a subfolder;
  - a workspace at a repository root, and one outside git;
  - a workspace in a checkout that git refuses (`GIT_DIR` set to a missing folder).

`table` and `json` are unchanged on purpose. They are read with the workspace, and `json` is the `--compare` input. Messages are unchanged too: a stale entry's message still names `../bl.json#/entries/0`.

**Note on JUnit "file attributes":** the JUnit reporter has no `file` attribute. The Jenkins xUnit XSD that the reporter is validated against (`junit-10.xsd`) allows only `name`, `time`, `classname` and `group` on `<testcase>`, so adding one would fail that check. JUnit names a file in the first line of each testcase body (`path:line` in `<failure>`, `<error>` or `<system-out>`), and that line now carries the prefix. Adding a `file` attribute would need a schema decision, so I left it to the integration owner.

## Limitations

- **A multi-repo workspace outside git** (repos below a plain folder) has no single repository root, so paths stay workspace-relative. Code scanning for one of those repos would need per-repo paths.
- **Messages** keep workspace-relative paths, for example a stale entry's `../bl.json#/entries/0`, because they are shared with `table` and `json`.
- **One git call per `mapx check` in a CI format;** `table` and `json` make none. On a git failure, paths fall back to workspace-relative, with a stderr warning when the folder is inside a checkout. Outside git there is no warning: a plain folder is the expected case.
- **A baseline outside the repository** (`--baseline ../../outside/bl.json` from `repo/sub`) is located at `../outside/bl.json`, a path that leaves the repository. Before this task it was `../../outside/bl.json`, which leaves it as well. This predates the task and is left as the coordinator ruled; code scanning cannot point at such a file anyway.
- **Submodules:** a workspace inside a submodule gets the prefix from the submodule's own top level (git's view). An upload from the superproject would then miss the submodule's path. This is acceptable, per review 1.
- **The prefix is git's view of the folder:** git resolves symlinks in it. A workspace reached through a symlink into a repository gets the prefix from git's top level.
