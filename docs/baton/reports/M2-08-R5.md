# M2-08-R5 report: Python and Java names imported from packages never link to same-named project symbols

Spec: [iterations/M2-08-R5.md](../iterations/M2-08-R5.md). Started from `develop@08aab1c`; the change is uncommitted at the time of writing.

## Cause (reproduced before the fix)

A probe workspace was scanned with the real CLI:
- **Python:** all 7 cross-file edges of `app/use_pkg.py` were false:
  - `from stripe import Order`: the base `Sub(Order)`, the call and instantiation of `Order()`, and `Order().total()`;
  - `stripe.Order().total()`;
  - `import os.path as osp; osp.join()` → `app/util.py#join`.
- **Java:** all 6 cross-file edges of `UsePkg.java` were false:
  - with `import com.vendor.Invoice;`: `extends Invoice`, both instantiations, `new Invoice().total()` and `i.total()`;
  - `import static com.vendor.Util.helper; helper()` → the project's `Invoice#helper`.

The import-bound gate from M2-08-R3 ran for JS/TS only.

## Delivered

- **One gate for Python and Java (`importBoundOutside`)** in `src/core/scanner.ts`. It runs in the reference loop for every kind except `import`, and in `resolveClassName`, so `new X().m()`, Python `X().m()` and base walks are covered. A gated reference gives no edge and goes to `noteExternal`, which writes Python's pypi rows; Java has no ecosystem yet, so nothing is recorded.
- **Python:**
  - The binding comes from M5-19's `pythonExternalBindings`: modules no indexed file satisfies.
  - It is gated only when the top-level name is no Python folder and no module stem anywhere in the project (`pythonNameInProject` in `src/core/import-resolvers.ts`), and no other import of the file binds the same local name from the project (`pythonProjectBound`, relative imports included).
  - The receiver is read from the call's line (`lineReceiver`, formerly `pythonReceiver`).
  - `stripe.Order().total()` is decided by its callee (`pythonInstanceCallee`), since the parser names a new instance's class only when it is bare.
  - A module-level declaration of the name ungates it.
- **Java:**
  - `javaExternalBindings` binds the class of a single-type import, and the member of a single static import.
  - A binding holds only when the import is certainly outside: `javaImportOutsideProject` finds no file for the class and no folder of JVM sources for the package, and `jvmProjectDeclares` finds no project JVM file that declares that package together with a class of that name, whatever its folder and at any nesting depth.
  - Call receivers are read from the line; a class member of the same name ungates.
- **`EXTRACTOR_VERSION` 24.**
- **Tests:** 15 new e2e tests in `tests/import-bound-externals.test.ts` (two `describe` blocks, real `init` and `scan`), 34 in the file.

## Limitations

- **Calls on a variable or parameter** whose type is a package class keep name lookup: Java `i.total()` with `Invoice i`, Python `o = Order(); o.total()`. M2-14 owns variables holding a new instance.
- **A parameter shadowing an imported module** (`import yaml` and `def run(yaml): yaml.join()`): the call is gated as the module's, so the by-name edge base gave is gone. Parameters are not tracked.
- **Two calls on one line:** when one name is called on two receivers on a line, both references fall back to name lookup, as before, false one included.
- **Not gated:**
  - a dotted Python base (`class Sub(stripe.Order)`);
  - a Java call on the result of a static call (`Invoice.of().total()`);
  - on-demand imports (`import com.vendor.*;`, `from x import *`);
  - Kotlin and Scala imports.
- **Open M2-12 chain:** a base walk that meets a package base (`class Sub(Order)` with Order from stripe, then `Sub().total()`) keeps M2-12's inferred name lookup.
- **Sync:** when a project package that a Java file imports is deleted, sync keeps the old edges (M2-08-R8).
- **Java has no external-reference rows:** no ecosystem covers it yet.
