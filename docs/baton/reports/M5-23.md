## Delivered

- **Attribution columns filled** for every Go candidate decided external: `package`, `origin`, `direct`, `dev` and `attribution`. This happens in the same end-of-run pass as npm and Composer (`decideExternalRefs`), once per folder and import path.
  - `origin` is `builtin` for a standard-library package, `ambient` for cgo's pseudo-package `C`, and `package` otherwise.
  - `package` is the import path for a built-in (`fmt`, `net/http`) and `C` for cgo. Standard-library paths have no dot in their first element and module paths do, so they cannot collide. For a module it is the module path (`golang.org/x/sys` for `golang.org/x/sys/unix`). It is null when no module of the build list provides the import (unknown).
  - `direct` is 1 when the file's go.mod requires the module without `// indirect`. It is 0 when go.mod marks it `// indirect`, or when another go.work module requires it (transitive). A module only go.sum holds is transitive when go.mod's `go` is below 1.17. From 1.17, go.mod lists every module that provides a package, so such a module is **not listed**: `direct` and `dev` null (review P2). For an unknown package `direct` is 0 ("not in the build list") only when a complete go.sum was read and the path has a dot, and null otherwise. It is null for a built-in.
  - `dev`: see the decision below. It is null for a built-in, an unknown package and a module go.mod does not list.
  - `attribution` is `lock` when a readable go.sum holds the module (or its replacement), and `manifest` when go.mod alone answered, which is criterion 2's flag. That happens when go.sum is missing, unreadable or corrupt, or stale (it lacks a module go.mod requires). It is null for a built-in.
- **The build list and the module of an import** (`src/core/manifests/go.ts`).
  - The file's module is the nearest go.mod, from the file's folder up to its own repo's root (never above it, never into another repo). A go.mod or go.sum that is present but cannot be read (a folder, no permission) ends the walk: never a parent module's files. A corrupt one counts as unreadable.
  - The build list is go.mod's requirements, the modules go.sum holds hashes for (of content or of a go.mod only), and, when a go.work above the module `use`s it, the other used modules' requirements and go.sum, go.work.sum and go.work's `replace` directives.
  - The module is the build list's **longest** module path that is the import path or its prefix at a `/` (`cloud.google.com/go/storage` over `cloud.google.com/go`, as Go resolves it once a package moved to a nested module). A **major-version element** right after a module path (`/v2`, `/v5`) names another module, never a folder of v1: `github.com/go-chi/chi/v5/middleware` is `github.com/go-chi/chi/v5`, and with only `github.com/a/b` in the build list `github.com/a/b/v2/x` is unknown. `gopkg.in/yaml.v3` is its own path.
  - **Exact ties** (the review rule "an exact tie gives unknown"): distinct module paths are compared as whole strings at a `/` boundary, so two different modules cannot both be the longest prefix of one import path. There is no tie branch, because it could never run (and no mutation could kill it).
- **go.mod directives.**
  - `require`, in blocks or single lines, quoted or not. `// indirect` follows Go's rule (`modfile.isIndirect`): the comment's words are exactly `indirect`, or start with `indirect;`. `// not indirect` and `// indirect dependency` are direct (review P2).
  - `replace`: a directive that names a version (`M v1.0.0 => …`) applies only when go.mod requires that version; one without applies to every version; go.work's directives override the modules' (review P2). The required path stays the package, because the import names it. go.sum holds a replaced module's hash under its replacement. A module replaced by a local directory is the workspace's (M5-25-R1), so it has no row; the stale check does not ask go.sum for its hash. A replacement path is not an import path of the build list: `github.com/acme/uuid` imported directly when it only replaces `github.com/google/uuid` is unknown.
  - `exclude`, `retract`, `toolchain`, `godebug` and `ignore` change no module path and are skipped.
  - `tool` (Go 1.24) is parsed. A tool is a main package that no code imports, so it gives no row, and it does not make its module dev.
  - A dotless module path that go.mod requires (through a non-local `replace`) is that module, never the standard library.
- **Stale go.sum** (M5-21 review P2, for Go): go.mod requires a module whose hash (or its replacement's) go.sum lacks. That module is attributed from go.mod, flagged `manifest`. An import no module provides is then unknown (`direct` null, `manifest`), never "not in the build list".
- **Standard library** (`src/core/manifests/go-stdlib.ts`, generated; `GO_STDLIB_SOURCE` records the source). It is the union of `go list std` of Go 1.22.12, 1.23.12, 1.24.13, 1.25.14, 1.26.10 and 1.27.3, run in the official `golang:<v>-alpine` Docker images (no local Go here). `go list std` lists only the packages that build for the current target, so each release is listed for every GOOS of `go tool dist list` (one GOARCH each), with cgo off and on (review P2: this adds `syscall/js` and `runtime/cgo`). It holds 181 importable packages: `vendor/…` and every package with an `internal` element are dropped, because a program cannot import them. The generator is `scripts/gen-go-stdlib.sh` (it removes each image it pulled). The list does not depend on the Go that runs MapX; a test checks it against `go list std` when a `go` is on the PATH (skipped here).
  - **Recognition (decision).** The brief's rule is "the first path element has no dot". Every list entry satisfies it, and MapX uses the list rather than the rule alone: a dotless path the list lacks (a GOPATH-style or `vendor/` import, a typo, or a package of a Go newer than 1.27) is unknown, not guessed to be the standard library. Regenerating the list picks up a new release.
- **Decision: dev for Go.** Go has no dev requirements. MapX calls a module **dev-only** (`dev` 1) when every reference to it from a Go module (the files under the same go.mod) is in a `_test.go` file, and production (`dev` 0) otherwise. This is the closest Go analogue of `require-dev`. It is computed in the decision pass over every Go row, stored or attributed now, so a file added, edited or removed changes it even when no input file changed. `goTestOnlyModules` does the grouping. A nested go.mod is its own scope. The `tool` directive was considered and rejected: no code imports a tool, so it would label no row.
- **Inputs, skip, staleness, sync.** The Go attributor records every go.mod, go.sum, go.work and go.work.sum it read, or probed and found absent, in M5-20's `external_inputs` record. As a result the next pass skips re-attribution when nothing changed, Go rows with no attribution (new rows, or an index built before) are still attributed (`go` joins `ATTRIBUTED_ECOSYSTEMS`), `mapx status` and the `check`/`arch` gates report a go.sum-only change, and a sync re-attributes like `scan --force`.

## Limitations

- **No module contents.** MapX reads no module cache, `vendor/modules.txt` or network. When both a module and a nested module could hold a package, the longer path wins; Go itself reports "ambiguous import" when both really do.
- **Unknown when no module matches.** Without a readable go.sum, an import whose module go.mod does not list (Go < 1.17 go.mod lists no indirect modules) is unknown; no host convention (`github.com/owner/repo`) is guessed.
- **dev is a property of the code, not of go.mod.** A module that production code also uses is production everywhere in that Go module, so a rule "production must not use dev modules" cannot fire for Go; `dev` reports test-only dependencies. A `_test.go` file is the only test marker; `testdata/` and build tags are not considered.
- **go.work** is read when it `use`s the file's module. A go.work outside the repo, `GOWORK` and `GOFLAGS=-mod=vendor` are not honoured.
- **The standard-library list** covers Go 1.22 to 1.27, every GOOS, cgo off and on. Packages behind the `race`, `msan` or `asan` build modes (`runtime/race`, `runtime/msan`, `runtime/asan`) are not listed; programs do not import them. A package that only Go 1.21 or older had is not guaranteed (none was removed in that range). Regeneration needs Docker and network access.
- **An unreadable go.mod** hides the module path, so the module's own imports (`example.com/app/x`) are rows of unknown package too, flagged `manifest`; MapX cannot tell them from third-party modules.
- **An unversioned local replace to a directory outside the workspace** (`X => ../../outside/y`) still makes X the workspace's (M5-25-R1), so its imports have no row.
- **An `// indirect` module that the code imports** is transitive by the task's rule, although `go mod tidy` would make it direct.
