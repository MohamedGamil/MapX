# M4-31 report — Test runs add no more than ten process listeners

Base: develop@ec44845, on top of M4-28-R1, M4-28-R2 and M4-29.
- Changed: `src/cli.ts` (`loadContext`) and `src/core/store.ts` (`Store.onClose`).
- Tests: the Store mock in `tests/cli.test.ts` gains `onClose`; `tests/process-listeners.test.ts` is new.

## Cause

`NODE_OPTIONS=--trace-warnings npx vitest run tests/cli.test.ts tests/cli-coverage.test.ts tests/arch-smells.test.ts` reproduced the three warnings, for `exit`, `SIGINT` and `SIGTERM`.
- Every stack points to `process.once` in `loadContext` (src/cli.ts:3797–3799), called from command actions (cli.ts:623, :681) under `Command.parseAsync`.
- Each `loadContext` call added three listeners to close its store, and never removed them.
- A test file that runs eleven commands in-process with `buildCLI().parseAsync` therefore passes ten.
- `grep` finds no other `process.on/once` of these events in src/. The MCP server and `Store` add none.

## Delivered, per acceptance criterion

**AC1 — `npm run check` output has no MaxListenersExceededWarning. Met.** The base run printed it 6 times (2 worker processes × 3 events), as did the M4-28-R1, M4-28-R2 and M4-29 runs. The run after the fix prints it 0 times (`grep -c` below).

**AC2 — listener counts return to their starting values after a store is closed (test). Met.**
- **The fix:**
  - `loadContext` registers its store in one module-level set.
  - One `exit`, one `SIGINT` and one `SIGTERM` listener close every store in the set. They are added with the first store and removed when the last store is closed, through the new `Store.onClose(fn)`, which runs once on `close()`.
  - Exit and signal behaviour are unchanged: the stores are closed, and the process exits with 130 on SIGINT or 143 on SIGTERM.
- **`tests/process-listeners.test.ts`**, on a workspace initialised and scanned with the real CLI:
  1. After twelve `loadContext` calls, each count is at most one above its start. With one of the twelve stores closed, it is exactly one above. With all closed, the counts equal their starting values. Closing a store twice changes nothing, and no warning is emitted.
  2. After twelve in-process `mapx status` runs (`buildCLI().parseAsync`), the counts are at most one above their start, and no MaxListenersExceededWarning is emitted.
