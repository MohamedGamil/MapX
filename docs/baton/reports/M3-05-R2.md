## Delivered

- **Plain modules that import only a store hook (Pinia).** The store pass now also runs on a module that calls a hook it imports from the project (`PROJECT_HOOK_IMPORT`: relative, absolute or `@/`, `~/`, `#/`), **when the file's package lists `pinia`**. Before, such a module needed a `use…Store` name, a store word, or an import of `vue` / `pinia`, so `const w = useWish(); w.add()` never reached the pass. Resolution then works as in R1: the hook is a `fallback` target, confirmed from the store file's `piniaHooks`.
- **A hook that is not a store resolves exactly as without the pass** (review P1-a/b/c). When `store.dispatch` / any-name hook targets are rewritten, the pass now records the call as the generic extraction gave it (`VueStoreTarget.call`: name and source). When resolution finds the hook is not a store, `storeCallOrPlain` (in `vue-stores.ts`, called at the top of the scanner's reference loop) gives back that original reference without a store target. The scanner's library filter (`JS_GLOBAL_FUNCTIONS`, package receivers), the original name (`send`, not `submit`) and the original source (`Page::render`, not `onClick`) all apply again.
- **Vuex member objects whatever the file name.** In a plain module, **when the file's package lists `vuex`**, an exported object (default or named, or an identifier bound to one) gives its arrow-function members `method` symbols (`memberObjectKind`). The object qualifies when every member is a function, and either all members take an action's context (`context`, `ctx`, or an object pattern taking `commit`, `dispatch`, `state`, `getters`, `rootState` or `rootGetters`) or all take `state`. A mix gives nothing.
  - Context members are scoped `actions`.
  - `state` members are `getters` or `mutations`, as the export or file name says (`userMutations`). Otherwise they are `mutations` when one of them writes to `state`, and `getters` when none does (review P2-b). A write is an assignment, update or `delete` of `state.…`, a mutating method on it (`state.items.push`), or `Object.assign(state, …)`.

  The module side (R1 `parts`) already recorded `actions: userActions`, so `ctx.defines` now finds the member. Files named `actions.js` / `getters.js` / `mutations.js`, and `export const actions = …`, keep the R1 behaviour.
- **The package check** (`storeDependencies`): the nearest `package.json` above the file that declares dependencies (`dependencies`, `devDependencies` or `peerDependencies`; a `{"type": "module"}` marker is skipped). It is cached per manifest by mtime. It is read only when one of the two widenings is the reason to run the pass (`storePass`). The parsers get the file's absolute path through the parse options, from the in-process path (`scanner.ts`) and from the worker path (`parse-worker.ts`).
- **Files changed outside `affectedFiles`**, needed by the review's direction:
  - `src/core/scanner.ts`: 3 lines, the restore and `absolutePath` in the parse options;
  - `src/types.ts`: `call` on the Pinia target;
  - `src/parsers/parse-worker.ts`, `javascript.ts`, `typescript.ts`: one line each, passing `absolutePath`.

  Root `CHANGELOG.md` (in `affectedFiles`) is left to the integration owner, per the lane brief.

## Limitations

- **The package check is the nearest manifest with dependencies.** It does not find a store library hoisted only to a monorepo root above a package that lists other dependencies. Nor does it count an existing `defineStore` / `createStore` elsewhere in the repo (the integration owner's alternative), because the parse cannot see other files. A file outside any package gets neither widening.
- **A `package.json` edit does not re-parse files.** The manifest cache follows the mtime, but adding `pinia` or `vuex` to a package moves no Vue scope, so files parsed before keep their old result until they change or a forced scan runs.
- **Confirmed stores keep the R1 owner rule.** A store call inside an object member in a class method is attributed to the member's name (`onClick`). The restore covers only hooks that turn out not to be stores.
- **Member objects by signature are a heuristic, now limited to vuex packages.** A member whose first parameter has another name (`s`, `_`), or takes none, disqualifies its object. A getters object in which no name says `getters` but a member writes state is scoped `mutations`.
- Root `CHANGELOG.md` is not edited (lane brief); the line is below. R1's other limitations stand.
