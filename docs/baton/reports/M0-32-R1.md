# M0-32-R1 — Architecture analysis: iterative SCC, no stack overflow on large cyclic graphs

Date: 2026-10-31. P1 found during M0-12-R3 (`reports/M0-12-R3.md`): `mapx scan` crashed with `RangeError: Maximum call stack size exceeded` in the recursive Tarjan `strongConnect` of `src/core/architecture-analyzer.ts` on a large cyclic graph.

## Reproduction (before any change)

- **In memory:** the analyzer on an n-node chain closing into a cycle (`f0 -> f1 -> … -> f(n-1) -> f0`, mock store). 2,000 nodes passed; 5,000, 8,000, 12,000 and 20,000 nodes each threw `RangeError: Maximum call stack size exceeded`.
- **Real CLI:** a generated 6,000-file TypeScript workspace (`src/m<i>.ts` imports and calls `f<i+1>` from `./m<i+1>`, the last file closing back to `m0`), `mapx init` + `mapx scan` from this checkout. The scan exited 1 after parsing, resolving and clustering, with the RangeError thrown at `strongConnect (src/core/architecture-analyzer.ts:80)` through repeated frames at line 86.

## Delivered

| Acceptance criterion | Change | Proof |
| --- | --- | --- |
| A generated cyclic graph deep enough to overflow the recursive `strongConnect` is scanned without a RangeError, and its SCCs are reported | `stronglyConnectedComponents(adj, order)` (exported, pure): Tarjan with an explicit stack of `(node, next neighbour index)` frames. A child's low-link is folded into its parent's when the child's frame pops, exactly where the recursive call returned. `detectCycles` keeps components with more than one member, as before. The cycle path per component is a parent-pointer BFS with a `Set` and a head index (`shortestCycleThrough`), replacing a BFS that copied the whole path per queue entry, used `Array.shift()` and `scc.includes()` (quadratic on a 20,000-node component) and ended in `push(...path)`. | `tests/architecture-scc.test.ts`: "handles a 100,000-node chain closing into a cycle without recursion"; "reports one cycle over all files of a 20,000-file chain closing into a cycle" (analyzer, all 20,000 files in the one smell, description path `m19999 -> m0 -> m1 -> … -> m19998 -> m19999`); e2e "scans without a RangeError and stores the one cyclic-dependency smell over every file" (real `mapx init` + `mapx scan` on an 8,000-file chain, `arch_smells` queried: exactly one `cyclic-dependency` row whose files are every file). A manual 20,000-file real scan is recorded below. |
| SCC membership and the cycle smells on the existing fixtures are unchanged | The iterative DFS visits, updates low-links and pops components in the recursive order, so components, their order and their member order are identical; the BFS visits nodes in the same order, so it returns the same path. | "finds exactly the known components, in the order and member order of the recursive algorithm" (11-node graph: `[f] [e,d] [i,h,g] [c,b,a] [j] [k]`, hand-written and compared with a verbatim copy of the old recursive function); "matches the recursive algorithm on seeded random graphs" (50 graphs, 5–64 nodes, up to 3 edges per node, self-loops and duplicates included); "reports the same cycle smells on the known graph as before" (descriptions and involved files pinned, and they pass on the original code, see mutation M0). Existing `tests/architecture-analyzer.test.ts`, `architecture-analyzer-coverage.test.ts`, `smells-dedup.test.ts`, `scanner-coverage.test.ts`: 17 tests pass unchanged. |

No other walk in `architecture-analyzer.ts` is recursive: hub, layer-violation and cluster-smell detection are single loops over files, edges and metrics. On the same generated input no later scan phase overflowed either (the 20,000-file scan below exits 0 after PageRank and the rest).

### Manual 20,000-file scan

The same generator with 20,000 files, this branch, real CLI: `init` exit 0; `scan` exit 0 in 323 s (load average 37–67, shared machine); `arch_smells` holds one `cyclic-dependency` smell with 20,001 entries (the path closes on its first file) covering all 20,000 files; 40,000 edges. The registered e2e test uses 8,000 files rather than 20,000 so that it finishes in a few minutes: on this machine the scan itself (parsing and resolution, not the analyzer) took about 5 minutes at 20,000 files, and 8,000 files is well past the ~5,000-node overflow point of the recursive version (mutation M0 shows it fails there).

## Limitations

- The registered e2e test scans 8,000 files, not 20,000; 20,000 is covered in memory (analyzer) and by the manual real scan above.
- The dedup in `analyze()` sorts each smell's `involvedFiles` in place, so stored cycle smells list files sorted, not in path order (the description keeps the path). Pre-existing and left as is, since the criteria require unchanged smells.
- Scan time grows faster than linearly with file count on this generated graph (6,000 files: 82 s for a first scan; 20,000 files: 323 s), in phases other than smell detection. Outside this task (see M0-12-R3).

Changelog: `mapx scan` no longer crashes with a stack overflow on large cyclic dependency graphs; cycles are found with an iterative Tarjan and reported as before (M0-32-R1).

## Post-acceptance change (2026-10-31, integration)

The 8,000-file real-scan test took 211 s of a 214 s run, so it now runs only with `MAPX_SLOW_TESTS=1` (`MAPX_SLOW_TESTS=1 npx vitest run tests/architecture-scc.test.ts`). The in-memory 20,000-file analyzer and 100,000-node SCC tests, which fail with the RangeError on the recursive version, still run in every `npm test`.
