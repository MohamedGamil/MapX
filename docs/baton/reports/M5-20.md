## Delivered

- **Attribution columns filled** for every npm candidate decided external: `package`, `origin`, `direct`, `dev` and `attribution`. M5-19 created these columns and left them null.
  - `origin` is `builtin` for a Node built-in module and `package` otherwise.
  - `package` is `node:<module>` for a built-in: `fs`, `node:fs`, `fs/promises` and `node:fs/promises` all give `node:fs`. It cannot collide with an npm name, because npm names have no `:`. For a package it is the package name of the specifier: `@acme/logging/core` gives `@acme/logging` and `lodash/get` gives `lodash`.
  - `direct` is 1 when a `package.json` from the file's folder up to its own repo's root lists the package in `dependencies`, `peerDependencies`, `optionalDependencies` or `devDependencies`, and 0 otherwise. A monorepo package therefore sees its own manifest and its repo root's, as Node's resolution does. The walk never goes above the repo's root and never into another repo (review P1).
  - `dev`:
    - for a direct package, it comes from the nearest manifest that lists it. Production fields win, so a peer repeated in `devDependencies` is production;
    - for a transitive package, it comes from the lockfile: dev-only in the dependency tree;
    - it is null when unknown (no readable lockfile, or a package the lockfile does not hold) and for a built-in.
  - `attribution` is `lock` when a lockfile was read for the file. It is `manifest` when none exists or none could be read, which is criterion 2's flag. It is null for a built-in.
  - Rows decided internal, and rows of other ecosystems, keep all five columns null. M5-21 … M5-23 plug in at the same place.
- **Node built-ins** (`src/core/manifests/npm.ts`): a static list, the union of `builtinModules` of Node 20 … 26. It includes the `_stream_*` modules that Node 26 dropped, and the `node:`-only `test`, `test/reporters`, `sqlite`, `sea`, `ffi` and `quic`.
  - Every `node:` specifier is a built-in. Without the prefix, only an exact name from the list counts, so `test`, `sqlite`, `fs/x` and `punycode/` are npm specifiers.
  - Polyfills (review P2, the owner's decision): a bare built-in name whose package the nearest readable manifest lists (in any dependency field) is that npm package (`buffer` with `"buffer": "^6"` gives `buffer`, origin `package`). `node:buffer` is always the built-in.
  - The list does not depend on the Node that runs MapX. A test checks that it covers the running Node's `builtinModules`. I checked it against Node 22.23, 24.11 and 26.13 on this machine.
- **Lockfiles.** MapX uses the nearest folder, from the file up to its repo's root, that holds one. In that folder it tries `npm-shrinkwrap.json`, `package-lock.json`, `pnpm-lock.yaml` and `yarn.lock`, in that order, and uses the first readable one. Each is reduced to one map: package name → dev-only, production or unknown.
  - `package-lock.json` / `npm-shrinkwrap.json`: the v2/v3 `packages` map (nested copies included) or the v1 `dependencies` tree, using npm's `dev` flag. A name is production if any of its copies is; `devOptional` counts as production. Workspace folders and links are not packages.
  - `pnpm-lock.yaml` v5, v6 and v9: the importers (or a single project's top-level sections) are the roots, and the `packages`/`snapshots` dependencies are the edges. A name reached from a production root is production; one reached only from dev roots is dev. An `npm:` alias (`alias: {specifier: npm:real@^1, version: real@1.0.0}`, `alias: real@1.0.0` as a dependency, v5 `alias: /real/1.0.0`) stands for its real package in roots and edges (review P2).
  - `yarn.lock` v1 and Berry: the same graph. Yarn records no dev flag, so the roots are the `package.json` files of the lock's repo in the lock's folder and below. `@workspace:` entries are not packages.
  - The readers are line-based and need no new dependency. A text that is not a lockfile throws, and the attributor treats it as unreadable.
- **No network and no `node_modules`.** Only manifests and lockfiles in the workspace are read. File reads that fail (for example a lockfile that is a folder) count as absent.
- **Where it runs.** Attribution runs in M5-19's end-of-run decision pass (`decideExternalRefs`), once per folder and specifier. A row is written when its decision or any attribution column changed. Store changes:
  - `getExternalCandidates` returns the attribution columns;
  - `setExternalDecisions` writes them with the decision, and its argument changed from `[external, id]` tuples to `ExternalDecision` objects. The decision pass is its only caller.
- **Inputs recorded** (review P2, `src/core/manifests/inputs.ts`). Each pass records in meta (`external_inputs`):
  - every manifest and lockfile path it read (or probed and found absent), with an md5 of its content;
  - the yarn locks' roots;
  - when it started.
- **Skipping re-attribution** (review P2). The next pass compares the recorded inputs.
  - A file whose mtime is more than 2 s older than the recording is unchanged without being read; any other is hashed.
  - When no recorded file changed and the indexed folders give each yarn lock the same roots, the stored attribution stands. Only rows with no attribution, or rows that became external, are attributed, and their reads are added to the record.
  - Otherwise every row is attributed again, and each lockfile is parsed once per run.
  - A no-op sync therefore parses no lockfile (timings in "Review").
- **Staleness** (review P2, `src/core/staleness.ts`). `findStaleFiles` reports a recorded manifest or lockfile whose content changed, appeared or went as changed. `mapx status`, MCP and the `check`/`arch` gates (exit 4) therefore see a manifest-only or lockfile-only change, and `check --sync` re-attributes.
- **Sync parity.** Every completed scan and sync compares the manifests and lockfiles on disk with the record and re-attributes when they differ. A sync therefore equals `scan --force` when `package.json` or a lockfile changes, appears, goes or is corrupted, and when a newly indexed folder adds a yarn lock's root. `node_modules` is not read, so changes there cannot matter.
- **Extractor version: no bump.** What a scan extracts from an unchanged file is the same. The candidates are identical, and only the end-of-run pass computes attribution. An index M5-19 built has null attribution until the next scan or sync fills it, without re-parsing (test "fills the attribution of an index M5-19 built").
- **Scorer** (`scripts/eval/score-arch.ts`): a new `externals` section scores labelled external rows per ecosystem. Only ecosystems whose labels carry `origin` are scored.
  - A match needs the identity and all five attribution fields to be equal.
  - Every scanned row of the ecosystem counts as reported, so an unattributed or unlabelled row lowers precision.
  - The output gives recall, precision, misses and extras, broken down by class: `builtin`, `direct-prod`, `direct-dev`, `transitive-prod`, `transitive-dev`, and `unlisted` (in no manifest, dev unknown).
  - `--min-recall` and `--min-precision` apply to this section too. The existing finding kinds are untouched.

  - `package.json` now lists `pg`, `express`, `@acme/logging` and `sqlite` as dependencies; `react` as a peer and as a dev dependency; and `reflect-metadata`, `lodash` and `eslint` as dev dependencies.
  - A new `package-lock.json` (v3): `js-yaml` comes through `@acme/logging` and `debug` through `express` (transitive production), `semver` through `eslint` (transitive dev). A nested dev copy of `debug` checks that production wins.

## Limitations

- **Ambient globals:** not in M5-20 (assigned elsewhere: M5-24 or a new task, by the integration owner). The `origin = 'ambient'` value is reserved in the type.
- **Dev for transitive packages is name-level.** Versions are not distinguished: production wins if any copy, or any path from a production root, reaches the name. In a monorepo with a yarn or pnpm lock, dev-ness is computed for the whole lock, not per importer.
- **Not read:**
  - `@types/*`-only declarations (`import x from 'foo'` with only `@types/foo` listed gives `direct = 0`);
  - Bun's `bun.lock`;
  - `bundledDependencies`;
  - the `exports` and `imports` maps of external packages;
  - `node_modules` (by design).
- **`direct`** is any manifest from the file up to its repo's root. A root-level dependency therefore counts as direct for every package of a monorepo, as Node's resolution allows. A stricter "own manifest only" rule would be a policy option for M5-24. Separate repos never share manifests or lockfiles, even when one sits inside another's folder.
- **Multiple lockfiles:** only the nearest folder that holds one is used. If no lockfile there is readable, the attribution is the manifests' alone, without looking further up.
- **Cost:** see "Review" for no-op sync timings. A sync after a manifest or lockfile change parses each nearest lockfile once. The stale check stats the recorded inputs and hashes only those touched within 2 s of the last pass or since.
- **mtime shortcut:** a recorded input whose mtime is more than 2 s before the last pass started is taken as unchanged without hashing. A tool that rewrites a lockfile and back-dates its mtime would go unseen until the next forced scan; the indexed-file stale check makes the same assumption.
