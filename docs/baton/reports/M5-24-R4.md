# M5-24-R4 report: uncovered packages are opt-in

## Delivered

Owner decision D039 reverses M5-24's default. `mapx check` now reports a package that no layer covers as uncovered only when the configuration opts in.

- **The rule** (`src/arch/config.ts`, `src/arch/schema.ts`):
  - `policy.uncovered.externals` keeps its type and its place in the loaded configuration.
  - When no document of the `extends` chain sets it, the loader resolves it to whether a merged non-overlay layer covers packages: a positive `package` selector in `selectors` or `private`, directly or inside `all`/`any`, but not under `not` (D039 addendum; changed in review, see below).
  - An explicit `true` or `false` wins, so `externals: false` still turns packages off in a configuration with package selectors.
  - Allowances name layers only, so "a rule uses a package selector" means a layer the rules name. There is nothing separate to look for in `rules`.
  - The default in `DEFAULTS` is `false`, with a comment saying the loader resolves it.
- **One value for every surface.** The evaluator (`evaluate.ts`), `mapx arch allowed` and `mapx_arch_allowed` (`introspect.ts`), `mapx_arch_check`, the dashboard's counts (`/api/arch` is check's report) and `mapx arch graph` all read the resolved value, so they agree without further change. For a package, `allowed`'s `out-of-scope` reason now names the opt-in.
- **`mapx arch init`:** it keeps proposing the `Packages` layer, `{ "package": "*" }`, which every layer may use. That layer is a package selector, so the draft opts in. It covers every package, so day one passes. Without the layer, packages are out of scope, and day one passes too.
  - Why keep it: it is the starting point for vendor rules, and it shows package dependencies in the layer graph. Narrowing it later makes a left-out package uncovered, which is the point of opting in.
  - The layer's comment and the `addPackagesLayer` doc comment no longer say that check fails without it.
- **Smells:** they do not need the opt-in.
  - `vendor-leak` is any `private-layer` violation on an external, a built-in included, so it needs a matching `private` selector rather than the opt-in (corrected in review).
  - `undeclared-dependency` and `dev-dependency-in-prod` compare the code with its manifests, not with the layers, and they never change check's exit code.
  - This is documented in `docs/architecture-rules.md` under Smells.
- **Docs and schema:**
  - `docs/architecture-rules.md`: the evaluation rule with an example, the vendor example, introspection, the policy table and init note 5.
  - `docs/cli-reference.md`: the `arch init` Packages note.
  - The `policy.uncovered.externals` description in `schemas/architecture.schema.json`, including its default.
- **MapX's own `.mapx/architecture.jsonc`:** unchanged. Its `Packages` layer (`{ "package": "*", "dev": false }`) opts in, so a dev-only package imported from `src/` is still uncovered and still fails CI.

## Fixture label changes (`tests/fixtures/arch-rules/expected-findings.json`)

The configurations of the existing apps (ts, php, python, go, workspace) have no package selector and no `policy.uncovered.externals`, so they do not opt in. M5-24 labelled 52 rows for them as `uncovered` on packages, "for the default policy.uncovered.externals". That default is what D039 reverses. Each of these rows is now a `none` row: a negative, so any finding on it is a false positive. Its `rule` is dropped, its from, to and edge types are kept, and its note says why. The rows are:

- go-x01 to go-x07 (7)
- php-x01 to php-x14 (14)
- python-x01 to python-x13 (13)
- ts-x01 to ts-x16 (16)
- workspace-x01 and workspace-x02 (2)

The file's `description` is updated to say this.

The vendor apps (ts-vendor, php-vendor, python-vendor, go-vendor) use package selectors, so they opt in. Their rows are unchanged, and each still has an uncovered package row (ts-vendor-03 express …). No fixture configuration was changed.

Literally, AC2 says labels change "only where a fixture config opts in". These 52 rows changed in apps that do not opt in, because their expected kind follows from the decision. The other reading would keep the labels and add `externals: true` to five fixture configurations, which would leave the new default untested by the scorer. I chose to change the labels; the integration owner may prefer the other reading.

## Review (integration owner, of b776aef)

No P0 or P1. The P2s, each fixed in this commit (rebased onto a0a7390, the D039 addendum):

1. **Test gap: `all`/`any`.** The opt-in test now has cases for a package selector inside `all` and inside `any`. Mutants that drop either branch fail.
2. **Vendor-leak docs.** The claim that vendor-leak exists only in an opted-in config was false: a private `builtin` selector gives one on `node:fs`. `docs/architecture-rules.md` now says what triggers it: any `private-layer` violation on an external, given a matching `private` selector. The smell is unchanged.
3. **`arch allowed` observed types.** Without an opt-in, `allowed Server.ts express` listed all 8 scope types with `observed: false`. `observedExternalTypes` (`introspect.ts`) now reads the stored external references whatever the policy. The answer lists only `import` and `call`, each `observed: true`, and the verdict stays `out-of-scope`.
4. **Reason with an explicit `false`.** The reason comes from the resolution: `policy.uncovered.externals is false in .mapx/architecture.jsonc` for an explicit value, and `… is unset and no non-overlay layer has a package selector` for the default.
5. **Ruling (D039 addendum).** `coversPackages` follows only `all` and `any`, not `not`, and overlay layers are skipped. Any `dev`/`direct` filter, and `private`, opt in. Tests:
   - opting in: `{package}` alone, with `dev: false`, with `direct: true`, in `all`, in `any`, and in `private`;
   - not opting in: under `not` in `private`, `not` inside `all`, and a dev-only overlay alone.
   The docs and the schema description match.
6. **Effective value.**
   - The loader records `config.uncoveredExternals` as `{ value, source: explicit|package-selector|default, file?, layer? }`.
   - It is additive output in three places, each with a schema or a test:
     - the check JSON report (`ArchReport.policy`, `schemas/arch-report.schema.json`): `policy: { uncovered: { externals, builtins } }`;
     - `arch validate-config --format json` (`policy`, the same shape);
     - the validate-config text output: a "Packages in no layer: …" line.
   - Because the report carries it, `mapx_arch_check`, `mapx_arch_validate_config` and `/api/arch` return it too.
   - The CI goldens (SARIF, GitHub, CodeClimate, JUnit, DOT, Mermaid, DSM) do not render it and are unchanged.
   - The `arch-config` validate-config test is updated deliberately: its chain fixture has a `package` selector in Http, so it reads "uncovered (layer "Http" has a package selector, which opts in)".
   - `src/mcp.ts`'s description of `mapx_arch_validate_config` still lists `{ valid, view, files, issues }`. Lane C owns that file, so it was not touched. `docs/mcp-integration.md` names `policy`.

## Limitations

- An explicit `externals: false` beats a package selector. D039 names the two ways to opt in but no way to opt out, and M5-24 documented `false` as the off switch, so it is kept and documented.
- `builtin` and `ambient` selectors do not opt in to packages. Built-ins keep their own opt-in (`uncovered.builtins`).
- `source: package-selector` names the first non-overlay layer that opts in, not every one.
- The CHANGELOG entry is left to the integration owner.

Changelog: `mapx check` no longer reports packages that no layer covers as uncovered unless the configuration opts in (`policy.uncovered.externals: true`, or a positive `package` selector in a non-overlay layer), so `--fail-on-uncovered` ignores them by default; this reverses 0.3.9 (M5-24-R4).
