# M5-18-R1 report: MapX's dogfood config judges calls and references, not only imports

M5-18 limited `.mapx/architecture.jsonc` to `import`/`require` edges, because names from `node:path` and the DOM linked project symbols (36 false violations). M2-08-R3, M2-12 and M2-13 removed those edges. Planned in `iterations/M5-18-R1.md`, on top of M2-20 in the same lane (develop `ef6a79e` + M2-20).

## Delivered

- **`.mapx/architecture.jsonc`.** `scope.types` is gone, so the default applies: `import`, `require`, `extends`, `implements`, `call`, `instantiation`, `param_type` and `return_type`.
  - `scope.exclude: ["tests/fixtures/**"]`. Fixtures are sample projects that no production module imports. Their thousands of declarations (`Database`, `Order`, `step`) are homonyms that a by-name call can reach. Both false edges below land in them.
  - The comments say why. `tests/**` and `scripts/**` stay targets through the `Outside` overlay.
- **`.mapx/architecture.baseline.json`**, regenerated: the 8 import entries are unchanged (same fingerprints), plus 29 call entries.
- **`tests/dogfood-architecture.test.ts`:**
  - The config judges `DEFAULT_SCOPE_TYPES`, `call` included, and excludes the fixtures.
  - New e2e describe "judges calls (real scan)". A probe workspace under MapX's own config has `src/frameworks/probe.ts` importing `src/parsers/helper.ts`. That import fails the check (1), and once baselined the check passes (0). Adding `helper()` to a function then exits **1**, with the finding `src/frameworks/probe.ts#use → src/parsers/helper.ts#helper (call)`.
- **`docs/architecture-rules.md`** ("MapX's own rules"): the scope (every type, fixtures excluded, why) and the baseline (imports and the calls behind them).

**2 false edges, not baselined: resolver bugs.** Both are `verified` edges into `tests/fixtures/**`, and both are kept out by the fixture exclusion.

| Source → target | Kind | Why it is false |
| --- | --- | --- |
| `src/core/store-bun.ts:12` `BunStore` → `tests/fixtures/arch-rules/ts-vendor/src/infrastructure/Database.ts#Database` | instantiation | `const { Database } = _require('bun:sqlite'); new Database(…)`: a class destructured from a local call in the constructor, linked by name to a fixture class |
| `src/parsers/languages/vue-options.ts:198` `resolveThisMember` → `tests/fixtures/vue-sfc/vue3/src/components/QuantityInput.vue#step` | call | `for (const step of THIS_MEMBER_STEPS) step(…)`: a for-of loop variable called, linked by name to a function in a Vue SFC's `<script setup>` |

Repro (`scratchpad/M5-18-R1-repro.mjs`, a synthetic workspace scanned with this tree's CLI):

```
src/steps.ts:       const STEPS = [(n: string) => n];
                    export function run(name: string) { for (const step of STEPS) { const t = step(name); … } }
other/Widget.vue:   <script setup lang="ts"> function step(d: number) { return d; } </script>
src/store.ts:       const load = createRequire(import.meta.url);
                    export class Store { constructor(p: string) { const { Database } = load('bun:sqlite'); this.db = new Database(p); } }
other/Database.ts:  export class Database {}

src/steps.ts run call -> other/Widget.vue#step verified                               (false)
src/store.ts Store::constructor instantiation -> other/Database.ts#Database verified  (false)
```

Causes (`src/parsers/generic-wasm-parser.ts` `boundLocally`):
- It knows parameters and plain `const x = …` declarators. It does not know a for-of/for-in loop binding, or a destructured local. Destructured locals are left out on purpose, for the Vue store and composable passes.
- In the scanner, M2-08-R3's global-scope rule then lets an ES module's bare name reach a "script". A `.vue` SFC whose `<script setup>` has no `import` counts as one, and so does a fixture file.

Suggested remediation (owner's call): treat a for-of/for-in binding and a destructured local of a function body as local for calls and instantiations, outside Vue files. Do not count an SFC as a global script.

## Limitations

- **Fixtures out of scope.** An import of a fixture from production code is no longer judged. M5-18 had it judged through `Outside`. Such an import is unlikely, but the owner may prefer fixtures in scope. In that case the two false edges above fail the check until the resolver bugs are fixed: they must not be baselined.
- **The 29 call entries make the baseline 37 entries.** A helper move removes an import entry and its calls together, and leaves stale entries for `--generate-baseline` to drop.
- **Inferred edges** stay ignored (`policy.inferred: "ignore"`, unchanged).

Changelog: MapX's own architecture check now judges calls, instantiations, inheritance and type references as well as imports (M5-18-R1).
