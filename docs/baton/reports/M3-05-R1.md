# M3-05-R1 — Vuex map-helper path forms and Pinia outside SFCs

Date: 2026-10-31. Base: `develop@00407d6` plus the integrator's P1 remediation patch (`review2.patch`). Iteration: `docs/baton/iterations/M3-05-R1.md`.

## Delivered

- **Map-helper path forms** (`mapHelperEntries`, `src/parsers/languages/vue-stores.ts`):
  - A Vuex name with a path, in an array (`mapGetters(['users/activeCount'])`) or as an object value (`{ load: 'users/FETCH' }`), names `activeCount` / `FETCH` in namespace `users`. A helper namespace and a path are joined (`mapActions('a', ['b/X'])` → `a/b`).
  - Before, the name kept its path and was looked up in the root namespace, so it gave no edge.
- **`createNamespacedHelpers`**, when imported from `vuex`. Helpers bound at the top level are recognised in three forms:
  - destructured: `const { mapActions } = createNamespacedHelpers('users')`;
  - renamed: `{ mapActions: mapUserActions }`;
  - as members: `const catalog = createNamespacedHelpers('catalog'); catalog.mapActions(…)`.

  The Options API pass reads the helpers through `mapHelperEntries`, so `this.NAME()` follows (rule 6, step 3). `vue-options.ts` is unchanged.
- **Members in imported objects.**
  - A store root or module records imported member objects in `VuexModuleInfo.parts`. This covers an imported binding as a kind's value (`actions,`, `import * as mutations`) and one spread into it (`actions: { ...auditActions, FETCH() {} }`).
  - Resolution looks at the module's own members first, then each part's file, by exact name (`ctx.defines`).
  - `state` is not looked up in parts, because state properties are not symbols.
  - A member file is `getters.js` / `actions.js` / `mutations.js`, or any file with `export const getters = { … }`. Such files give their arrow-function members a `method` symbol scoped to the kind (`visible`, scope `getters`), as M3-05 does in module files. These files pass the store pass's gate by their name.
- **Pinia outside SFCs:**
  - In a JS/TS module, `const { checkout, add: addItem } = useCartStore(); addItem()` gives a store reference to `add`. The existing reference is retargeted, from `addItem` to `add`.
  - A binding is shadowed by a function declaration or a parameter of the same name in between.
  - In SFCs, the M3-04 composable pass already resolves destructured calls through the import, with re-exports. They are left to that pass.
  - `x.dispatch('…')` / `x.commit('…')` with a string argument is Vuex, whatever `x` is bound to.
- **Hooks of any name:**
  - A hook defined in the file with `defineStore` is a store, whatever its name (`usePrefs().reset()`).
  - Each store file records its hooks in `files.metadata.vuex.piniaHooks`.
  - Pinia's own map helpers (`mapActions(useWish, …)`, with the helper imported from `pinia`) accept an imported hook of any name. Resolution confirms the hook from the module's `piniaHooks`. A composable passed there (`mapActions(useLegacy, …)`) gives no edge, as before.
- **Not delivered here: member calls on an imported any-name hook** (`const wish = useWish(); wish.checkout()`). This part needs `src/core/scanner.ts`; see "Scanner change needed".
- **Tests** (`tests/vue-stores.test.ts`): a new e2e suite, "Vuex map-helper forms, imported members and Pinia outside SFCs", with 6 tests. Each runs a real `init` + `scan` and asserts by identity, against same-named traps:
  - another namespace with the same getter and action;
  - `src/api/catalog.js` and `src/api/orders.ts` with the same function names;
  - a composable with an inner `checkout`.

  `tests/vue-script-setup.test.ts` needed no change.
- `typescript.ts`, `javascript.ts` and `vue-script-setup.ts` (listed in `affectedFiles`) needed no change: the store pass already runs from both parsers.

## Scanner change needed (companion patch, not applied)

**Why the scanner is needed.** Take `const wish = useWish(); wish.checkout()`, where the imported `useWish` might be a store or a plain composable.

- Only resolution can tell which, from the store file's `piniaHooks`. When it is not a store, the reference must resolve as it did before, by the default resolution.
- `resolveStoreTarget` can return only a target or "no edge". With the parse side alone, every member call on a plain composable would lose its default edge.
- I measured this with a probe that used no fallback: 3 correct edges were lost:
  - `useBoth.ts#go → api/http.ts#fetchAll`;
  - `useBoth.ts#go → useLocal.ts#refresh`;
  - `Page.vue#go → api/http.ts#fetchAll`.

  So this part is held back.

**The patch.** Path: `/tmp/claude-1001/-home-mgamil-mapx/41a6413c-dab3-4adb-a8ee-58b4c522412c/scratchpad/M3-05-R1-companion.patch`. It applies on top of this task's changes (`git apply --check` passes). It contains:

- **`src/core/scanner.ts`** (3 lines): the Vue branch is taken only when the resolver's result is not `undefined`; otherwise the reference falls through to the default resolution.

  `vueHit` is declared next to `targets`.
- **`src/types.ts`:** `fallback?: boolean` on the Pinia `VueStoreTarget`.
- **`vue-stores.ts`:**
  - `storeOf` accepts an imported project hook of any name (`use[A-Z]…`, not `useStore`, not a package import) with `fallback: true`;
  - the gate also admits hook calls in SFCs and in modules importing `vue` / `pinia`;

## Limitations

- **Imported any-name hooks** in member calls or destructuring: as above, they wait for the companion patch. Until then, `wish.checkout()` keeps its name-lookup edge.
- **Barrels.** A Pinia hook imported through a barrel (`@/stores` re-exporting `useCartStore`) resolves only in the import's own file. A destructured action in a `.ts` file then gives no edge (before: name lookup). In SFCs the M3-04 pass follows re-exports.
- **Member files** are recognised by name (`getters` / `actions` / `mutations` files, or an exported `getters` / `actions` / `mutations` object). An imported object under another name with arrow-function members (`userGetters.js`) has no symbols, so it gives no edge (method members still do).
  - Any JS/TS file named `actions.ts` etc. now gets `method` symbols, scoped to that kind, for the arrow-function members of its exported objects, even outside Vuex.
- **Not handled** (unchanged from M3-05):
  - `mapStores` (`this.cartStore.x()`);
  - `$store.getters['ns/x']`;
  - `registerModule`;
  - `state` held in imported objects;
  - `createNamespacedHelpers` bound inside a function.
- **Stale metadata.** `piniaHooks` lives in `files.metadata.vuex`. A store file indexed before this change gets it on its next parse. Until then, Pinia map helpers that use an imported any-name hook give no edge, as before.

## Findings outside this task

- `BUILTIN_GLOBALS` is checked in the scanner before the `vueStore` branch. A store action named like a global (`fetch`) is therefore dropped. This is pre-existing and not changed here.
