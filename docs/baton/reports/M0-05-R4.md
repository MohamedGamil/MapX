# M0-05-R4 — MCP parity for Laravel relationships and bindings

Date: 2026-10-31. Remediation of the review 2026-10-31 P2 finding: `mapx query` and `mapx deps` showed relationships and bindings, `mapx_query` and `mapx_dependencies` did not.

## Before (reproduced through a real MCP client)

On the 11-file Laravel fixture of `tests/legacy-laravel-surface.test.ts`, before the fix:

- `mapx_query {term: "User"}` returned `class User`, `@ app/Models/User.php:4` and `signature: class User extends Model`, with no `relationships:`.
- `mapx_dependencies {file: "app/Providers/AppServiceProvider.php"}` returned only `→ app/Contracts/PaymentGateway.php (binding)` and two import lines, with no concrete class.

Both new tests failed (2 failed, 4 passed).

## Delivered

- **`src/core/relations.ts`:** new `fileBindings(store, file)` and `describeBinding(b)`. This is the CLI's former inline binding renderer, moved so that the CLI and MCP share one function: `$listen` reads `Event → Listener (listen)`, and closures show as `(closure)`.
- **`src/cli.ts`:** `deps` uses the helper. Output is unchanged, and the existing CLI test still passes.
- **`src/mcp.ts`:**
  - `mapx_query`: class results append `relationships:` with one `describeRelation` line per relation, the same text as `mapx query`.
  - `mapx_dependencies`: appends a `Bindings (abstract → concrete):` block.
  - Both tool descriptions now mention the new blocks.
- **`docs/mcp-integration.md`:** both tools document their new blocks.

| Acceptance criterion | Status | Test |
| --- | --- | --- |
| `mapx_query` on a model lists its relationships, through an MCP client | met | `mapx_query on a model lists its relationships (MCP client)`. It asserts that the `class User` entry is followed by `relationships:`, `team → belongsTo App\Models\Team (many-to-one)` and `orders → hasMany App\Models\Order (one-to-many)`, in order. |
| `mapx_dependencies` on a provider lists its bindings, through an MCP client | met | `mapx_dependencies on a provider lists its bindings (MCP client)`. It asserts `Bindings (abstract → concrete):\n  App\Contracts\PaymentGateway → App\Services\StripeGateway (bind)`. |

Both tests use `Client`, `InMemoryTransport.createLinkedPair()` and `buildServer()` on a workspace scanned with the real CLI. This is the same harness as `tests/legacy-metrics-edges.test.ts`.

## Limitations

- `mapx_dependencies` still takes an indexed file path. The CLI's `deps` also resolves partial names and globs (`deps AppServiceProvider`). That is a separate parity gap, not part of this criterion, and was left alone.
- When a file has bindings but no dependency edges, `mapx_dependencies` prints `No dependencies found` before the bindings block. The CLI behaves the same way.
