# M0-02-R12 report: a full scan killed after its index transaction keeps referrers and changed files

Found by the independent review of M0-02-R11 (2026-11-02), reproduced for git and hash. The full scan's index transaction wrote real content and blob hashes before parsing, so a scan killed after that transaction committed:
- lost the referrers whose `removed_files:` records the transaction consumed (no `a → b` edge through later scans and syncs);
- left a changed file with stale symbols under a fresh hash.

## Delivered

`Scanner._scanFullForRepo`:
- **Index transaction:** it upserts each file with null hashes and `last_scanned` unset, as both syncs have done since M0-02-R10.
- **Parse batches:** each batch's transaction writes a file's content and blob hashes (`setFileHashes`) together with its parse result.
- **Read time (review fix):** `Store.setFileHashes` stamps `last_scanned` with the time the content was read (the path's start), in the full scan and both syncs. Before, it used the time the result was written, so an edit made while the scan parsed was hidden.
- **After a kill in between:** every file the scan was re-indexing is still "changed" for the next scan or sync. That includes the referrers of the consumed records, since they were in the same parse list.

New tests in `tests/sync-interrupt.test.ts`, for git and hash. The kill is simulated by `writeParseResultWithMap` throwing on its first call, after the index transaction has committed:
- **Restored file:** `b.ts` is deleted, scanned and restored; the full scan is killed; then a full scan and a sync run. Symbols and edges equal `scan --force`, including `src/a.ts a → src/b.ts b`.
- **Changed file:** `b.ts` gains `b2`; the full scan is killed; the next full scan indexes `b2`, and the symbols equal `scan --force`. The git case fails before the fix too: the commit makes HEAD's blob the indexed one.
- **Unchanged files:** an uninterrupted second full scan writes no parse result.
- **Edits during parsing:** `b.ts` is edited at the first parse event of a full scan, and of a sync that re-indexes it; it is stale afterwards.

## Independent review

A fresh agent got both diffs, without these conclusions. It confirmed the claim: 4 of the 6 new tests fail without the change. It found clean results for three other interruptions, each ending equal to `scan --force` in git and hash: a sync after the killed scan, `abort()` during parsing, and the git sync's null-hash re-read. It found one defect:

| Rank | Finding | Fix |
| --- | --- | --- |
| P1 | `setFileHashes` stamped `last_scanned` when the batch was written, so an edit made during the parse phase was hidden from `mapx status`, `mapx check` and the git sync of gitignored files. Since M0-02-R10 the syncs had the same cause. | The read time is passed in all three paths (test above) |

It also noted, as consistent with M0-02-R10 and not a defect: while a scan runs, the files being re-indexed read as changed.
