# M5-26 report: the index records the extractor version that built it

Found by the review of M5-05 (2026-11-02, P2). Store migrations add columns but keep the extracted data, and nothing recorded which extractor built an index. An index scanned before M5-25, which added the Go cross-package instantiation edges, or before M2-08-R1 made `mapx check` under-report with no staleness signal.

## Delivered

- **`src/core/extractor-version.ts` (new):**
  - `EXTRACTOR_VERSION = 1`, with a rule for when to bump it: a change that makes an unchanged file index differently;
  - `extractorVersionKey`;
  - `outdatedRepos(store, repos)`: scanned repos whose `meta extractor_version:<repo>` is missing or lower;
  - `outdatedIndexWarning`.
- **`Scanner`:**
  - for an outdated repo, the full path sets `reparseAll`, as it does for changed filters, and both syncs take the full path;
  - only a completed, uninterrupted full-path scan records the version;
  - for an outdated repo, the full path ignores the resume state an older interrupted scan left, as `--force` does (review fix).
- **`mapx check`:** an outdated repo exits 4 with "The index of <repo> was built by an older MapX: run `mapx scan`, or `mapx check --sync`, to rebuild it". `--sync` runs the sync, which re-parses every file of that repo. A repo still outdated afterwards (a missing folder, an interrupted sync) keeps exit 4 (review fix).
- **Warnings:** the CLI staleness warning (`query`, `deps` and the other index readers) and the MCP warning (`run mapx_sync`) name the outdated repos.
- **`docs/cli-reference.md`:** the staleness section and `mapx check`'s exit-4 row.

## Independent review

A fresh agent got the diff, without these conclusions. It confirmed the upgrade path:
- on a single repo and a 3-repo workspace, the first sync re-parsed every file once and the next two parsed none;
- each warning is printed once, and not at all for a fresh index;
- `check --sync --format json` prints valid JSON;
- `resetRepoForScan` clears the version.

Findings, all fixed:

| Rank | Finding | Fix |
| --- | --- | --- |
| P1 | A resume state left by an older MapX's interrupted scan made the upgrading scan skip the files it listed as completed, yet record the new version ("Scanned 1 files"; 5 files never re-parsed) | The resume state of an outdated repo is cleared (test) |
| P2 | "re-parses the older index once" compared counts, which also match unchanged files; it passed with the re-parse removed | It compares each file's `last_scanned` |
| P2 | `mapx check --sync` did not re-check, so a repo it could not rebuild (a moved folder) passed the gate | It re-checks and keeps exit 4 (test) |

Not changed:
- `outdatedIndexWarning` takes its repos from the files table, so a scanned repo with no files warns only in `mapx check`. One sync clears it.
- The rescan advice cannot clear a repo whose folder is missing; the stale-file gate already behaves this way.

## Limitations

- **One version for the whole index:** after a bump, every file of every repo re-parses once, even when the change touched one language.
- **A bump is a manual step:** nothing enforces it when a change alters extraction. The constant's comment states the rule.
- **Partial stores:** a test double without `getRepoNames` or `getMeta` gets no warning (`outdatedIndexWarning` guards it); the real `Store` always has both.

Changelog: An index built by an older MapX is stale: `mapx check` exits 4, the commands warn, and the next `mapx scan` or `mapx update` re-parses every file once (M5-26).
