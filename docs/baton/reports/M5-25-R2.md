# M5-25-R2 — Go methods with a generic receiver are indexed

Planned in `iterations/M5-25-R2.md`. Source: `reports/M5-25-R1.md` (Limitations). Rebased on develop `f0fc004` (after M5-09 and M5-21), on top of M5-07-R1, and revised after the coordinator's review (see Review 1).

## Delivered

- **`queries/go/symbols.scm`:** the method pattern takes two more receiver types:
  - `(generic_type type: (type_identifier) @symbol.scope)`, for `func (p Pair[K, V]) Swap()` and the unnamed `func (Pair[K, V]) Len()`;
  - the same under `pointer_type`, for `func (p *Pair[K, V]) Set()`.

  The scope is the bare type name, as for a non-generic receiver.
- **`src/parsers/generic-wasm-parser.ts` (review 1):** `goSelectorCall` records `goReceiver` for every selector call that is not on a package.
  - When the code writes the value's type, the call carries that type (`goType`), plus its import (`goPackage`) when qualified.
  - `goVariableType` finds the nearest declaration, by the same scope walk as `goBoundLocally`:
    - a receiver, parameter or named result;
    - `var x T` or `var x = T{}`;
    - `x := T{}` or `x := &pkg.T{}`;
    - else a package-level `var` of the file.
  - `goNamedType` unwraps pointers, parentheses and generic arguments. Predeclared types and type parameters give no type.
  - A literal of the calling package's own type (`Box[int]{}.Get()`) carries its type too.
  - `goMaybePackage` marks a bare identifier that is no local and has no written type. It may still name a package whose name is not its import path's last element (`database.Connect()` for `internal/db`).
- **`src/core/scanner.ts` (review 1):**
  - A typed call resolves through `resolveGoQualifiedType` to the method of that type (or of a type it embeds), in the imported package or in the caller's own package, `verified`.
  - It falls back to `resolveGoMethodByName` when the value has no written type (a call's result, a range variable, a chained call) or when its type is an interface or an alias the package declares as no struct.
  - That fallback links only a method declared in the caller's package or in a package the file imports (`goReach`). Unresolvable imports that may be the project's own count too, matched by path suffix as in M5-25-R1.
  - With `goMaybePackage`, the fallback also accepts package-level functions of the imported packages.
  - The result is `inferred`, and the file nearest the caller wins, as in by-name resolution.
  - `goReceiver` and `goMaybePackage` are stripped from stored edge metadata.
- **`src/core/extractor-version.ts`:** `EXTRACTOR_VERSION` 13 with its comment line. 11 is M5-09 and 12 is M5-21.
- **`tests/go-qualified-instantiation.test.ts`:** 3 new tests over two synthetic workspaces, scanned with the real CLI.

## Limitations

- **Types that are not written stay by name, within reach:** a call's result (`svc := build(); svc.Run()`), a range variable, a chained call (`domain.NewOrder().Run()`), a struct field (`s.repo.Save()`). These need type inference, and their edges are now `inferred`.
- **Package-level variables** are found only in the calling file, not in the package's other files.
- **An interface-typed value** links an implementation in reach, by name, `inferred`. Interface methods are not symbols in the Go query.
- **A dot import** (`import . "pkg"`) or a package-level `var` in another file that is named like a package is not told apart from a package. Such an identifier gets `goMaybePackage`, so the fallback still stays within the file's reach.
- **A parenthesised receiver type** (`func (p (Pair[K, V])) M()`) is not matched by the query, as before.
- **Behaviour change:** Go method calls on values whose type is not written used to link the nearest homonym anywhere, `verified`. They now link only within reach, `inferred`, and an out-of-reach homonym gives no edge.
