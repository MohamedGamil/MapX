# M7-07 report: landing media: dashboard screenshots generated from a fixture

Delivered 2026-11-07. Spec: `docs/baton/iterations/M7-07.md`.

## Delivered

- **Three screenshots on the landing page,** in a "See it" section below the hero: the Graph Explorer (a clustered code map of the M5-01 TypeScript fixture, in the layered ELK layout), the Architecture "Layer rules" view of the same fixture (health tiles with violations, baseline debt and uncovered code, and the top of the layer diagram with its legend) and the HTTP Calls view of the multi-repo workspace (a Vue frontend paired with a Laravel backend, three matched calls and one with no route). Each is a 1280 x 800 WebP of 27 to 42 KiB (104,136 bytes in all), with alt text that says what it shows, its real width and height, and `loading="lazy"`.
- **The generator:** `npm run site:shots` (`scripts/site/gen-screenshots.ts`, about 17 seconds). It builds two synthetic workspaces under fixed project names (the dashboard shows the folder name), scans them with the source CLI, serves them with `mapx ui` and drives headless Chromium in the dark theme with reduced motion. Chromium takes the PNG and its canvas encodes the WebP, so no image library is added. It reuses `scripts/ui/workspace.ts` and the dashboard's own readiness signal. The output is committed, so a site build never needs it.
- **One list for everything:** `scripts/site/screenshot-list.ts` (file, size, alt text, caption) is read by the generator, by `site-facts.ts` (and so the landing page and `facts.json`) and by the tests.
- **Budget:** the lazy images are not part of the home page's first load, so `homeGzipBytes` stays at 163,000 (measured 149,708, up 1,240 bytes for the new markup). `totalBytes` rises from 4,430,000 to 4,540,000: measured 4,132,661, which is the 4,023,819 of M7-06 plus the 104,136 bytes of images plus 4,706 bytes of markup and script (an earlier figure of 108,426 for the images was taken before the graph picture was regenerated with the ELK layout, and the independent review caught it). The home page's first load measures 149,651 bytes (was 148,468).

## Found on the way

- **The default graph layout is not reproducible.** The first generator run passed everything except the determinism check: two runs of the Graph Explorer differed in 8.87 percent of their pixels, because the dashboard's default layout (Organic, fCoSE) is a force simulation with random starting positions. The 1 percent bound was kept; the generator now selects the layered ELK layout, which is deterministic (the picture also reads more tidily). Mesh (Dagre) is deterministic as well and was tried, but is more cramped.
- **Alt text was wrong for two pictures** until the pictures were looked at: the graph has no side panel (it shows cluster hexagons) and the architecture picture shows only the top of the layer diagram.
- **The dashboard header says "MapXGraph"**, the project's former name, in all three pictures. That is the product's own UI text, outside this task; the pictures show it as it is.

## Independent review

A fresh reviewer, given the criteria and the diff, found no P0 and no P1. It confirmed that the three pictures show only synthetic data (the fixture names `acme-shop` and `orders-platform`, fixture paths and counts; no home path, user name, machine name, email or token; the WebP files carry no EXIF or XMP, only an sRGB profile), that the image tests cannot pass vacuously, and that the WebP header parsing is right.

- **P2, fixed:** the generator could leave a dashboard server running (the first `mapx ui` was registered only after the second started, and `serve` did not kill a child that missed its 60 s start); each server is now registered as soon as it runs, `serve` kills a child that fails to start, the browser is launched inside the `try`, and the cleanup steps no longer depend on each other. No dashboard process or temp folder was left after the runs (checked).
- **P2, fixed:** the graph picture waited a fixed 1.5 s after changing the layout; it now waits on the dashboard's own `body[data-graph]` signal (`layout`, then `ready`).
- **P2, fixed:** the two dense dashboards render at about 42 percent on a wide screen, too small to read. Each picture is now a link that opens the full-size file (tested: `href`, `rel="noopener"`, `target="_blank"`, a label).
- **P2, fixed:** a focus ring was left on the layout selector in the graph picture; the active element is blurred before the shot.
- **P2, fixed:** the graph and architecture alt texts were 230 and 240 characters and said "hexagons" for a map that also holds dotted circles; all three are about 150 characters and exact.
- **P2, fixed:** the budget figures were stale (see above): the images total 104,136 bytes, not 108,426, which was measured before the graph picture was regenerated. The report and `budgets.json` now carry the exact figures.
- **P2, tightened:** the pixel comparison is coarse (a changed number is about 100 pixels). Two runs differ by 0.036, 0.000 and 0.000 percent, so the criterion stays 1 percent but the test enforces 0.25 percent.
- **Not changed:** the committed images are not compared with a fresh run (they depend on the machine's system fonts), and the pictures are of the dark theme at one size, so a dashboard change leaves them stale until `npm run site:shots` is run.

## Limitations

- The determinism test compares two fresh runs, not the committed images with a fresh run: the pictures use the machine's system fonts, so a regeneration elsewhere differs in anti-aliasing and glyph shapes. Regenerate after a dashboard change and commit the output.
- Dark theme at one size only; no light-theme or phone screenshots.
- The test that generates the pictures twice adds about 25 seconds to the site browser tests in CI.
