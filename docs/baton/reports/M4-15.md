# M4-15 — Sharing compiled grammar code across workers: risk evaluation

Decision D025 required evaluating the risk of patching tree-sitter before changing anything. The result: no route works without patching `web-tree-sitter`, and sharing would save under 1% of a worker's startup. **Nothing was changed or patched.** The owner decided not to patch (D026, 2026-11-01).

## Measurements (16 cores; probes in the session scratchpad)

**Grammar loading in a fresh worker, per grammar.** The first figure is `WebAssembly.compile` alone; the second is the whole `Language.load`. Times in ms.

| Runtime | typescript | php | python | go | c_sharp |
| --- | --- | --- | --- | --- | --- |
| Node 26.13.0, 1st worker | 0.8 / 3.5 | 0.7 / 1.8 | 0.2 / 1.2 | 0.1 / 0.5 | 2.6 / 7.0 |
| Node, 2nd and 3rd worker (sequential) | 0.5–0.8 / 3.5–4.6 | 0.5–0.7 / 1.8–2.1 | 0.2 / 1.2–1.3 | 0.1 / 0.5–0.7 | 2.7–2.9 / 6.0–6.6 |
| Bun 1.4.4, 1st worker | 3.0 / 4.3 | 2.3 / 3.2 | 1.1 / 1.2 | 0.4 / 1.0 | 8.2 / 8.5 |
| Bun, 2nd and 3rd worker | 1.4–1.8 / 2.8–3.7 | 0.8–1.8 / 1.8–2.1 | 0.5–0.8 / 0.9 | 0.2–0.3 / 0.7–0.9 | 8.3–8.4 / 8.8–8.9 |

- **8 concurrent workers** loading 5 grammars took 103 ms wall on Node (TypeScript 4–9 ms per worker) and 126 ms on Bun.
- **Cross-worker reuse:** on Node, later workers are no faster, so V8 shows no reuse of compiled code across worker isolates. On Bun, compiling gets somewhat faster for later workers (TypeScript 3.0 → 1.4 ms), which suggests partial reuse. Either way, compiling is cheap: V8 compiles WebAssembly lazily, and both runtimes return quickly.

**Where a worker's startup goes** (source mode, one TypeScript file):

| Step | Time |
| --- | --- |
| Start a worker and parse its first file | 377 ms |
| TypeScript grammar: `Language.load` | 6.8 ms, of which compile is about 1 ms |
| TypeScript queries: compile | symbols 22 ms + references 26 ms |
| Other query compiles | PHP 4 + 45 ms; Python 4 + 8 ms; Go 1 + 2 ms |
| Parse the same file again on the warm worker | 1.1 ms |

**Conclusion.** Most of a worker's startup is booting the worker itself: the V8 isolate, the module graph, and tsx from source. Compiling the queries is second, and they cannot be shared: they live in each worker's WebAssembly memory. Compiling the grammars costs about 1–3 ms each, so sharing it would save at most about 2% of a cold worker's grammar and query setup, and well under 1% of its startup. That is far below the 30% the criterion asks for.

M4-10 to M4-14 already remove the costs that mattered:
- grammars loaded only when needed, once per thread (M4-10);
- workers reused across batches and MCP calls (M4-11);
- no workers for small batches (M4-13);
- fewer grammars per worker (M4-12).

## Routes to share compiled grammar code, with their failure modes

1. **Pass a precompiled `WebAssembly.Module` to `Language.load`.** Not possible on Node without a patch: `Language.load` reads any input other than a `Uint8Array` as a file path (`web-tree-sitter.js` line 1484). Only the browser branch, through `compileStreaming`, passes a compiled module on.
2. **Call the internal loader through the Emscripten module object.** `Parser.init(options)` makes the options object the Emscripten `Module` (`var Module = moduleArg`). So after init, `options.loadWebAssemblyModule(compiledModule, { loadAsync: true })` is reachable and accepts a `WebAssembly.Module` (line 2400). But a `Language` can only be built through `new Language(INTERNAL, address)`, and `INTERNAL` is module-private (line 1310).

   Using this route means re-implementing the private constructor, which reads `C._ts_language_symbol_count` and other internals, on an object from `Object.create(Language.prototype)`. Failure modes on an upgrade:
   - a changed constructor (new fields, other internals) breaks silently, as wrong or missing node types and wrong query captures, not as a load error;
   - the loader's name and signature, and the `moduleArg` identity, are undocumented Emscripten details.

   In effect it is a patch without the visibility of one.
3. **Patch `web-tree-sitter`**, with patch-package or a vendored copy: accept `input instanceof WebAssembly.Module` in the Node branch of `Language.load`, and have each worker receive a compiled module from the main thread through `postMessage`. Node and Bun can both clone a `WebAssembly.Module`. Failure modes:
   - the patch stops applying, or applies wrongly, on an upgrade (the file is a bundled build, about 4,000 lines);
   - `npm ci --ignore-scripts` installs skip patch-package;
   - the compiled binary bundles whichever copy is installed;
   - the main thread must compile every grammar the workers need, even ones it never uses itself.

   The gain is at most about 1–3 ms per grammar per worker.
4. **Shared memory:** rebuild tree-sitter with threads, and share one `WebAssembly.Memory` holding grammars and queries. Not supported upstream; it would mean a custom Emscripten build of the runtime. High risk, and large work.
5. **Share compiled queries:** impossible, because queries live in each instance's linear memory. The real lever on query cost is fewer cold workers, which M4-11 and M4-13 already deliver.

## Recommendation

Do not patch. Only routes 2–4 can work, and each depends on library internals or rebuilds, for a measured gain under 1% of worker startup. Close M4-15 on this evaluation. The owner chose this (D026).
