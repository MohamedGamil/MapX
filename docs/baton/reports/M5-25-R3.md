# M5-25-R3 — Go: an unversioned local replace outside the workspace is external

Planned in `iterations/M5-25-R3.md`. Sources: `reports/M5-25-R1.md`, `reports/M5-23.md` (limitation "An unversioned local replace to a directory outside the workspace"), and `reports/M5-23-R1.md`. Based on develop `03ca6f6`, after M5-25-R4 on this branch.

## Delivered

- **`src/core/import-resolvers.ts`:** `goLocalReplaces` keeps a `replace M [v] => ./dir` directive only when its target folder lies inside the workspace or a registered repo. The decision is `ImportContext.localDir`, which the scanner supplies (`goLocalDir`, see Review); without it a folder is judged by its path alone (`..` or `../x` is outside).
  - This applies to every user of the function: the externality decision (`goImportInWorkspaceModule`), import resolution (`resolveGoImport`), and go.work's replaces and `use` folders (`goWorkModules`). Versioned and unversioned directives are treated alike, and a versioned one still applies only to the required version (M5-23).
  - A replace whose target leaves the module but stays in the workspace (`=> ../lib` from `svc/`) stays internal, as before.
- **`src/core/manifests/go.ts`:** a module replaced by a local directory is attributed `manifest`, always: go.sum never holds a directory's hash, so no lock vouches for it (review P2; the first delivery gave `lock` when an unrelated go.sum was complete).
- **`tests/external-refs.test.ts`:** one e2e test with the real `Scanner` over a temp workspace.

No CLI, MCP or schema change. No new dependency.

## Extractor version: no bump

What a scan extracts from an unchanged file is the same:
- Before the fix, `resolveGoImport` stopped at an outside replace with no hit (`null`). After it, the import resolves to nothing either way, so there is no import or call edge.
- `goImportOutsideProject` and `goReach` (call resolution) do not read replaces.

Externality is decided at the end of every scan and sync from the stored candidates (M5-19), and a new external row has no attribution, so it is attributed. An index built before therefore gets the new rows on its next sync, with no re-parse.

The one exception is a module replaced by an **absolute** path (`=> /abs/y`). It already had a row, `manifest` both before and after the review's fix, so no stored row changes. M5-19-R1 adds an attribution-rules version for changes of this kind, and its first bump lists this task.

## Limitations

- An absolute replace target is never checked against the workspace root. It counts as outside, as before, even when it points into the workspace.
- MapX reads nothing in the replacement folder, so the module's own requirements do not join the build list (as for any third-party module).
- An in-workspace symlink to a folder outside every repo is external (see Review, P2-1). It was internal before this task, with no edge and no row.
