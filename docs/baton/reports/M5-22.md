## Delivered

- **Attribution columns filled** for every pypi candidate decided external: `package`, `origin`, `direct`, `dev` and `attribution`. This happens in the same end-of-run pass (`decideExternalRefs`) as npm and Composer, once per folder, module and imported name.
  - `origin` is `builtin` for a standard-library module, else `package`.
  - `package` is `python:<top-level module>` for a built-in (`os.path` → `python:os`). A colon never appears in a PyPI name, so it cannot collide with one. For a distribution, it is the name normalised per PEP 503 (`PyYAML` → `pyyaml`). It is null when unknown.
  - `direct` is 1 when a manifest from the file's folder up to its repo's root lists the distribution, and 0 when none does. It is null for a built-in and when the package is unknown.
  - `dev` comes from the nearest manifest that lists the distribution, where production wins. For a transitive distribution it comes from the lockfile. It is null when unknown and for a built-in.
  - `attribution` is `lock` when a readable `uv.lock` or `poetry.lock` answered. It is `manifest` when the manifests alone did: the lock is missing or unreadable, or it is stale and lacks the required distribution (criterion 2's flag).
- **Manifests** (`src/core/manifests/pypi.ts`), merged per folder:
  - `pyproject.toml`:
    - production: PEP 621 `[project] dependencies`, every extra of `[project.optional-dependencies]` (an extra is installed for production use, like npm's `optionalDependencies`), Poetry's `[tool.poetry.dependencies]` (without `python`) and its group `main`;
    - dev: PEP 735 `[dependency-groups]`, Poetry's `[tool.poetry.dev-dependencies]` and its other groups, and uv's legacy `[tool.uv] dev-dependencies`.
  - `*requirements*.txt` files in the folder:
    - `requirements.txt` is production. A file is dev-only when a qualifier around `requirements` names development: `dev`, `test(s)`, `lint`, `docs`, `typing`, `ci`, `qa` and the like (`requirements-dev.txt`, `test-requirements.txt`). Any other is production (`requirements-prod.txt`, `requirements-py311.txt`).
    - `-r`/`--requirement` includes are followed inside the repo.
    - `-e …#egg=name` and `name @ url` name a distribution. Options, `-c` constraints, paths, URLs and wheels do not.
- **Lockfiles:** the nearest folder, from the file up to its repo's root, that holds `uv.lock` or `poetry.lock`.
  - A lockfile that is there but cannot be read (a folder, no permission) ends the walk, as a corrupt one does. The manifests answer, flagged `manifest`, and a parent folder's lock is never used. This is the M5-21 review P2 and M5-20-R1 defect, avoided from the start.
  - `uv.lock`: the workspace members (`source` `editable` or `virtual`) are the roots. Their dependencies and extras are production, and their dependency groups (`[package.dev-dependencies]`) dev. Dev-ness is reachability, where production wins, following only the extras an edge asks for (`requests[socks]` reaches `pysocks`).
  - `poetry.lock`: dev-only is read from the package's `groups` (lock 2.1: not in `main`), else from its `category` (lock 1.x), else by reachability from the lock folder's pyproject. Optional dependencies count only through an extra that is asked for.
- **TOML** (`src/core/manifests/toml.ts`, new): no TOML parser is in the dependency tree, and the lane may not install one. So a small reader parses TOML 1.0 into plain objects: tables, arrays of tables, dotted and quoted keys, basic and literal strings (multi-line too), arrays and inline tables. Text it cannot read throws, which the attributor treats as unreadable. No new runtime dependency.
- **Import name → distribution.** No site-packages or venv is read, as M5-20 reads no `node_modules`. So the attributor tries each prefix of the module, longest first, and then the imported name as a possible submodule: `from google.cloud import storage` tries `google.cloud.storage`, then `google.cloud`, then `google`.
  - The candidates for a prefix are its PEP 503 form (`google.cloud.storage` → `google-cloud-storage`, `zope.interface` → `zope-interface`) and a documented table of well-known mismatches, `IMPORT_DISTRIBUTIONS`, with 41 entries (`yaml` → `pyyaml`, `PIL` → `pillow`, `sklearn` → `scikit-learn`, `socks` → `pysocks`, `bs4` → `beautifulsoup4`, `google.protobuf` → `protobuf`).
  - A table entry lists every well-known distribution of that import name: `cv2` has four opencv builds, `psycopg2` has `psycopg2` and `psycopg2-binary`, and `jwt` has `pyjwt` and `jwt`.
  - A candidate counts only when a manifest or the lockfile names it.
  - **Several candidates that count** (review P1-1): MapX takes the one the manifests list for production, else the one they list for dev. If several are listed at the same level, or none is, the module is **unknown**. It never picks one arbitrarily.
  - **No candidate counts:** a table entry with exactly one distribution gives that distribution, in no manifest (`direct` 0, `dev` null: the `unlisted` class, as npm's `left-pad`). Any other module is **unknown** (`package` null). An import name is not a distribution name, so it is never a guess. Python has no counterpart to Composer's "not locked" (`direct` 0 without a package), because a lockfile never lists import names.
- **Stale lock** (review P2): a distribution that a manifest requires and the lock lacks is attributed from the manifest, flagged `manifest`. With a stale lock, an unknown module is also flagged `manifest`.
- **`replace` and `provide`** (review P2): Python lockfiles have no such fields, so nothing is needed. Recorded as a decision.
- **Standard library** (`src/core/manifests/python-stdlib.ts`, generated). It is the union of `sys.stdlib_module_names` of Python 3.10.12 (this machine) and `Python/stdlib_module_names.h` of CPython tags v3.10.0, v3.11.0, v3.12.0, v3.13.0, v3.14.0 and v3.15.0: 331 top-level modules. `PYTHON_STDLIB_SOURCE` records the sources.
  - The header is the file `sys.stdlib_module_names` is built from. It is read as text and never compiled.
  - The union keeps removed modules (`distutils`, `imp`, `cgi`) and new ones (`tomllib`, `annotationlib`, `compression`).
  - The generator is `scripts/gen-python-stdlib.py`: `dump` per Python binary, `header` per CPython tag (it needs network access to GitHub), then `merge`.
  - The standard library comes before site-packages on `sys.path`, so a distribution of the same name never shadows it, and built-ins always win.
  - A test checks that the list covers the running Python's `sys.stdlib_module_names`. It is skipped when no `python3` 3.10+ is on the PATH.
- **Inputs, skip, staleness, sync.** The pypi reads join M5-20's `external_inputs` record.

## Limitations

- **No site-packages.** An import name is matched to a distribution only by its own normalised form, its dotted prefixes and the 41-entry table. Distributions whose import name differs and that are not in the table give an unknown row, even when listed (`import factory` with `factory-boy`, `import Xlib` with `python-xlib`). Reading `*.dist-info/top_level.txt` or `RECORD` would answer them, but that changes M5-20's "no installed tree" policy, so it is left to the integration owner.
- **Longest listed prefix.** If both `foo` and `foo-bar` are listed, `import foo.bar` is attributed to `foo-bar`. That is right for namespace packages (`azure.storage.blob`), and wrong if `foo` itself ships a `bar` subpackage while `foo-bar` is unrelated.
- **Requirements files:** whether a file is dev-only is read from its name. `requirements-prod.txt` and `requirements-py311.txt` are production. A pip-tools compiled `requirements.txt`, which pins transitive packages, is read as a manifest, so those packages count as direct. Only `*requirements*.txt` in the walked folders is read: `requirements/dev.txt` counts only through a `-r` include.
- **Not read:** `Pipfile`/`Pipfile.lock`, `pdm.lock`, `setup.py`, `setup.cfg` and conda `environment.yml`. A folder with only those has no manifest.
- **Markers** (`sys_platform == 'win32'`) are ignored. A dependency is counted whatever platform or Python it applies to.
- **Dev-ness is name-level**, as for npm and Composer: a distribution reachable from production anywhere in the lock is production.
- **`ambient`** (`os.environ`, `sys.argv`) is not classified. As for npm and Composer, it is left to M5-24 or a new task. `os.getenv` is the built-in `python:os`.
- **The TOML reader** does not reject every invalid document, such as a redefined table or mixed arrays. Attribution only needs keys and strings.
- **The fixture** exercises uv. Poetry and pip are exercised by e2e scans in the registered test file (see criterion 1).
