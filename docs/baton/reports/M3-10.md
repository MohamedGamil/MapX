# M3-10 report — Case-sensitive symbol name lookup in resolution

Lane: `lane-resolve`. Branch `worktree-agent-a67de7e1c45ff2cba`, rebased on `develop@9519f83` (M3-11).

## Delivered

**Where the lookup ignored case** (`src/core/scanner.ts`, `resolveSymbolToFile`):

- `buildSymbolIndex` files every declaration under its lowercased name, plus its exact name when that differs. `resolveSymbolToFile` looked up the exact name, then the lowercased one. When no language-compatible candidate had the exact name, it took the first compatible candidate, so `Cart` took `cart`.
- Without a symbol index, it used `store.searchSymbols`: a case-insensitive *substring* `LIKE`, with the same first-candidate fallback. Scans never take this path, because the index is always built during resolution. Unit tests and direct calls still reach it.

**Fix** (one helper and one filter, both inside `resolveSymbolToFile`):

- `foldsCase(language, kind)`: true for Pascal (its identifiers ignore case) and for PHP classes, interfaces, traits, enums, structs, records, functions and methods. That is PHP's own rule: its constants, variables and properties are case-sensitive. Every other language is case-sensitive.
- `named(name, candidates)` keeps a candidate when its name equals the looked-up name, or when the names are equal ignoring case and `foldsCase` holds for the candidate's language and kind.
- **Index path:** candidates come from the lowercase bucket, which holds every case variant, and are filtered by `named` before the language filter and the pick. The pick order is unchanged: same file with exact case, then exact case anywhere, then a case-folded PHP or Pascal declaration.
- **Store path:** each `searchSymbols` result is filtered by `named`, so a substring hit (`helperFn` for `helper`) or a case variant no longer resolves.
- **Unchanged:**
  - PHP namespace matching and `resolvePhpFunction`, which were already case-insensitive and correct for PHP;
  - `fileDefines`, the C# base kinds and the Vue rules, which already compared exactly;
  - user-facing `query` and `search`.

## Limitations and not done

- **Qualified names** (`Foo::bar`, dotted names) keep their old splitting. Only the case rule changed.
- **Pascal and PHP are the only case-insensitive languages** among the registered ones. A user-defined language is treated as case-sensitive.
- **PHP constants stay case-sensitive** (PHP 8 rule), and so do properties. Before, they matched in any case. No test or scorer depends on this.
- **The self-scan input is the tree at the task's start** (`e5a49ff` plus the new test). The comparison measures code only, not the sources M3-09 and M3-11 added since.

## Findings outside this task

- **Global `fetch()` resolves by name.** JS `fetch()` is not skipped as a built-in global, so a project that declares its own `fetch` (exact case) still gets edges from every global `fetch()` call. The same holds for receiver calls like `classList.remove` and `axios.create` whenever a project declares `remove` or `create`. This is the wider "member call resolved by bare name" issue; this task removes only its case-folded form.
- **Ruby `Cart()`** (method-call syntax on a constant) gives no reference at all, so the Ruby case uses `Cart.new`.

Changelog: Symbol resolution is now case-sensitive except where the language is not (PHP class, function and method names; Pascal), so `Cart` no longer links to a `cart` function or constant and global calls like `fetch()` no longer link to a Vuex `FETCH` mutation (M3-10).
