# M2-08-R7 report: Python, an unimported name (a builtin such as open) never links a function in another module

Spec: [iterations/M2-08-R7.md](../iterations/M2-08-R7.md). Started from `develop@a189eda`; the change is uncommitted at the time of writing.

## Cause (reproduced before the fix)

In MapX's own index (`scan . --force` before the change), `scripts/gen-python-stdlib.py` linked `tests/fixtures/arch-rules/python-vendor/app/infrastructure/database.py#open` twice (`header`, `merge`) for the builtin `open()`. The new e2e workspace, scanned with the real CLI before the fix, showed a module importing nothing of the project linking:
- the builtin `open(path)` to a project `open` in another module (`app/rel/sibling.py#open`, the nearest);
- the decorator `@helper` to `db/database.py#helper`;
- `Model()`, an annotation `m: Model`, `class Child(Model)` to `db/database.py#Model`;
- after `from os.path import *`, `open()` to a project `open`.

After `resolveImportedCall` finds no binding, the reference falls to `resolveSymbolToFile`, a by-name lookup over every compatible file. Nothing restricted a Python name to its module's scope.

## Delivered

- **`pythonScopeFilter` / `pythonScope`** in `src/core/scanner.ts`, the Python analogue of M2-08-R3's `globalScopeFilter`, passed as `resolveSymbolToFile`'s `allowFile`. A bare Python name resolves by name only in the caller's own file and the files its star imports reach. The rule's other leg, a module an import binds the name from, is unchanged: a name any `import` statement of the file names is not restricted.
  - **Names an import binds:** every identifier of every `import` / `from … import` statement of the comment-stripped text, over-inclusively: under `TYPE_CHECKING`, in a function, in `try`, parenthesised or backslash lines, after a `;`, relative imports.
  - **Star imports:** `from m import *` of a project module adds the module's files and, recursively, what its own star imports reach. A name it imports is added per name: the declaration `findExport` reaches from the starred module's binding, through any chain of re-exports (review P2-1). One that no file satisfies and is outside the project (top-level name is no project folder or module) adds nothing. One that is relative, or named like a project folder or module, may be the project's (generated, not indexed), so the file keeps name lookup. A scope built during another file's walk is not cached (cycles).
- **`stripPythonComments`** reads `from . x import y` as `from .x import y` (review P2-2).
- **`bareOnLine`**: the name is on the reference's line and no use of it there is an attribute. Receiver calls (`conn.open()`, `f.read()`), calls whose line does not show the name, and references with `metadata.receiver` keep name lookup.
- **`resolveClassName`** applies the filter to a bare class name, so `Model().save()` (M2-12) and bases no longer find an unimported project class.
- `sourceLine` shares the line cache with `lineReceiver`.

## Found, not fixed

- **A test encoded the defect (changed, owner to confirm):** `tests/legacy-languages.test.ts` "shebang scripts in the graph" (M0-12-R3). `bin/tool` called `shared_util()` and `app.py` called `ops_entry()` without importing either; they linked `lib/util.py` and `bin/ops` by name. The first fixture now has `from lib.util import shared_util` (still links). `bin/ops` has no `.py`, so no import can reach it (probed: `from bin.ops import ops_entry` links nothing), and the unimported call is a NameError; the test now expects no edge, renamed "a shebang script is no call target of a module that cannot import it". The 'shebang scripts take part in resolution' intent stays covered by `bin/tool`'s own and import edges.
- **Sync gap, unchanged by this task:** after a plain `scan`, adding a module that a relative Python import (`from .gen import *`) named does not re-parse the importer (same on the base commit); after `scan --force` it does. Python relative imports go through the Python resolver, which records no `unresolvedImports`.
- **`@name` decorator or a name imported from a project module that `resolveImportedCall` cannot place** (no `(` on the line, or a `;` import line) keeps by-name lookup and can pick a nearer homonym (seen in the probe: `from db.database import helper` + `@helper` linked another file's `helper`). Unrelated to unimported names; not touched.
- A dotted base (`class Sub(models.Model)`), and receiver calls on variables: unchanged, as in M2-08-R5.
- `.ipynb` notebooks are not indexed, so no notebook case arises.
- A builtin gives no external reference row: `pythonBuiltin` names stdlib modules (`os`, `sys`), not builtin functions.

## Limitations

- A star import's visibility is by file, not by name: a name a starred module imports from a third file is visible (the third file is added), and `__all__` is not read. Over-inclusive, never drops a visible name.
- A name defined only in a nested scope or by `global` (no module-level symbol) now links nothing cross-file, which is right; a same-file same-named method still resolves in-file as before.
- Python names shadowed by a conditional re-definition are treated as the module's own (symbol present).
