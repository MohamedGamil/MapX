# M0-06-R1 — Run PHP post-processing in parallel worker scans

Date: 2026-10-31. P0 from the M0-41 legacy audit (I06).

## Root causes (two)

1. **Workers bypassed the language parsers.** `parse-worker.ts` reimplemented generic tree-sitter capture handling and never called the language parser classes (`PhpParser` etc.). Every parallel scan (the default for more than 10 files) therefore lost PHP post-processing: facade rewrites, dispatch/notify edges, `laravelRole`, binding metadata. The auditor reproduced this on a 17-file Laravel fixture (0 dispatch vs 5 with `--no-parallel`).
2. **Found while proving the fix: workers never ran when MapX runs from TypeScript source.** The worker bootstrap imported `tsx/esm/api`, resolved from the *scanned workspace*, which has no `tsx`. Every source-mode scan silently fell back to one thread. This is why the first mutation check here **failed to fail**: the test passed with the fix disabled, because no worker ever ran. Earlier "parallel" tests in this repo proved nothing for the same reason.

## Fixed

- **`parse-worker.ts`:** each non-static file is parsed with `getParserForFile(...).parse(...)`, the same parser as the main thread, with `userLanguages` and `facadeMap` passed via `workerData`. The old generic walk remains only as a fallback if that throws.
- **`scanner.ts`:**
  - the worker bootstrap imports tsx via `import.meta.resolve('tsx/esm/api')`, MapX's own install;
  - a fallback to one thread now logs `[mapx] Parallel parsing unavailable (…)` instead of happening silently;
  - workers receive `userLanguages` and `facadeMap`.
- **`php.ts`:**
  - `Event::dispatch(new X)` / `Bus::dispatch(new X)` target the dispatched class X (role `event` / `job`), not the facade;
  - `$listen` arrays in providers yield `binding` edges provider → listener with `bindingType: listen` and `event: <FQN>`.

  Deviation, recorded in the acceptance criterion: F12 described an "event → listener" edge. MapX edges originate in the parsed file, so the event is carried as metadata.
