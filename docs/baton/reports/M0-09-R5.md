# M0-09-R5 — Agent files: consent for edited hashless legacy blocks; JSONC configs already up to date

Date: 2026-10-31. Base: `develop@00407d6` plus the integrator's P1 remediation patch and M0-12-R7 (same lane). P2 from review 2026-10-31 (`reviews/REVIEW-2026-10-31-2db08bd25e13.md`), against M0-09-R3 and M0-09-R4. Iteration: `docs/baton/iterations/M0-09-R5.md`.

## Delivered

- **Hashless legacy blocks need consent when edited** (`src/agents/generator.ts`, `planLegacy`). The code now matches what `docs/cli-reference.md` already said. M0-09-R4 counted every hashless block in `.continue/mapx.yaml` as mapx's own, so an edited one was deleted without asking. Now a hashless block counts as unedited only when its body, with LF line endings and trimmed, is one a released version wrote. The new table `LEGACY_BODIES['.continue/mapx.yaml']` holds the Continue block with 25, 26 or 32 tools. That covers every tag that used YAML sentinels: 0.1.9–0.2.7, 0.3.0–0.3.1 and 0.3.2–0.3.5, read with `git show <tag>:src/agents/templates.ts`. Version 0.1.7 wrote HTML sentinels into the YAML file, which the YAML regex never matched. Hashed blocks keep the M0-09-R4 rule. `needsConsent` is unchanged, so `init`, `agents generate`, `agents update` and `mapx_agents_generate` all ask, or skip without a TTY or `force`.
- **JSONC MCP configs already up to date** (`generateMcpConfigs`). The raw text was compared with `JSON.stringify(merged)`, so a JSONC file that already held the identical entry was a `merge`, rewritten as plain JSON without its comments. The check now compares parsed values (`isDeepStrictEqual(existing, merged)`, from `node:util`), so the file is `up_to_date` and is not written. This also covers plain JSON in another indentation, and an entry whose keys are in another order.
- **Docs** (`docs/cli-reference.md`, `mapx agents` sections only):
  - `agents generate` / `continue`: an edited block includes a hashless block whose body is not one those versions wrote.
  - `zed`: a settings file that already holds the identical entry is left untouched, comments included.
  - `agents mcp`: the same sentence.
- **Fixture correction** (`tests/legacy-agent-templates.test.ts`). The existing `LEGACY` constant was labelled "what mapx 0.3.x wrote", but it was a truncated body: it had no `mapx-status` provider. It is now built by `shipped(version, tools)`, which gives the exact bytes 0.3.5 wrote, plus a final newline. With the old constant, the three M0-09-R4 tests that use it would count the block as edited under the new rule.

Blast radius (`mapx impact`, scan of this worktree):

- `planLegacy` → `AgentGenerator::plan` (HIGH) → `buildCLI`, `buildServer` (MEDIUM) → `main.ts`, `startMcpServer` (LOW).
- `generateMcpConfigs` → `buildCLI`, `buildServer` (HIGH) → `main.ts`, `startMcpServer` (MEDIUM).
- Action shapes and statuses are unchanged.

## Limitations

- A hashless legacy block is recognised by its exact body, as each tag wrote it. If an unreleased commit between tags wrote a different body, that block now needs consent.
- When the mapx entry does change, the merged file is still written as plain JSON, with a warning (M0-09-R3 behaviour).

## Findings outside this task

The checked-in agent files were not changed (`git status`).
