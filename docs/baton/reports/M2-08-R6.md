# M2-08-R6 report: a bare specifier never resolves to a relative project file

Spec: [iterations/M2-08-R6.md](../iterations/M2-08-R6.md). Started from `develop@3afa180`; the change is uncommitted at the time of writing.

## Cause (reproduced before the fix)

A probe workspace was scanned with the real CLI (`express.js`, `lib/thing.js` and `components/Button.tsx` at the repo root, `express` in package.json, no tsconfig or alias):
- `server.js`: `import express from 'express'`, `'lib/thing'` and `'components/Button'` each gave an import edge to the root file, and each call a verified call edge (`a call express.js#express`).
- `legacy.js`: `require('express')` and `require('lib/thing')` gave import edges to `express.js` and `lib/thing.js`, and `b call express.js#express`.
- Under a CRA jsconfig (`baseUrl: src`, `src/utils.js`), `import { helper } from 'utils'` kept its import and call edges. This is the task's M2-25 example; it already worked.

`resolveImportPath` (`src/core/scanner.ts`) ended its candidates with the specifier itself, `bases.push(target)`, for a bare specifier as well as a relative one. After `paths`, aliases and `baseUrl` found nothing, `express` was probed as the repo-root path `express(.js|.ts|/index.js …)`. M2-20 sent `require('x')` through the same function, so CommonJS got the defect too. `resolveRequirePath` is PHP's and is not involved.

## Delivered

- **`resolveImportPath`:** for a JS, TS, Vue or Svelte importing file, a specifier that is neither relative nor absolute is no longer probed as a path from the repo root. `paths` (with `*` patterns), bundler aliases, `@/` fallbacks and the `baseUrl` entry come first and are unchanged. A root-relative URL (`/lib/thing.js`) and every other language (C `#include "util.h"`, shell `source lib.sh`) keep the old probe. The unresolved-import record (M2-08-R2) is unchanged.
- **Sync:** `sync` and `scan --force` now agree for a project `express.js` added later (before: `scan --force` linked it, sync did not).
- **Workspace packages (review P1):** a bare specifier naming a workspace package resolves to its folder (`workspacePackageTargets` in `src/core/scanner.ts`, over the `npmWorkspacePackages` name-to-folder map that `npmWorkspacePackageNames` now derives from), after `paths` and `baseUrl`. `name` is the entry: `exports` (`.`, string or `import` / `default` / `require` / `node` / `types` condition), `module`, `main`, `types`, then `index` and `src/index` (a `main` naming an unindexed build output falls through). `name/sub/path` is an `exports` subpath or pattern (`./utils/*`), then `<folder>/sub/path`. It works for nested folders and names unlike their folder.
- **`baseUrl` follows `references` (review P2):** `tsBaseUrl` in `src/core/js-aliases.ts` takes the `baseUrl` of the first referenced config that has one when a solution-style tsconfig.json has none, as `paths` already did.
- **`EXTRACTOR_VERSION` 26** (not bumped again by the review).
- **Tests:** 13 new e2e tests in `tests/import-bound-externals.test.ts` (three `describe` blocks, 64 tests in the file). Failing before the fix: the import, require, Vue/Svelte and sync tests (4 of the first 8 written; the other 4 were guards that already held).
- **Existing test changed:** `tests/external-refs.test.ts`, case "an indexed module named like a bare specifier is added at the root". It asserted that a root `pg.ts` made `import 'pg'` a project module (the `pg` external reference `gone`); it now asserts the package stays external (`stays`), sync equal to `scan --force`. This is the behaviour M2-08-R6 sets out to change.

## Scope decision: the M2-25 limitation

Not the same mechanism, scoped out. The loss (`import u from 'utils'; const { helper } = u; helper()` giving no by-name edge) happens in the parser: `isPackageSpecifier(spec, true)` in `src/parsers/generic-wasm-parser.ts` drops the reference at parse time, when no tsconfig or resolver is known. The probe confirms it (`cra/src/App2.jsx` has an import edge and no call edge, before and after). The task's own example, `import { helper } from "utils"` with `{"baseUrl": "src"}`, already kept its edges and is now a regression test (a one-segment name that is also a package, `express`, resolves to `cra/src/express.js` under `baseUrl`, as tsc does). A fix needs the parser to hand the specifier to the scanner: follow-up M2-25-R1.

## Limitations

- **Root-level module folders without MapX-readable config** (follow-up M2-08-R11): `NODE_PATH=.`, webpack `resolve.modules: [__dirname]`, jest `moduleDirectories: ["<rootDir>"]`, Deno `deno.json` import maps. Such an import (`require('lib/a')`, `import 'models/user'`) loses the accidental root-relative edge. The reviewer's cases:
  - G: the import edge is lost;
  - K: colliding names (`user.save()`, `find()`, `post.save()`) lose their real call edges, since by-name lookup is ambiguous;
  - J: type-only, constant and side-effect imports lose all their edges;
  - `external_ref_candidates` now mark such root folders (`models/user`, `lib/util`) as `npm`, `external=1`, which arch `npm:` selectors may pick up.
- **M2-25 destructured-call loss** (follow-up M2-25-R1): `import u from 'utils'; const { helper } = u; helper()` under `baseUrl` keeps its import edge but no call edge.
- **Workspace packages:** any folder holding indexed files whose package.json has a `name` counts, as `npmWorkspacePackageNames` already decided; the root's `workspaces` list, `pnpm-workspace.yaml` and `lerna.json` are not read. An entry that `exports` points at a build output (`dist/…`) with no source twin finds no file; only `src/index` is tried as a fallback. Sync picks up a package entry or file that appears later at `scan --force`, as for `baseUrl`.
- **A solution-style tsconfig** with several references takes the first `baseUrl`.
- **By-name lookup for an unplaceable import** (`lib/thing` beside a project `lib/`) is unchanged (M2-08-R3).
