# M4-14 — Batched worker messages

Decision D025.

## Before

There was one message per file each way: 3,000 files meant 3,000 job messages and 3,000 result messages, each a structured clone and a round trip during which the worker sat idle.

## Delivered

- **Protocol** (`src/core/worker-pool.ts`, `src/parsers/parse-worker.ts`):
  - A lane sends `{type:'batch', seq, jobs}` of up to `BATCH_FILES` (16) files or `BATCH_BYTES` (256 KB).
  - The worker parses them in turn and answers `{type:'results', seq, results}`.
  - A file that fails is still handed back on its own, inside the results.
  - When the results will not clone together, the worker posts them one by one, and hands back only the file whose result cannot be cloned.
  - Stale `seq` messages are ignored.
- **Crashes:**
  - When a worker dies on a batch, the batch's files are retried one per message (`solo`).
  - Only a death on a file alone counts toward its hand-back (2 deaths → main thread) and toward the replacement cap (`> size × 2`).
  - A batch death happens at most once per killer file, because its files then travel alone.
- **Watchdog:** a batch with no answer within 30 s plus 1 s per 100 KB (`MAPX_WORKER_BATCH_TIMEOUT_MS`) terminates its worker and takes the crash path. Before, as with one file per message, a parse that never ended held its lane forever.
- **Scheduler fixes found while verifying** (M4-12 code, exercised harder by batches):
  - **Steal the heaviest language:** a lane out of work steals the language with the most work left in another lane, judged against the grammar-load threshold by that group's weight. It used to take the last language of the largest queue, which in the segment layout is a small one, so a minority grammar got loaded by two workers. The M4-12 e2e test caught this in `npm run check`.
  - **No new grammar mid-batch:** only a batch's first file may need a grammar the lane does not hold; the rest come from its own queue or languages it holds.
- **Statistics:** `messages: { jobs, context }` per run.
- **Test hook:** `MAPX_TEST_WORKER_UNCLONEABLE=<file>` makes a worker produce a result that cannot be cloned.
- **Docs:** `docs/configuration.md` and the CHANGELOG.

## Measurements

The machine was heavily loaded by other processes (load average 13–32) throughout, so I ran interleaved before/after pairs (M4-12 `d2e2bed` worktree against the working tree), with `MAPX_PARSE_WORKERS=8`:

| Bench | Before (median of 5) | After (median of 5) | Job messages |
| --- | --- | --- | --- |
| Generated, 3,000 files | 3,503 ms | 3,499 ms | 3,000 → 188 |
| MapX sources ×3 (829 files) | runs from 6.5 s to 14 s; noise exceeds any difference | same | 829 → 55 |

Batching cuts messages about 16-fold. Wall time is unchanged within this machine's noise: message passing was not the bottleneck at these sizes. Each index is identical to `--no-parallel`.

`tests/worker-pool.test.ts`, the M4-14 tests:
- **Message bound:** 150 files on 4 workers use at most ⌈150 ÷ 16⌉ + 4 job messages and at most 4 context messages. `BATCH_FILES` is pinned at 16.
- **Progress and hand-back:** an in-process scan reports progress up to 60 of 60, and `MAPX_TEST_WORKER_FAIL` hands back one file while the rest of its batch is used.
- **Unclonable result:** one file hands back with `DataCloneError`, and the index equals `--no-parallel`.
- **Worker death:** a worker dying on `src/m20.ts` mid-batch hands back only that file, and the index equals `--no-parallel`.
- **Fake workers, through the pool's `spawn`:**
  - one killer file on a pool of 1 costs only itself, received in its batch once and then alone twice;
  - a batch that never answers is ended by the watchdog (150 ms in the test), handing back only the silent file.
- **Steal choice:** a lane out of work steals the heaviest language, and the rest of a batch never takes a grammar the lane does not hold.

## Independent review (fresh agent)

No lost or duplicate results, and no hang introduced:
- **Harness checks:** with fake workers, the reviewer checked partial results followed by a death, stale `seq`, `close()` mid-run, and solo loops. Every file was covered exactly once.
- **Bun binary:** the index is identical to `--no-parallel`. The fail, exit and unclonable hooks each hand back exactly one file, and `DataCloneError` behaves as in Node.

Findings:
- **P2, fixed:** one killer file cost three replacements instead of two, because the batch death counted, so a pool of 1 handed back 185 of 200 files. Only solo deaths now count, and the cap is strictly greater than `size × 2`, so the replacement after the last death is still allowed. A fake-worker test covers it.
- **P2, fixed:** nothing tested "only a solo death counts". The fake-worker test now asserts the exact sequence of messages the killer file receives.
- **P2, fixed:** the message bound in criterion 1 ignored the 256 KB cap. It now reads ⌈N ÷ 16⌉ + ⌈B ÷ 256 KB⌉ + workers.
- **Recommendation, done:** a per-batch watchdog.
- **Minor, accepted:**
  - Abort and close finish the in-flight batch (at most 16 files).
  - Progress advances per batch.
  - A batch may exceed 256 KB by one file, because the size check runs before a file is added; a single large file still travels alone.
