# M0-02-R4: re-resolving references to moved files; blob-hash keys for non-root repos

Date: 2026-10-31. Source: the limitations in `docs/baton/reports/M0-02-R3.md`. Built on develop `02e6c03`, which includes M0-10-R3.

## Before (reproduced on the unchanged code)

## Delivered

### Moved targets (the M0-02-R2 ledger, extended in the spirit of M0-10-R3)

M0-10-R3 records what resolution could see and re-parses when that changes. Here the record is the existing removed-files ledger, and the re-parse is limited to the recorded referrers.

- **`removeFiles`** still records each removed file's referrers (`meta removed_files:<repo>`). It now also records the names they resolved into the file (`meta removed_names:<repo>`): the trailing identifier of each inbound edge's `target_symbol`, so `App\Services\UserService` gives `UserService`.
- **`movedReferrers`.** When a scan has new or changed files, one combined word-boundary regex over the pending names is run on their text. For each removed file whose names appear, its recorded referrers are re-parsed. Whole repos are never re-parsed. A file that only mentions a name costs one re-parse of those referrers.
- **`settleMovedNames`.** A removed file's names are dropped once a new or changed file parsed in that scan declares one of them. Later mentions then trigger nothing. The referrer list stays, so the M0-02-R2 path-returns case still works. `takeReferrers` drops both entries when the path itself comes back.
- **Wiring.** All three paths use it:
  - full scan (`_scanFullForRepo`);
  - git sync (`_scanIncrementalForRepo`), alongside R3's rename referrers;
  - content-hash sync (`_scanIncrementalByHash`).
- **Order.** Each path now removes deleted files *before* deciding what to parse. For the full scan this moved the deletion from the end of the scan to just after discovery, guarded by `!aborted`. This way a move within one scan records the old path's referrers, and neither the file map nor the symbol index can resolve them back to the old path.

### Blob hashes (`src/core/git-tracker.ts`, `src/core/scanner.ts`)

- `getGitBlobHashes(repoRoot, relativeTo = repoRoot)` prefixes keys with the repo's path relative to `relativeTo`. The full scan passes the workspace root.
- The new `gitBlobId(content)` computes git's blob id in-process (`sha1("blob <n>\0" + bytes)`).
- The full scan stores HEAD's blob only when it is the id of the indexed content. A file modified in the working tree stores `null`, so a later sync never takes stale content for unchanged.
- Git sync skips a listed file whose stored `git_blob_hash` equals the blob id of its current content, for example after a mode-only change. It still stores `null` for the files it re-indexes, as before.

## Limitations and findings

- **Text pre-check.** Whether referrers are re-parsed is decided from the text of new or changed files, before parsing. A file that mentions a recorded name without declaring it re-parses those referrers each time, until a declaration settles the name. The cost is bounded by the recorded referrers.
- **Edges without `target_symbol`** (path-based imports) record no names. Moving their target breaks the import path, so the referrer changes and is re-parsed anyway.
- **Same repo only.** A target that moves into another repo is not followed; the ledger is per repo, as in M0-02-R2.
- **Git sync stores `null` blob hashes** for the files it re-indexes, as before. So the skip applies to files whose last indexing was a full scan of clean content.
- **R3's rename-specific referrer re-parse is kept.** It is unconditional and also covers edges without names. For renames it now overlaps with the general mechanism. R3's mutant M4 (rename referrers not re-parsed) was re-run and now survives: the rename test exits 0, because the moved-name path re-links the parameter type. This is equivalent for by-name references; the R3 code only matters for edges without a `target_symbol`.
- **Finding, out of scope (pre-existing, reproduced):** git sync never drops a deleted file that was untracked or only staged at the last scanned commit. A probe added an untracked `b.ts`, ran `sync` (b.ts indexed), deleted it and ran `sync` again: `b.ts` was still in `files`. `git diff <last_scan_commit>` lists neither side, and `git ls-files --others` no longer lists it. It showed up while I was extending R3's rename test (a staged rename back followed by a delete). It needs a remediation task, for example comparing the repo's indexed paths that are absent from HEAD against the disk.

Changelog: `scan` and `sync` now re-link the referrers of a class moved to another file without `--force`, store git blob hashes for repos that are not at the workspace root, and skip files git lists whose content is unchanged (M0-02-R4).
