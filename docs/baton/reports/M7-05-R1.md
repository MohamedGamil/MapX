# M7-05-R1 report: first Pages deployment: the environment refuses main, and the site base path has the wrong case

Delivered 2026-11-07. Spec: `docs/baton/iterations/M7-05-R1.md`. Remediation of M7-05 (DONE is terminal; the defect note is also in `reports/M7-05.md`).

The work was done before this task was registered and started: the owner reported the failure, the fix was written and tested, and BATON's remediation record was added around it. The task's `startedAt` therefore lies after most of the work. The owner committed and pushed the fix (`c353e04`) before this report was written; the real run that followed is the strongest evidence below.

## Defects

1. **The first deploy was refused.** The first run of `pages.yml`, on `main` (run 42333986272), failed: `Branch "main" is not allowed to deploy to github-pages due to environment protection rules.` Its build job had succeeded in every step; only the deploy job was refused, before any step ran. The cause, read from the repository's settings (read-only `gh api`): the `github-pages` environment has one custom deployment-branch policy, `develop` (GitHub derives it from the default branch, which is `develop`); no required reviewers, no wait timer. M7-05 had listed this as a likely first-run failure but never read the environment.
2. **The base path had the wrong case.** The repository is `MapX`, and Pages reports its address as `https://mohamedgamil.github.io/MapX/`. A Pages address is case-sensitive in that segment: a public repository with a capitalised name shows `/TypeScript-Website/` served and `/typescript-website/` a 404, and this site's own `/mapx/` is a 404 on the live host. The site had been built for `/mapx/`, copied from the lowercase name in `package.json` and never checked. Every asset URL would have been a 404 once a deploy succeeded.

## Fix

- **Deploy branch:** the owner chose `develop` when asked (the other option was to add `main` to the environment's allowed branches). `pages.yml` triggers on pushes to `develop` and its deploy job is guarded for `refs/heads/develop`; a manual run from another branch builds but does not deploy.
- **Base path:** the default is `/MapX/`, and the Pages build step sets `SITE_BASE` to `/${{ github.event.repository.name }}/`, so a rename or a case difference cannot recur. The tests read `DEFAULT_BASE` instead of about 20 `/mapx/` literals; one test pins `/MapX/` with the reason beside it.
- **Links into the repository** (edit links, the changelog link, and links to files the site does not publish) now point at `develop`, the branch the live site is built from, through one constant (`REPO_BRANCH`); a test ties it to the workflow's deploy branch. This came from the independent review: they had said `main`.
- **Records:** D045 corrected, the M7-05 report and the M7-01 report and spec carry dated notes.

## Independent review

A fresh reviewer, given the criteria, the diff and read-only access to the repository's real GitHub settings and the failed run's log, found no P0 and no P1. It confirmed from the API: the environment has one policy (`develop`) and nothing else restricting it; Pages is set to build from GitHub Actions with no custom domain; the built canonical URLs, sitemap, `og:image` and `robots.txt` all carry `https://mohamedgamil.github.io/MapX/`; `github.event.repository.name` is `MapX` for both `push` and `workflow_dispatch`; a job-level `if` is evaluated before the environment is requested, so a manual run from another branch cannot be refused; and the failed run's log shows no other error.

- **P2, fixed:** the edit, blob and tree links pointed at `main` while the site tracks `develop` (see Fix).
- **P2, noted:** the M7-01 acceptance criterion and records still say the default base is `/mapx/` (they are DONE records; a dated note says what superseded them, and the criterion is read as "starts with `DEFAULT_BASE`").
- **P2, accepted:** `robots.txt` and `sitemap.xml` under `/MapX/` are not read by crawlers, because the host root has no `robots.txt` (documented since M7-06; the sitemap can be submitted in Search Console).
- **P2, accepted:** if `github.event.repository.name` were ever empty, `//` would normalise to `/` without an error. It cannot be empty for the workflow's two triggers.
- **Inherent:** the tests read the workflow's text and never GitHub, so a later change to the environment's branch rule or a rename of the repository is not caught by them; the evidence above holds as of today.

## Limitations

- A failed deployment record from the `main` run (id 7615966058) remains in the repository; it is harmless.
- The workflow now runs on every push to `develop`, in parallel with CI, which it does not wait for.
- Node 20 deprecation notices appear in the Actions logs (the actions are forced onto Node 24 by GitHub); the workflow uses Node 20 for the build, as `ci.yml` does.
