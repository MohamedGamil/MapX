# M0-02-R11 report: a sync killed before its upserts commit keeps restored files

Found by the 2026-11-02 review (M0-02-R10 DEFECTIVE, P2).

`takeReferrers` and `takePendingReferrers` deleted their `removed_files:`, `removed_names:` and `pending_referrers:` entries with autocommit writes before the sync read files and wrote its upserts. A sync killed in that window lost the records:
- **git sync:** a file restored at HEAD stayed out of the index until `scan --force`, because git never lists it again;
- **hash sync:** the restored file's referrers lost their edges into it.

## Delivered

`src/core/scanner.ts`:
- **Deferral window:** `startDeferredConsumption`, `consumeLater` and `applyDeferredConsumption`. These record writes now wait:
  - the deletions of `takeReferrers` and `takePendingReferrers`;
  - after the independent review, the git sync's new `dirty_paths:` list and `configReferrers`' new `js_configs:` signatures.
- **When they run:** at the top of the transaction that writes the upserts, in the full scan, the git sync and the hash sync. A rollback, or a sync killed before that transaction, undoes them together with the upserts. Each early return that re-indexes nothing applies them too.
- **How a deletion runs:** it re-reads the record and removes only the taken files or paths, so entries queued meanwhile (another repo's `queueReferrers`) stay.
- **Outside a sync:** `consumeLater` applies at once, for example at the end-of-run `configReferrers` calls.
- **Full scan, not covered:** a full scan writes real hashes in that transaction and parses afterwards, so a kill after it commits still loses the consumed referrers. That case is registered as M0-02-R12.
