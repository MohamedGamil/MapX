# M5-20-R1 — npm attribution: a nested lockfile that cannot be read gives manifest-only attribution

Date: 2026-11-03. Base: `develop@f0fc004`. Owner: lane agent. Iteration: `docs/baton/iterations/M5-20-R1.md`. Source: `reports/M5-21.md`, "Findings outside this task" (the same defect as M5-21 review P2 for Composer).

## Delivered

- **`src/core/manifests/npm.ts`, `NpmAttributor.lockFor`:** a folder holds a lockfile when one of `npm-shrinkwrap.json`, `package-lock.json`, `pnpm-lock.yaml` or `yarn.lock` reads as text **or exists** (a folder, a file without read permission). So a lockfile that is there but cannot be read ends the walk, as a corrupt one already did. The first readable, parseable lockfile of that folder answers, as before. If none does, the manifests answer alone, flagged `manifest`, and a parent folder's lockfile is never used.
- **`NpmWorkspace`** gains the optional `exists(path)` probe. `ComposerWorkspace` now picks it from there, with no change in behaviour. The decision pass's workspace already provided it (M5-21 review), so `src/core/scanner.ts` is unchanged.
- **Inputs and staleness:** unchanged. An unreadable lockfile is recorded as read with no text, as before. A later fix to it (made readable, or replaced by a file) changes its hash, so the index becomes stale and a sync re-attributes.

No CLI, MCP, schema or extractor change (what a scan extracts is unchanged). No new dependency.

## Review

The integration owner's review of ceed474 found one P2, which is fixed in the amended commit, rebased onto `develop@b4f450b`.

**P2: after an unreadable nested lock was removed, a sync differed from `scan --force`.**
- **Cause:** only a lock's text was recorded as an input. An unreadable lock was recorded as null, the same as an absent one, so removing it was no change. The skip kept `manifest`, while `--force` gave `lock` (probe `pip-review/s3.mts`).
- **Fix:** a path that is there but cannot be read is now recorded as `UNREADABLE_INPUT`, a marker no file can hold, in `src/core/manifests/inputs.ts`.
  - `changedInputFiles` compares the same three states: absent, unreadable (a folder, or a file it cannot read) and its text. So removing or fixing an unreadable lock is a change, and leaving it alone is none.
  - The npm and Composer attributors record it through `read`, and test for a lock with `present`. Composer had the same defect since M5-21's review, so it is fixed here too. The pypi attributor (M5-22) uses the same mechanism.
  - An index whose inputs recorded an unreadable path as null re-attributes once on its next sync.
- **Regression tests:** in "a git sync / a hash sync, when a manifest or lockfile changes" and "… when composer.json or composer.lock changes", "a nested package-lock.json / composer.lock that is a folder / a file it cannot read is removed: the root lock answers, as scan --force" (8 tests). Each test:
  - scans and gets `manifest`;
  - checks that the untouched unreadable lock is no input change;
  - removes the lock, syncs, and gets `lock`, equal to `scan --force`.
- **Mutation check:**
  - An unreadable path recorded as null (the code before the fix): all 8 fail.
  - A folder compared as absent in `changedInputFiles`: the 4 folder cases fail (an untouched folder would make the index stale forever).

## Limitations

- When the tests run as root, the chmod 000 case is skipped, because root can read the file. The folder case still runs.
- A folder that holds both an unreadable lockfile and a readable one uses the readable one, in `NPM_LOCKFILES` order, as before.
