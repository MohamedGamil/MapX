# M5-21-R1 — Composer: classmap and files autoload attribution from vendor/ when present

Date: 2026-11-03. Base: `develop@0628819` plus this lane's M5-23-R1 commit. Owner: lane agent. Iteration: `docs/baton/iterations/M5-21-R1.md`. Source: `reports/M5-21.md` (Limitations "No `vendor/`" and "PECL extensions"; review P1-1's sibling packages).

## Delivered

- **Composer's generated metadata, read as data** (`src/core/manifests/composer.ts`). MapX reads three files, never by executing PHP:
  - `parseAutoloadMap` reads `vendor/composer/autoload_classmap.php` and `autoload_files.php`. These are arrays of `'Key' => $vendorDir . '/pkg/name/src/X.php'` (or `$baseDir . …`, `__DIR__ . '/..' . '/…'`, or a plain absolute path). A linear tokenizer reads them (review P1): single- and double-quoted strings with their escapes, `=>`, `.`, comments, with `array(` or `[` syntax. Files over 64 MB are skipped with a warning. Each path becomes relative to the Composer root: `$vendorDir` is `vendor/` and `$baseDir` is the root. Text with no `return array(`/`[` throws, and is then treated as absent.
  - `parseInstalledJson` reads `vendor/composer/installed.json` the same way. Composer 2 writes `{"packages": [...], "dev-package-names": [...]}`, where `install-path` is relative to `vendor/composer/` and is null for a metapackage. Composer 1 writes a plain list, and each package is at `vendor/<name>`.
  - No other file under `vendor/` is read. A package's sources never are.
- **A file → its package:** the installed package whose install path is the longest prefix of the file's path. A package installed by a custom installer outside `vendor/` (`$baseDir . '/lib/legacy/…'`) is found too. Without a readable installed.json, MapX uses Composer's default layout `vendor/<vendor>/<name>/…`. A file in no package (the project's own `$baseDir . '/app/…'`, or Composer's runtime `vendor/composer/InstalledVersions.php`) has none.
- **Precedence** in `ComposerAttributor.attribute`:
  1. a built-in;
  2. a PECL name (ambient, below);
  3. a **class the classmap names**: the package installed where its file is;
  4. the lock's PSR-4/PSR-0 prefix (M5-21);
  5. a **namespaced function no prefix covers**: by naming convention among the packages whose `files` autoload loads. A global function stays unknown, even when only one package loads files (review P1: nothing MapX reads shows which file defines it);
  6. M5-21's fallbacks (convention over the lock's classmap and files packages, then the stale-lock requirements).

  The classmap comes before the prefix. An optimised autoloader (`composer install -o`, `dump-autoload -o`) lists every class there, so it also tells apart sibling packages that share a prefix (`Illuminate\Support\Collection` → illuminate/collections, `Illuminate\Support\Str` → illuminate/support). M5-21's review P1-1 had left those unknown.
- **The Composer root** is the nearest folder, from the file up to its repo's root, that holds a composer.lock (readable or not), or else the nearest one holding vendor/composer metadata. A nested composer.json is no root (review). An absolute install path maps to no package (review).
- **Lazily, cached per pass** (`ComposerVendor`, one per root and per pass).
  - The classmap is read and parsed when a class first reaches step 3.
  - `autoload_files.php` is read when a function first reaches step 5.
  - installed.json is read when a classmap or files entry first needs its package.
  - A large classmap is parsed once into a `Map`, and its paths are mapped to packages per lookup, memoised. A name that a built-in, a PECL extension or the lock already answers reads nothing more (test "reads vendor/composer files only when a name reaches them").
- **`direct`, `dev`, flag.**
  - `direct` comes from the manifests, as before.
  - `dev` comes from the manifests, then the lock, then installed.json's `dev-package-names`.
  - An answer from the vendor metadata is flagged `lock` when composer.lock or installed.json was read: installed.json is Composer's record of the installed tree. With neither, it is flagged `manifest`.
- **Inputs, sync, stale.** `src/core/manifests/inputs.ts` names the three paths (`COMPOSER_VENDOR_INPUTS`). The attributor reads them through the same recorded reader as composer.json and composer.lock, so each read, or each probe that found nothing, joins the `external_inputs` record. As a result, `mapx status`, the `check`/`arch` gates and sync notice `composer install` or `dump-autoload` rewriting them. Tests: "vendor/composer: the classmap drops a class / installed.json moves a package / vendor/ is removed: the stale check sees it, sync equals scan --force", on the git and hash syncs.
- **PECL decision: `ambient`** (`phpPecl`, `src/core/manifests/php-pecl.ts`).
  - Why: PHP does not ship a PECL extension (`Redis`, `Imagick`, `Memcached`, `apcu_fetch`, `igbinary_serialize`, `xdebug_*`), and no Composer package provides it. composer.json can only require it as a platform package (`ext-redis`). The runtime the code is deployed on provides it, which is what `ambient` means for cgo's `C` (M5-23). Calling it `builtin` would let a `builtin: true` allowance pass a dependency that exists only on some servers.
  - The row is `package: 'ext-<name>'`, `origin: 'ambient'`, and `direct`, `dev` and `attribution` null, like a built-in. The `ambient` selector matches it (`ambient: "ext-redis"`).
  - It is checked after built-ins and before packages: a polyfill package (symfony/polyfill-apcu) defines the name only when the extension is missing.
  - The list is generated by the new `pecl` mode of `scripts/gen-php-builtins.php`, which reflects the running PHP's non-bundled extensions. Here that was PHP 8.2.35 with apcu 5.1.28, igbinary 3.2.16, imagick 3.8.1, memcached 3.4.0, msgpack 3.0.0, redis 6.3.0 and xdebug 3.5.3 (`PHP_PECL_SOURCE`). No name is in both lists (test).
- **Extractor version 19** (`src/core/extractor-version.ts`; 17 before the rebase onto develop's M2-12/M2-13). The scan still extracts the same candidates. But a pass whose recorded inputs are unchanged keeps the stored attribution, and an index built before records no vendor input. So without the bump, its PHP rows would keep their old attribution (`Redis` with package null) until a Composer input changed. The bump makes such an index rebuild once.
- **Docs:** `docs/architecture-rules.md`, the external-dependencies table (Composer row: the vendor metadata read and PECL as ambient) and the `ambient` selector row.

Files beyond the task's `affectedFiles` (`src/core/manifests/composer.ts`, `tests/external-refs.test.ts`): `src/core/manifests/inputs.ts` (as the brief asks), `src/core/manifests/php-pecl.ts` (generated, new), `scripts/gen-php-builtins.php` (`pecl` mode), `src/core/extractor-version.ts`, `docs/architecture-rules.md`.

No CLI or MCP option changed. No schema change. No new dependency.

## Limitations

- **Only the generated metadata.** A class the autoloader does not list, because the autoloader is not optimised and the class is PSR-4, is answered by the prefix as before. A global function is attributed only when exactly one installed package autoloads `files`. Real projects usually have several (polyfills, illuminate/*), so `collect()` stays unknown: telling which file defines it would need the package sources, which MapX never reads.
- **`config.vendor-dir`, `COMPOSER_VENDOR_DIR` and `COMPOSER`** are not honoured. Only `<root>/vendor/composer/` is read.
- **Stale vendor metadata.** The vendor metadata is trusted as installed. If composer.lock changed and `composer install` has not run, the classmap's answer wins for the classes it lists.
- **The PECL list** is the extensions the reflected PHP had loaded (seven here). Others (mongodb, swoole, grpc, protobuf, …) are not recognised and stay package rows of unknown package. Regenerating on a PHP with more extensions widens the list.
- **An index built before** is rebuilt once (extractor version 19), as explained above.

## Findings outside this task

- **Attribution changes skip an index built before.** A pass whose recorded inputs are unchanged keeps every stored attribution, so a change to the attribution rules alone (no extraction change) does not reach an existing index without `scan --force`. Here it is handled with an extractor-version bump. A separate "attribution rules version" in the inputs record would avoid re-parsing for such changes. That is left to the integration owner.
