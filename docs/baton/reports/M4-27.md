# M4-27 report: Lua files parse correctly after the first one in a process

The M4-26 lane found it: a scan sometimes lost the Lua call edge `M.foo → M.bar`, more often under CPU load. It was traced here to the grammar, not to the scanner.

## Finding

| Probe | Result |
| --- | --- |
| 12 parallel scans of Lua, Go and Java files, auto worker sizing (load ~28) | the Lua edge missing in 10 of 12 |
| The same with `MAPX_PARSE_WORKERS=0` / `=4` | missing in 4 of 10 / 0 of 10 |
| One process: parse the same Lua source 3 times with the pooled parser | ok, ERR, ERR |
| …with `parser.reset()`, a fresh `Parser`, or a freshly loaded `Language` | ERR every time after the first parse of the process |
| Every other bundled grammar, 3 parses of a sample each | identical, error-free trees |

- **The broken parse:** after the first parse, `local M = {}` reads as an unterminated string (`(ERROR) … (MISSING _string_end)`), so the reference query finds no calls.
- **Cause:** the external scanner (`tree-sitter-lua` 2.1.3, `src/scanner.c`) allocates its state with `malloc`, and its `deserialize` ignores the empty state that starts a parse. The previous parse's state leaks in, through the reused payload or recycled heap memory.
- **Why it looked like a race:** each worker or process parsed its first Lua file correctly. Load changed how many files the main thread parsed, and in what order.

## Delivered

- **`scripts/build-wasm.ts`:** grammars can carry `patches`, exact replacements applied to a copy of the source under `build/`.
  - Each patch must match exactly once.
  - A patched grammar is built from source, and is never copied or downloaded prebuilt.
  - The Lua patches: `calloc` for the state, and a reset to zero on an empty `deserialize`.
- **`wasm/tree-sitter-lua.wasm`:** rebuilt with `npm run build:wasm` (tree-sitter CLI 0.23.2, emsdk 3.1.64 in Docker). It is still ABI 13: the grammar's generated parser is unchanged, only its scanner.
- **`EXTRACTOR_VERSION` 3:** indexes built before this re-parse every file once on their next sync (M5-26). Version 3 also covers M2-04-R4 and M2-06-R4.
- **`tests/grammar-health.test.ts`:**
  - every bundled grammar has a sample, or a stated exclusion;
  - all grammars are loaded, then each parses its sample three times, with identical error-free trees required;
  - Lua parsed repeatedly, two files, and Lua after Java each yield their references;
  - an end-to-end scan of three Lua files gives each its call edge.

## Mutation check

The old `wasm/tree-sitter-lua.wasm` was put back, then the new one was restored and compared with `cmp`. Three of the four tests fail:
- "parses every sample three times alike";
- "gives every Lua file its references";
- "gives each file its call edge".

The fourth, "has a sample… for every bundled grammar", does not depend on the binary.

## Independent review

A fresh agent got the diff and the old binary, without these conclusions. It found no P0 or P1.
- **Realistic Lua:** five files with long strings and comments, escapes, `goto`, metatables, `:` calls, varargs, `//`, bit operators, `<const>`/`<close>` and Luau syntax, plus four unterminated-token files. The new grammar's trees match the old binary's first-parse trees byte for byte, in any order and after the unterminated files.
- **Through MapX:** an 11-file workspace gives identical results with `MAPX_PARSE_WORKERS=0` and `=4`: 97 symbols, 13 call edges, and every file has its edge.

**Pre-existing, unchanged** (the old and new trees are identical):
- a backslash-newline inside a string, and `\z`, give an ERROR node;
- `.luau` type syntax gives an ERROR node;
- `self:other()` and `acct:withdraw()` give no call edges. Registered as **M2-10**.

## Limitations

- **The Vue grammar:** `wasm/tree-sitter-vue.wasm` throws "resolved is not a function" (a missing import) on `{{ }}`. VueParser does not use it; the health test lists it as excluded, with that reason.
- **Rebuilding needs Docker or emcc:** a patched grammar cannot fall back to a prebuilt binary, so `npm run build:wasm` for Lua requires one of them.
