## Delivered

- **`src/parsers/languages/vue-stores.ts` (new).** `annotateStoreRefs` runs from the JavaScript and TypeScript parsers, so it also runs on `.vue` script blocks. A regex gate keeps unrelated files to one test.
  - **Vuex store model** (`fileMetadata.vuex`):
    - a file is a root (`new Vuex.Store` / `new Store` / `createStore` from `vuex`) or a module (`export default { … }` with `namespaced` / `getters` / `mutations` / `actions` and no component keys, directly or through `const actions = { … }`);
    - the model records member names per kind (`state`, `getters`, `mutations`, `actions`) and `modules` (import specifier, or an inline module).
    - Arrow-function members, which the generic extraction skips, become `method` symbols scoped to their kind (`openTickets`, kind `method`, scope `getters`).
  - **Vuex calls:**
    - `this.$store` / `$store` / `store` `.dispatch|commit('ns/NAME')` adds a `call` reference to `NAME` with the namespace and kind;
    - `dispatch|commit('NAME')` on the action context inside a module stays in that module, when it declares `NAME`;
    - `{ root: true }` and slashed names are resolved from the root.
  - **Map helpers** (`mapActions` / `mapGetters` / `mapState` / `mapMutations` / `mapWritableState`, Vuex namespace or Pinia store) in an Options API component add one reference per mapped name from the component symbol. `this.NAME()` resolves through `THIS_MEMBER_STEPS` step 3, which is now exact: the store it maps from, with `local: 'REMOTE'` naming `REMOTE`. The name-only fallback is gone.
  - **Pinia** (a store hook `use…Store` that is imported, or defined in the file with `defineStore`):
    - `useXStore()` → the hook;
    - `x.action()` where `x` is bound to `useXStore()` in an enclosing scope → the action;
    - `useXStore().action()` → the action.
    The existing name-only reference is re-targeted, or a reference is added when the generic extraction skipped it (`clear` and `add` are on the JS built-in method list).
  - **Ownership** of these references (rule 2): a member's bare name (`FETCH_ALL`, not `actions::FETCH_ALL`); the component for top-level `<script setup>` code and code directly in `setup()`.
  - **Resolution (`resolveStoreTarget`):**
    - Pinia goes to the store's own file only, and only if that file declares the member, so a call never resolves to another store or to the caller.
    - Vuex walks the namespace path through namespaced modules from the store root, following imports, and requires the member for its kind. Without a namespace, it looks at the root and its non-namespaced modules. In-module calls resolve to the module file.
    - The nearest store root is tried first, so each app in a monorepo resolves against its own store.
- **`src/parsers/languages/vue-ast.ts` (new):** tree-sitter helpers now shared with `vue-options.ts`. `vue-options.ts` keeps its exported API (`analyzeOptionsComponent`, `vueThisScope`, `OptionsComponent`, which M3-02 uses). `resolveThisMember` now returns `{ file, symbol }`.

## Limitations

- **Unresolved (no edge):**
  - `mapStores` (`this.cartStore.x()`);
  - actions destructured from a store (`const { add } = useStore()`);
  - `createNamespacedHelpers`;
  - `$store.getters['ns/x']` / `$store.state.ns`;
  - modules added with `registerModule`;
  - non-namespaced modules nested under a namespaced one;
  - `@/` imports inside store files (`resolveImportPath` maps `@/` only for `.vue` sources).
- **Pinia store detection is by naming convention:** the hook must match `use…Store` and be imported or defined with `defineStore`.
- **Stale store models are possible.** `files.metadata` merges keys, and the model is written only for JS/TS files whose text mentions `mutations`, `actions`, `getters`, `namespaced` or `modules`. A store root edited until none of those words remain keeps its old model until a forced scan.
- **References are matched to calls by (line, name)**, as in M3-03.
- **Extra parse cost:** a JS/TS file that passes the regex gate is parsed a second time with tree-sitter.
- **Overlap with M3-04:** component ownership is applied only to store references. M3-02's `assignOwners` already covers the rest; M3-04 owns the composable / macro work.

Changelog: Vuex map helpers, `$store.dispatch/commit('ns/NAME')`, in-module dispatch/commit and Pinia `useXStore()` / `store.action()` calls now link to the member in the right store module, by namespace or store import, never to a same-named function elsewhere (M3-05).
