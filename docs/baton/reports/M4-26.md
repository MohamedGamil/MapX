# M4-26 — A symbol whose name contains a dot opens by its exact name

Planned in `iterations/M4-26.md`. Source: `reports/M4-24-R1.md` (follow-up on `Store.getSymbolByName`). Reworked after the independent review (section "Review" below); based on develop `917a8cc`.

## What the parsers produce

In a real scan (temp workspace, `mapx init`/`scan`), `api.get = function () {}` and `obj.method = () => …` produce **no** symbol for the assignment; only `api` and `obj` appear, as constants. Dotted names do come from two shapes:
- **JS string-keyed members.** `export const actions = { 'api.get': (ctx) => fetchJson('/a') }` gives a `method` named `api.get` with scope `actions`, and its call edge has `source_symbol = 'actions::api.get'`. This is the Vuex-action shape from M4-24-R1.
- **Lua.** `function M.foo() return M.bar() end` gives symbols `M.foo` and `M.bar` with no scope, and a call edge `M.foo → M.bar`. This is the shape for callers of a dotted name.

## Lookup rule

`src/core/store.ts` has one private resolver, `findSymbolsByName(fullName, repo, one)`. It replaces the three copies of the split logic in `getSymbolByName`, `getCallersOfSymbol` and `getCalleesOfSymbol`.

- **The scoped reading.** `Scope::name`, or `Scope.name`, is matched by scope: first exactly, then with `.` and `::` treated as the same separator. This is the parent's reading.
- **The exact reading.** A symbol whose own name is `fullName`.
- **`getSymbolByName`** (`mapx node`, MCP `mapx_node`, `/api/symbol`, the impact importer target, context seeds) prefers the scoped match and falls back to the exact name. It returns what the parent returned whenever the parent found something.
- **`getCallersOfSymbol` and `getCalleesOfSymbol`** (and so `callers`, `callees` and `impact`) return the union of the two readings, without duplicates.
- **File extensions.** A name whose last part is a file extension (`Runner.go`) is kept whole only when a scanned file has that path. Otherwise it is split like any other name, and the exact name is still the fallback.

The owner's decision means a collision is resolved toward the class member: when a class `api` has a member `get`, `api.get` opens that member, and `actions::api.get` opens the object member. The docs say so.

## Delivered

- **`src/core/store.ts`:** the resolver above.
- **`src/core/context-builder.ts`:** a seed containing `.` or `/` is taken as a file path only when such a file exists. Otherwise it is looked up as a symbol, so `--seeds Server.Start` and `M.foo` now match.
- **`src/core/impact-analyzer.ts`:** the importer check searches for the matched symbol's stored `name`: the whole `api.get` for an exact match, and the last segment for `A::m`, as before.
- **Callers that did not change:** `src/cli.ts` (`node`, `callers`, `callees`, `impact`, `context`), `src/mcp.ts` (`mapx_node`, `mapx_callers`, `mapx_callees`, `mapx_impact`, `mapx_batch`, `mapx_context`) and `src/ui-server.ts` (`/api/symbol`). They all go through the store, so CLI, MCP and the dashboard stay in step.
- **`tests/store-extended.test.ts`:** two new blocks.
  - "dotted symbol names in a real scan (M4-26)" (6 tests) runs a real `mapx init`/`scan` over JS, TS, Go, Lua and Java files, then queries the CLI (`node --format json`, `callers`, `impact --format json`, `context --format json`), MCP `mapx_node` (an in-memory client on `buildServer()`) and the dashboard (`startUiServer`, `GET /api/symbol/…`).

  - Callers of a dotted name are pinned at store level because the scan's Lua call edge is unreliable under load (see Finding).
- **Docs (outside affectedFiles):** `docs/cli-reference.md` (`mapx node`) and `docs/mcp-integration.md` (`mapx_node`) describe the rule and the collision case.

## Finding (outside this task): the scan sometimes loses Lua call edges under CPU load

I ran a workspace of 8 files (JS, TS, Go, Lua, Java) through a fresh `mapx init`/`scan`, 12 times per run:

| Conditions | Scans with the `src/m.lua` edge `M.foo → M.bar` |
| --- | --- |
| Load average about 6 | 12/12 |
| One process under synthetic CPU load (20 busy threads) | 7/12 |
| 7 probe files in parallel (load average 37–39) | 6/84, 15/84 and 41/84 in three runs |

- In every scan the symbols were identical (`M` constant, `M.foo` and `M.bar` functions), and every other file's edges were present: Go, JS and TS were stable.
- Forcing `MAPX_PARSE_WORKERS=4` at low load did not reproduce it (12/12), and neither did an incremental `mapx update` after an edit.
- The scanner has no time-based logic, so this looks like an async ordering race between parsing and resolution. I did not localise it, and it is not fixed here. It needs its own task and a fixture.

## Limitations

- `api.get = function () {}` and `obj.method = () => …` produce no symbol in a JS scan, so nothing named `api.get` exists for them to open. This is a parser gap, not a lookup one, and it is not registered.
- On a collision, `api.get` opens the class member, as the owner decided; `actions::api.get` opens the object member. `actions.api.get` (scope and dotted name joined by `.`) is not resolved.
- Because the readings are unioned, callers and callees of a colliding name include those of both symbols (here, `Server.Start` has 2 callees).
- A name that ends in a file extension is now split unless a file of that path exists. If some symbol were named `X.ts` and a class `X` also had a member `ts`, `X.ts` would open the member. No such case is known.
