# M5-23-R1 — An unreadable go.mod keeps the module's own imports internal

Date: 2026-11-03. Base: `develop@0628819`. Owner: lane agent. Iteration: `docs/baton/iterations/M5-23-R1.md`. Source: `reports/M5-23.md`, limitation "An unreadable go.mod".

## Delivered

- **The module path of an unreadable go.mod, from the folder layout** (`goModuleByLayout`, `src/core/manifests/go.ts`).
  - Each import `M/rel` of the module's Go files votes for `M` when `rel` is a package folder of the module (a folder with non-test `.go` files, relative to the go.mod's folder). `cmd/main.go` importing `example.com/app/internal/store` with an `internal/store/` folder votes for `example.com/app`.
  - **Strong evidence only (review):** a path is inferred when exactly one candidate has votes, from imports of at least two distinct folders. Any competing candidate, a single folder, or no vote gives no module path, and the imports stay unknown rows as before M5-23-R1. So `github.com/google/uuid` with a `uuid/` folder, or `k8s.io/api` with `api/`, never makes its prefix the module.
  - The imports of every non-test Go file of the file set vote, so a go.work member is voted for by the members importing it. The package folders are the module's own: folders under a nested go.mod are another module.
  - A standard-library path never votes (`net/http` and an `http/` folder do not make `net` a module). A dotless module path (`module app`) can win.
  - `goImportPaths` reads a Go file's import paths with a small tokenizer (single, aliased, dot, blank and block imports; comments, strings and raw strings skipped).
- **Resolution** (`src/core/import-resolvers.ts`): `goModuleIn(dir, ctx)` gives a folder's module path, either from go.mod's `module` line or, when go.mod is there but unreadable, from the layout. It is cached per file set and folder. `resolveGoImport` and `goImportInWorkspaceModule` use it.
  - An own package resolves to its folder, which gives an import edge and no candidate decided external.
  - A missing own package (`example.com/app/internal/gone`) is the workspace's, so it gives no row.
  - Third-party modules stay unknown rows, flagged `manifest` (M5-23 behaviour).
- **go.work members** whose go.mod cannot be read get the same inference (review).
- **A sync input** (review): `configReferrers` signs an unreadable go.mod with the module path its layout gives over the Go files as they stand, so an import that changes it re-parses the module's files, as `scan --force` would.
- **The resolver context** gains an optional `exists(path)` (`ImportContext`). `src/core/scanner.ts` passes it in its two resolver contexts (`importContext`, `resolveModuleImport`) through `workspaceExists`, which is cached per resolution phase beside the text cache and cleared with it. No call-extraction code changed.
- **Extractor version 18** (`src/core/extractor-version.ts`; 16 before the rebase, as develop's M2-12 and M2-13 took 16 and 17): under an unreadable go.mod, the import edges of unchanged Go files change, so an index built before re-parses once.

Files beyond the task's `affectedFiles` (`src/core/manifests/go.ts`, `src/core/import-resolvers.ts`, `tests/external-refs.test.ts`): `src/core/scanner.ts` (`exists` in two contexts, `workspaceExists` and its cache) and `src/core/extractor-version.ts`.

No CLI or MCP surface changed. No schema change. No new dependency.

## Limitations

- **No evidence, no inference.** A module that imports none of its own packages, or whose own and third-party imports tie, keeps its own imports as unknown rows, as M5-23 did. MapX never guesses from the repository folder's name.
- **Only non-test files vote.** Imports that appear only in `_test.go` files do not count.
- **The `replace` directives of an unreadable go.mod** cannot be read, so a module it replaces with a local folder is external, not the workspace's.
- **The attribution of third-party rows is unchanged:** they are unknown and flagged `manifest`, because the build list is unreadable.
