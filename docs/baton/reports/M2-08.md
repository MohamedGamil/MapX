# M2-08 — Calls resolve through the file's own imports before name lookup

Date: 2026-11-01. Base: `develop@e1d5da0`. Owner: claude. Iteration: `docs/baton/iterations/M2-08.md`.

## Delivered (`src/core/scanner.ts`, `src/core/store.ts`)

- **`importBindings(file)`.** The names a file binds to project modules, read per phase from the file's text, with comments and Python docstrings stripped.
  - JS/TS and the scripts of `.vue`/`.svelte` files:
    - named imports, aliases, default imports and `* as ns`;
    - `require` with destructuring renames, and `require` namespaces.
  - Python:
    - `from m import a, b as c`, including parenthesised multi-line lists and relative modules;
    - `from pkg import submodule`;
    - `import m.n [as x]`.
- **`resolveImportedCall`.** For a call or instantiation, the bound module's declaration:
  - JS: a bare name's named or default binding, or a receiver's namespace binding.
  - Python: the dotted receiver read from the call's line, or a bare name.
  - When it does not apply:
    - A declaration in the file that is visible at the call shadows the import. That means a module-level declaration (such as a later top-level `def`) or a function nested in the caller's enclosing function.
    - A Python line with both `x.f(` and a bare `f(` is ambiguous, so it falls back.
    - An imported value symbol (a literal constant) gives no edge (M0-17-R2).
    - When the module or export is not found, name lookup applies as before.
- **`findExport`.** It finds a top-level declaration, or follows `export { a [as b] } from`, `export *`, `export { a }` of an import, and a package `__init__.py`'s imports, to depth 5. It is memoised per phase per file and name, which also guards against cycles.
- **Sync.**
  - `importerReferrers` re-parses the importers of every changed JS/TS/Python module, and the importers of each barrel above them up to five levels, in all three paths: full incremental, git sync and hash sync.
  - The new `Store.getImporters` is limited to import and require edges, so a module's callers are not re-parsed.
  - The test mocks gain `getImporters`.

## Independent review

One fresh agent reviewed the change in its own copy. It confirmed that the tests discriminate (6 of 7 fail on the old scanner) and that the self-scan changes are corrections. It also confirmed the handling of `import type`, multi-line clauses, `export { default as X }`, `.d.ts` files, Vue with two script blocks, Svelte, imported-class instantiation, the Vue and M0-17-R4 ordering, and the per-phase caches.

Findings, all fixed with a regression test:
- **P1: sync diverged from a fresh scan** when a barrel or imported module changed but its importer did not. Fixed with `importerReferrers`.
- **P1: `findExport` fanned out exponentially** through `export *` (19.7 s and 21.6 s). Fixed with memoisation and a cycle guard (3.6 s and 2.8 s).
- **P2s:**
  - commented-out imports bound;
  - two same-named calls on one Python line;
  - shadowing by a nested or later declaration;
  - Python lines re-split and regexes recompiled per call;
  - an unescaped name in one regex;
  - test gaps, including `.vue`/`.svelte`, which went back into the criteria.

## Limitations

- **Calls on objects** (`self.x()`, `obj.m()`, `this.x()`) are unchanged. Type-directed method resolution is not planned.
- **Python receivers** are read from the call's line. Two same-named calls on one line with different bindings keep name lookup.
- **Only JS/TS/Vue/Svelte and Python** resolve through import bindings. Other languages keep their existing rules.
- **Sync cost.** Changing a module re-parses its importers, and the importers of barrels above it.
