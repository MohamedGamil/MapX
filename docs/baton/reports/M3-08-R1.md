# M3-08-R1 — Vue app boundary: one global registry and route table per app folder, whatever the root manifest lists

Date: 2026-10-31. Base: `develop@00407d6`. Owner: maintainer. Iteration: `docs/baton/iterations/M3-08-R1.md`.

## Reproduction (before any fix)

The new tests failed on the unmodified scanner, with these results:

- **Root lists `vue` or only `vue-router`:** `apps/b/src/App.vue` renders `apps/a/…/OnlyA.vue`.
- **Two apps:** `shop/src/Nav.vue` navigates to `admin/src/views/Reports.vue`, by name and by path, which gives 4 navigate edges instead of 2.
- **`backend/` beside `frontend/`:** `frontend/src/Nav.vue` navigates to `backend/tools/views/AdminPanel.vue`.
- **Two registrations of `Btn`:** the winner changed after a sync.

## Delivered

- **`src/core/scanner.ts`:**
  - `vueScope` gives the nearest folder holding a `package.json`, up to the repo folder, cached per resolution phase (`vueScopes`).
  - `vueRouterActive` checks that vue-router is active for the repo or for the file's M3-07 scope. If detection has not run in the phase, nothing is ruled out.
  - `resolveNavigation` builds one route table per repo and app folder, from files where vue-router is active.
  - `vueGlobalComponents` reads registering files in path order.
- **Docs:**
  - `docs/cli-reference.md` (scan, Vue global components);
  - `docs/framework-integration.md` (detection paragraph);
  - `CHANGELOG.md`: the M3-08 entry's "except when the root…" qualifier is removed, and a new M3-08-R1 entry is added.

## Limitations

- **Every `package.json` is an app boundary.** That includes a `{"type": "module"}` marker or a component-library package inside an app: a library package's own `.vue` files then do not see the app's global registrations. M3-09-R1 treats `package.json` folders the same way for aliases.
- **Re-parse set.** `vueRegistryReferrers` still decides per repo which unchanged files to re-parse. It may re-parse a file of another app folder that uses the same tag, which costs a parse but gives the same edges.

Final review round (reviewer I), P2s fixed:
- **`main` made an app a library.** An app with `"main"` (as `npm init` writes) became a library, so a shop app navigated into the admin app.
- **An internal package became an app.** A package with a name and dependencies but no `main` or peer dependency was an app, which hid its plugin registrations.
- **Fix.** Classification follows the build: a folder with a bundler config, or with a bundler or dev server among its dependencies, is an app; any other named package is a library.
- **Tests.**
  - The navigation test's shop app now has `main`.
  - The library test runs for both a published library and an internal package.
  - Mutations "main makes a library" and "named package is an app" each fail a test.
  - App fixtures in the Vue and HTTP tests now list their build tool (vite or @vue/cli-service), as real apps do.

Review of the previous round's fixes (reviewer M). The library and importer-scope fixes were checked, and a manifest-kind change re-scopes correctly in git and hash modes. Fixed:
- **P1, importer scopes on sync.** Adding or removing another app's registration of a `.vue` file did not re-parse that file, so sync ≠ `scan --force`.
  - **Fix.** Importer scopes count registered components only, and a component whose registration a changed file adds or removes is re-parsed.
  - **Test.** "follows a component that another app starts or stops registering, on sync as scan --force". The mutation fails it.
- **P2, library-mode detection.** Any `lib:` key in a bundler config (such as an alias) counted as a library build.
  - **Fix.** `isLibraryBuild` looks only inside the `build: { … }` object.
  - **Test.** "keeps an app an app when its vite config merely has an alias named lib". The mutation fails it.

The importer scope is not transitive; this is documented in D017.
