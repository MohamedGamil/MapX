# M2-08-R11 report: a bare import resolves under the module roots a project configures

Spec: [iterations/M2-08-R11.md](../iterations/M2-08-R11.md). Started from `develop@0bed26b`; the change is uncommitted at the time of writing.

## Cause (reproduced before the fix)

The M2-08-R6 reviewer's cases G, J and K were scanned with the real CLI on the working tree and on `3afa180` (the commit before M2-08-R6, extracted with `git archive`) as the oracle:
- **G** (jest `moduleDirectories: ["node_modules", "<rootDir>"]`): `3afa180` had the import edge and the call edge; the tree had only a by-name call edge, no import edge, and an `npm` `external = 1` candidate for `services/api`.
- **J** (type-only, constant and side-effect imports): `3afa180` had 5 import edges (3 files); the tree had none, and 6 `external = 1` candidates (`models/user`, `components/Btn`, `config/settings`).
- **K** (`NODE_PATH=. node main.js`, colliding `save` / `find`): `3afa180` had 3 import edges and the calls `find` -> `models/post.js`, `save` -> `models/user.js`; the tree lost them, and all 10 rows were `npm` `external = 1`.

`resolveImportPath` had no source of module roots: a bare specifier named a package whatever webpack, jest or `NODE_PATH` said. `jsExternalSpecifier` calls the same function, so an unresolved specifier was also an external candidate.

## Delivered

- **`jsModuleRootTargets`** (`src/core/js-aliases.ts`): the module paths a bare specifier may name under the roots configured for the importing file. Sources, read statically, each applying to the files under the folder that declares it, the nearest declaration of its kind winning:
  - webpack `resolve.modules` (`resolve: { modules: [...] }`, `resolve.modules = [...]`, `.push(...)` / `.unshift(...)`) in webpack.config.{js,cjs,mjs,ts,mts,cts}, webpack.{common,dev,prod}.js, vue.config.{js,cjs}, webpack.mix.js, craco.config.{js,cjs,ts}, next.config.{js,mjs,cjs,ts}. Entries: a string is a folder name searched in every ancestor of the importing file (inside the declaring folder); `__dirname`, `path.resolve(__dirname, 'src')`, `path.join(...)`, `path.resolve('./src')` are one fixed folder; `'node_modules'` (or a `...spread`) is the marker. `resolveLoader.modules` is not read.
  - jest `moduleDirectories` and `modulePaths` from the package.json `jest` key, jest.config.json, and the literal values of jest.config.{js,ts,mjs,cjs,mts,cts} (`<rootDir>` substituted, a literal `rootDir` honoured, scope = the rootDir). `roots` is not read: jest-resolve builds its lookup paths from `moduleDirectories` and `modulePaths` only; `roots` says where tests are found. A JS/TS config text containing `projects:` is skipped.
  - `NODE_PATH=` in a package.json script, `:`-separated, relative to the package (`NODE_PATH=. node x`, `cross-env NODE_PATH=src:./shared jest`, `export NODE_PATH=...`, leading `$PWD/`); other variables, absolute and Windows paths are skipped.
- **Precedence** (`resolveImportPath`): `paths`, aliases, `baseUrl` (unchanged) -> roots listed before `node_modules` -> workspace packages -> roots after `node_modules`. Justification: Node searches `NODE_PATH` after `node_modules`, jest's `modulePaths` after its `moduleDirectories` chain, a webpack list in order; a workspace package is a `node_modules` symlink, so it wins over a late root and loses to a root listed first. A late root is also skipped when `node_modules` supplies the name (`isNpmPackage`: a listed or installed package) and for a Node built-in (`nodeBuiltin`), for every root.
- **External candidates and the M2-08-R3 gate:** no change needed. `jsExternalSpecifier` and `outsideProject` call `resolveImportPath`, so a resolved specifier is `external = 0` and counts as project; the e2e tests assert no `external = 1` row for any resolved specifier.
- **Sync:** `configReferrers` hashes `MODULE_ROOT_CONFIGS` too (jest and extra webpack-family names; package.json was already hashed), so editing, adding or removing such a config or a NODE_PATH script re-parses the files below it. A bare import that resolves nowhere is recorded as unresolved against its root paths (M2-08-R2), so a module added under the root later re-parses its importers.
- **Review fixes (2026-11-04):**
  - **List elements MapX cannot read** (a spread of jest's `defaults`, a call, a variable, a `${}` template) stand for `node_modules` in a jest `moduleDirectories` and a webpack `resolve.modules` list, so the roots after them are searched after `node_modules` and never beat a listed package. A list followed by `.concat(...)` or `+ ...`, and a list given by a variable, is ignored.
  - **The nearest jest or webpack config decides** even when it declares no root (`nearest` in `jsModuleRootTargets`); NODE_PATH still comes from the nearest script that sets it.
  - **Only top-level keys are read:** jest `globals: { moduleDirectories }`, webpack `externals: { resolve: { modules } }` and a jest key set in two top-level objects give no roots; a jest `projects` config (text or object) declares none.
  - **Cost:** `isNpmPackage` is memoized per folder and package (and package.json parsed once per folder, `manifestAt`), root discovery and the roots of each (folder, specifier) are cached, a late root is not probed or recorded as unresolved for a name `node_modules` supplies, and the early roots are recorded only for what a later file could change.
- **`EXTRACTOR_VERSION` 27.**
- **Tests:** 18 new e2e tests in `tests/import-bound-externals.test.ts` (two `describe` blocks, 82 tests in the file; one workspace of small per-config apps, plus a per-test sync workspace) and 4 cases in the `DECIDED_ELSEWHERE` table of `tests/external-refs.test.ts` (jest config added, webpack config added, NODE_PATH script added, NODE_PATH script removed), each checked sync equal to `scan --force` on the git sync, hash sync and full-scan variants.

## Limitations

- **Not read, no task opened:** Deno `deno.json` import maps (an alias form, not a module root), `.env` `NODE_PATH` (create-react-app before 4), Dockerfile `ENV NODE_PATH`, jest `moduleNameMapper`, babel `module-resolver`, a jest or webpack config in a non-standard path, built from variables or functions, jest `projects` (skipped), a webpack `resolve.modules` entry that is an absolute path or a variable. Suggest follow-ups if wanted.
- **Order is by list position:** jest's ancestor-by-ancestor interleaving of `moduleDirectories` is not modelled; an entry counts as before or after `node_modules`. A webpack config with several webpack-family files in one folder (webpack.config.js and vue.config.js) takes the union.
- **Scope:** a nearest declaration of each kind wins (a nested package with its own jest key and no module roots hides an outer jest config's roots, as jest projects are separate). A webpack folder-name root is looked up in ancestors inside the declaring folder only, narrower than webpack, which also looks above it. A root `NODE_PATH` in a monorepo root script governs every file below it.
- **Late roots and installed packages:** `isNpmPackage` looks at the enclosing package.json files and a physical `node_modules`; a package installed hoisted at a path outside those is not seen, so a late root could win over it.
- **Sync and a higher-priority root added later (inherited, review P2-4):** `NODE_PATH=src:lib` with `lib/x.js` linked, then `src/x.js` added: `scan --force` links `src/x.js`, sync keeps `lib/x.js`. HEAD behaves the same for tsconfig `paths` arrays (`targets` lists). Only an unresolved import is recorded, not a lower-priority resolution.
- **`cd sub && NODE_PATH=. node x`** applies to the whole package, not `sub`.
- **A webpack config whose `resolve` sits under a key other than `configureWebpack` / `configure`** (a config written as a function returning a wrapper, say) is not read; a jest key set in two top-level objects is ignored.
- **Unconfigured projects keep the M2-08-R6 effect:** `models/user` in a project with no root config is still an `npm` `external = 1` candidate (the unknown rule, M2-08-R3); the task only changes configured roots.
- Found, not fixed: the default `.mapx` exclude patterns (`**/*.test.ts`) drop `*.test.ts` files from the index unless `--no-suggestions` init is used, so a jest `.test.ts` importer is not indexed by default; unrelated.
