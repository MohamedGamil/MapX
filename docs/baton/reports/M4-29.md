# M4-29 report — The installer replaces a running mapx binary

Base: develop@ec44845, on top of M4-28-R1 and M4-28-R2. Changed: `scripts/templates/install.sh` and `scripts/templates/install.ps1`. New: `tests/installer-replace.test.ts`.

## Cause

`install.sh` installed the binary with `cp "$binary" "$PREFIX/mapx"`. That opens the existing file for writing. Linux refuses to write to an executable that a process is running (ETXTBSY), so the install failed while `mapx serve` ran the old binary (D037).

## Delivered, per acceptance criterion

**AC — with a process executing the installed binary, `install.sh --prefix <tmp> --force` exits 0, the new binary is in place, and the running process keeps working. Met.**

- **install.sh:** `mktemp "$PREFIX/.mapx.XXXXXX"` creates a temp file in the target folder. The binary is copied to it, `chmod 755`, then `mv -f` renames it over `$PREFIX/mapx`. The rename is atomic within one filesystem. Running processes keep the old inode, which is freed when they exit. If a step fails, the temp file is removed and the installer exits with an error.
- **The test, first case** (`tests/installer-replace.test.ts`):
  - **Setup:** the "installed binary" is a copy of the system `sleep`, a real ELF. A shell script would not reproduce ETXTBSY, because the kernel execs `/bin/sh`, not the script. The new binary is a small shell script.
  - **Run:** the old binary runs as `<prefix>/mapx 4`, and `bash install.sh --prefix <tmp>/bin --force` runs alongside it.
  - **Asserts:** exit 0 and no "Text file busy". The new content is in place, executable, and prints its version. The folder holds only `mapx`, so no temp file is left. The old process is still running after the install, then exits normally (code 0, no signal).
  - **Isolation:** `HOME` is set to a temp folder, and the prefix is put on `PATH`, so `add_to_path` edits no real shell config. The test never touches `~/.local/bin` or the real install. It is skipped on Windows.
- **The packaging path, second case.** The test packs `install.sh`, `VERSION` and the fake binary into a tar.gz. It runs `scripts/make-installer.sh sh` on it, which is the real packaging step that embeds install.sh, without bun-compiling. Then it runs the resulting self-extracting installer with `--prefix <tmp>/bin2 --force`, with the same old binary running and the same assertions.
- **install.ps1 (Windows): changed, not run.**
  - **The problem:** Windows has the same problem in another form. It refuses to overwrite or delete a running `.exe`, so `Copy-Item … -Force` fails, but it allows renaming one.
  - **The change:** the old `mapx.exe` is moved aside as `mapx.exe.<guid>.old`, then the new one is copied in. If the copy fails, the old one is moved back. Then every `mapx.exe.*.old` that can be deleted is removed, and the ones still running are left for the next install.
  - **Not run:** this machine has no `pwsh`, so the change is untested. Uninstall on Windows still fails while mapx.exe runs, which is out of scope.

## Review 1 (integration owner, 2026-11-03)

The replace moved into `install_binary` in install.sh. Every fix below has a test in `tests/installer-replace.test.ts`, which now has 7 tests.

- **P2, fixed: a symlinked `mapx`.** `mv` replaced the link with a regular file, and the old binary stayed at the link's target.
  - `resolve_link` resolves the link first: with `readlink -f` where it exists, else one link at a time, relative links included.
  - The real file is then replaced in its own folder, so the link stays and points to the new binary.
  - Tested with `readlink -f`, and with a shimmed `readlink` that refuses `-f`, as older macOS's does. A running process at the real path keeps working.
- **P2, fixed: Ctrl-C.** EXIT, INT and TERM traps remove the temp file while the replace runs; INT exits 130 and TERM exits 143. The traps are reset after the rename.
  - Tested with SIGTERM and SIGINT. A shimmed `chmod` holds the install while the temp file exists, then the signal is sent; the prefix is left empty.
- **P2, fixed: a folder that cannot be written.** When `mktemp` fails in the target's folder but the target file is writable, the installer warns and overwrites it in place with `cp`, as before M4-29. Otherwise it stops with "Cannot write to <dir>".
  - Tested with a 0555 folder holding a 0755 binary. The test is skipped as root, because root can write anywhere.
- **P2, fixed, not run: install.ps1 uninstall.** It also removes the `mapx.exe.*.old` files earlier installs moved aside; one still running stays until it exits. There is no PowerShell on this machine, so this cannot be tested here.
- **Mutations:** each fails its test, then the suite passes once restored (7/7):

  - no traps fails both signal cases;
