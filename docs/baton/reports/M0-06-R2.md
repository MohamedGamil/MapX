# M0-06-R2 — The compiled binary parses on worker threads

## Defects

1. **The worker was never in the binary** (owner report, 2026-11-01, installed `v0.3.7` binary). Every scan of more than 10 files printed `[mapx] Parallel parsing unavailable (Cannot find module '/$bunfs/parsers/parse-worker.js'); parsing on one thread.` Two causes:
   - `bun build --compile` was given only `src/main.ts`, in the Makefile, `scripts/package.sh` and `scripts/build-all.ts`, so `src/parsers/parse-worker.ts` was never embedded.
   - The scanner resolved the worker as `../parsers/parse-worker.js` from `import.meta.url`. In a compiled binary that URL is the binary's own module, `/$bunfs/root/<binary>`, so the path pointed one folder above the embedded root.

   The 0.3.0 changelog entry "Standalone Bun Binary WASM Path Fix" fixed WASM asset paths only; the worker was never covered.
2. **One PHP call name broke parallel scans at scale** (found verifying 1 on a copy of a 3,481-file Laravel project; Node and the binary alike).
   - **Cause:** `src/parsers/languages/php.ts` looked up a call's short name in a plain-object facade map. `$x->toString()` read `Object.prototype.toString`, a function, and made it the reference's target. `valueOf` and `constructor` did the same.
   - **On the main thread:** the call was silently dropped.
   - **On a worker:** `postMessage` threw `DataCloneError`, the worker failed, and the whole scan fell back to one thread. Node printed `Parallel parsing unavailable ()` with an empty message; the binary printed `(The object can not be cloned.)`.

## Delivered

- **Build:** every `bun build --compile` (5 Makefile targets, `scripts/build-all.ts`, `scripts/package.sh`) names `./src/parsers/parse-worker.ts` as a second entrypoint. Bun embeds it at `<root>/parsers/parse-worker.js`.
- **`parseWorkerUrl` (`src/core/scanner.ts`):**

  | Runtime | Worker module |
  | --- | --- |
  | Source | `src/parsers/parse-worker.ts` |
  | npm build | `dist/parsers/parse-worker.js` |
  | Compiled binary (`/$bunfs/`, or `~BUN` on Windows) | `./parsers/parse-worker.js` beside the binary's module |

- **PHP facade lookup:** checks own keys only (`Object.hasOwn`), and only a string resolves.
- **Worker hand-back:** a parse that throws, or a result a worker cannot post, is reported for that file (`retryOnMainThread`). The main thread parses only those files once the workers finish.
- **Fallback warning:** names the error's `name` when its `message` is empty.
- **Hand-back warning:** a hand-back is reported once per scan as `[mapx] N file(s) parsed on the main thread: a worker could not return them (<first file>: <error>)`. A test hook, `MAPX_TEST_WORKER_FAIL=<repo-relative path>`, makes a worker fail that one file.
- **Same lookup bug elsewhere** (from the review): `src/parsers/languages/vue-stores.ts` (`CALL_KINDS`, `MAP_HELPER_KINDS`) and `src/frameworks/detectors/laravel-mounts.ts` (`IRREGULAR`, `PATH_HELPERS`) now look up own keys only.
- **Packaging gate:** `scripts/package.sh` `package_tarball` smoke-scans every packaged binary this machine can run, whether built by `make` (`--skip-build`) or by the script.
  - It scans 13 files, with `MAPX_TEST_WORKER_FAIL=f1.ts`.
  - The build fails on the one-thread fallback warning. It also fails when the hand-back line is missing, which means no worker ran.

## Independent review (fresh agent, 2026-11-01)

The reviewer confirmed:
- the binary scans on workers with the test's build command and with `package.sh`'s, and also under `bun src/main.ts` and node+tsx;
- the smoke check fails on a binary without the worker, and cleans up after itself;
- Bun and Node both throw `DataCloneError` synchronously from `postMessage`, so the worker's catch works in both;
- the retry counts progress once, and maps results back by index.

The reviewer could not test the Windows `~BUN` URL.

Findings:
- **P1, fixed:** `vue-stores.ts` `CALL_KINDS[...]` and `MAP_HELPER_KINDS[...]` read `Object.prototype` members. A Vuex hint plus `x.hasOwnProperty('a/b')` produced a store reference whose `kind` was a function. With the hand-back it was retried silently; without it, it failed the parallel scan. Fixed, with a test.
- **P1, fixed:** the hand-back had no test, and retries were silent. They now print a warning, and a test drives the path through the hook.
- **P2, fixed:** `laravel-mounts.ts` `IRREGULAR[lower]` threw for `Route::resource('constructor', …)` and lost every route of the file; `PATH_HELPERS` used `in`. This was an existing main-thread bug. Fixed, with tests.
- **P2, fixed:** the smoke check only looked for the warning text, so a binary that never started workers would pass. It now requires the hand-back line that only a worker scan prints.

## Measurements (local, 16 cores)

The corpus is a scratch copy of a private 3,481-file Laravel project. It was used only for measurement; it is not a fixture and is not committed.

| --- | --- | --- | --- | --- |

| Binary, before | `--no-parallel` | 36.9 s | 2.06 GB | same |
| Binary, after | parallel | 25.5 s | 3.78 GB | identical to `--no-parallel` |

| Node 26 source, after | parallel | 38.9 s | — | identical to the binary |

- **Installed layout:** the new installer, installed with `--prefix` into a scratch folder, scanned the corpus on workers with `env -i` (no Node, no `HOME`) in 33.9 s, with an identical index. Another job was running at the same time.
- **MapX's own sources** (378 files): the binary gave an identical index on workers and on one thread, in about 6 s either way.

## Limitations

- Eight workers each load every grammar, so peak memory on the large corpus rises from about 2.0 GB to 3.8 GB.
- The installed `~/.local/bin/mapx` is still the `v0.3.7` build. A new version (owner decision, D007) is needed to ship this fix.
