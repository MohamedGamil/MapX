## Delivered

### Scope per manifest folder

`src/core/scanner.ts`:

- `vueScope(repo, path)` returns the M3-07 folder of the `vue-router` detector that contains the file; that detector's `manifestDependencies` list `vue`. It returns `''` when Vue is active for the whole repo, or when the file is in no such folder.
- `vueGlobalComponents(sourcePath, fileMap)` is now keyed by (repo, scope). It reads only the registrar files and `.vue` files of the source file's scope.
- The glob-folder match moved to `vueGlobFiles` (`vue-template.ts`) and is shared with the sync check.

### Re-link on sync and plain scan (global registry and route table)

This reuses the M0-02-R4 mechanism:

- the record is kept in `meta`;
- a referrer set computed before the parse is merged into each scan path's existing re-parse set;
- the record is settled only after the parse completes.

Details:

- **`meta vue_registry:<repo>`** holds, for each JS/TS file that has any, what it contributes to Vue resolution:
  - its `globalRegistrations()` output;
  - its `routeRecords()` output, without line numbers, so moving a record inside its file re-targets nothing.
- **`vueRegistryReferrers(repo, files, deleted)`** runs next to `movedReferrers` in all three paths (`_scanFullForRepo`, `_scanIncrementalForRepo`, `_scanIncrementalByHash`). It applies the new or changed files' text and the deletions to the record, then works out what changed:
  - `changedGlobalNames` (`vue-template.ts`) gives:
    - each named entry added, removed or retargeted;
    - the `.vue` files under the old and new folders of a changed glob;
    - each `.vue` file added to or deleted from a glob folder.
  - `changedRoutes` (`vue-navigation.ts`) gives:
    - each route record added, removed or changed (name, path, component, redirect);
    - the records whose redirect reaches a changed record, up to 4 hops, as `matchRoute` follows.
- **Who is re-parsed.** Only these unchanged files of the repo:
  - `.vue` files whose tags name a changed component (`usesTag`);
  - `.vue` files and JS/TS modules (stores, guards, composables, which M3-11 made callers) whose navigations a changed record may answer. `navigatesTo` runs `navigationReferences` or `moduleNavigationReferences`, then M3-06's name/path/pattern candidates.

  No other file is re-parsed, and none at all when nothing changed. The texts are read only in a scan where something changed; JS/TS modules are read only when a route record changed.
- **`settleVueRegistry`** stores the new record after the parse. If the scan is aborted, the old record stays, so the next scan repeats the comparison.
- **No record yet** (a first scan, or an index built before this task): the record is built from the current text and stored at once. On a first scan, every file is already being parsed, so nothing extra is read.
- **Footprint.** The scanner changes are small hooks:
  - one referrer line in each of the three paths;
  - a settle call in each path;
  - the `deletedPaths` hoist in the full scan;
  - the scoped registry.

  The pure logic sits at the end of `vue-template.ts` and of `vue-navigation.ts`.

## Limitations

- **Root manifest plus nested apps.** If the root `package.json` also lists `vue`, M3-07 reports the detector as active for the whole repo, so the registry is whole-repo too.
- **Route table scope.** The route table itself stays per repo, matched by directory nearness (M3-06). This task does not scope it by manifest folder; the criteria ask for that only for the registry.
- **Users are found by text.** Finding users reads every indexed `.vue` file of the repo, but only in a scan where a registration or route record changed. When a route record changed, it also reads every JS/TS module. The matches over-approximate:
  - a `<X` in a script or comment re-parses that file;
  - a caller whose path matches a changed record by pattern, while a more specific unchanged record wins, is re-parsed;
  - the same applies to files in another app folder.

  No scope filter is applied, because scopes are not known before the parse in every path.
- **Not covered.** A route component's import target moving while the router file stays unchanged is left to M0-02-R4's moved-target ledger: the component symbol name is recorded.
- **Upgraded indexes.** For an index built before this task, the first sync records the current state as the baseline. A change made in that same sync is not re-linked; any later change is.
- **Unchanged from M3-02.** `<component :is>`, barrel re-exports, Nuxt auto-imports and root-absolute globs are still not handled.

## Finding outside this task

Git sync does not notice a working-tree edit that is reverted to HEAD's content.

- **What I saw.** My first version of the git variant made uncommitted edits. After `main.js` was restored to its committed content, `sync` did not re-parse it, and the UserCard edges stayed.
- **Why, as I read it.** `git diff <last_scan_commit>` lists nothing for a file whose content equals HEAD again. The stored blob id is that of the edited content, but only listed files are compared.
- **What I did.** The test now commits each edit. I did not investigate further.
- **Possible remediation.** Compare the stored `git_blob_hash` of indexed files that are not listed with HEAD's blob.

Changelog: `scan` and `sync` now re-link Vue render and navigate edges when a global component registration (`app.component`, `Vue.component` or an auto-registered folder) or a Vue Router route record changes, without re-parsing unrelated components, and each app folder with its own `package.json` keeps its own global registry (M3-08).
