# M2-08-R8 report: sync re-resolves Java and Python importers when an imported project package goes away

Spec: [iterations/M2-08-R8.md](../iterations/M2-08-R8.md). Started from `develop@2f33090`; the change is uncommitted at the time of writing.

## Cause (reproduced before the fix)

Probe workspace (hash mode, and git mode after a commit): `com/acme/Invoice.java`, `com/thirdp/Marker.java` (`package com.thirdp`), `com/use/Use.java` with `import com.thirdp.Invoice;` and `new Invoice().total()`.
- `scan`: `com.thirdp` is a project package, so the import of the missing `Invoice` is unknown and links by name: `Use::run call total` and two `instantiation Invoice` edges into `com/acme/Invoice.java`.
- Deleting `com/thirdp` and running `mapx sync`: "0 symbols updated, 0 edges updated"; the three edges stay.
- `scan --force`: no edge.

(A first probe with `thirdp/Invoice.java` itself deleted did not reproduce: the edge into a deleted file goes with it, and the importer's other edges were not wrong.)

The outside decision of M2-08-R5 reads three things in other files: a file at the import's path (`resolveJvmImport`), a folder of JVM sources for its package (`javaImportOutsideProject`), and a file declaring that package with that class, whatever its folder (`jvmProjectDeclares`). Python's rule reads whether a folder or module of the top-level name exists anywhere (`pythonNameInProject`). Sync re-parsed an importer only through edges (`importerReferrers`, JS/TS and Python modules), the removed-file record, or `unresolvedImports` (JS/TS), none of which sees these reads.

## Delivered

- **A record per parse** (`files.metadata`, `importDecisionMetadata` in `src/core/scanner.ts`):
  - `jvmDecl` for every JVM file (`java`, `kt`, `kts`, `scala`): its `package` and declared type names;
  - `jvmImports` for a Java file: the dotted names of its single-type and static imports;
  - `pyImports` for a Python file: the top-level names of its absolute imports that no indexed file satisfies, star imports (`from x import *`) included.
- **Referrers** (`importDecisionReferrers` for added and edited files, `importDecisionReferrersOf` for the metadata lookup, one pass per kind, none when no JVM or Python file changed). The keys (`ImportDecisionKeys`) are:
  - `stems`: the dotted trailing runs of a JVM file's path without extension (the file of a class);
  - `folders`: the dotted trailing runs of its folder, **only when the folder or path run is new or lost**, judged against an `ImportDecisionBaseline` read lazily from `Store.getJvmAndPythonPaths()` (for a removal, the removed paths are left out), so a file added beside others, or deleted from a busy package, adds none;
  - `types`: the qualified names of the types a JVM file declares, gained or lost (a removed file's from its stored `jvmDecl`; an edited file's difference of old and new; a body edit has none);
  - `pyNames`: the folder and module names of a Python file that no remaining Python file has.
  - A Java importer is re-parsed when a recorded import's own or one-up name is a stem (drops 0 and 1), its one- or two-up name is a folder key (drops 1 and 2: a class's package, a static member's), or a prefix of it, outer classes included, is a type key (`jvmImportAffected`). A Python importer is re-parsed when a recorded top-level name is a name key.
- **Wiring:** deletions in `removeFiles` (the removal queue, seen by hash sync, git sync and `scan`); additions and edits beside `newModuleReferrers` in `_scanFullForRepo` (a plain `scan .`), `_scanIncrementalForRepo` (git sync) and `_scanIncrementalByHash` (hash sync).
- **Helpers** in `src/core/import-resolvers.ts`; `javaExternalBindings` and `jvmPackageOf` share `javaImportStatements` and `jvmPackageIn`; `Store.getJvmAndPythonPaths` in `src/core/store.ts`.
- **JSON export** (`src/exporters/graph-exporter.ts`): `jvmDecl`, `jvmImports` and `pyImports` are removed from a file's exported `metadata` (about 0.78 MB of records on the 3000-file probe); the other keys, `unresolvedImports`, `exportSig` and the rest, are unchanged. No other consumer reads them: the file metadata is only read by name elsewhere (scanner, arch, MCP/CLI edges read edge metadata).
- **`EXTRACTOR_VERSION` 29:** the records are new, so an older index re-parses once.
- **Tests:** in `tests/import-bound-externals.test.ts`, one `describe.each` over git and hash sync, 20 e2e tests (40 runs, the JSON export test included): Java delete, add (folder file, declaring file elsewhere, class added to a file), package edited away and back, declaring file deleted from another folder, move out of the package folder, a file added beside others and deleted (re-parses only importers of that class), static import (package gains a folder; class file added with no package line), nested class through an outer class declared elsewhere, Kotlin file added, Scala file deleted, no re-parse for a body edit or an unrelated package; Python delete and re-create (named and star import), add by folder, by module file, star import, no re-parse for an unrelated file; a plain `scan .` rescan; the JSON export. Each sync case compares the synced edges with `scan --force`.

## Limitations

- Kotlin and Scala importers record no imports: they have no outside gate (M2-08-R5), so a change to a package they import is not re-parsed for. A follow-up when that gate lands.
- An unresolved relative Python import (`from .models import X`) is not re-parsed when its target is added later (`newModuleReferrers` is JS/TS only); the same at HEAD.
- Adding a second same-named declaration does not re-link importers that already link by name; the same at HEAD.
- Adding an absolute module under an existing top-level package (`app/newmod.py` for `from app.newmod import X`) leaves the import edge un-re-parsed: no name flips (`app` exists) and the importer had no edge to the module; the same at HEAD.
- A new project `json.py` re-parses the importers of `json` (a real flip: the import is no longer outside).
- Folder keys re-parse all importers of a deleted package, including those whose class was in a different surviving folder of the same package run; this is a real flip, not over-inclusion. A deleted or added class re-parses the importers of that class even when its package folder survives (types, not folders, stand in for a nested import's class folder).
- A deleted or moved target that resolves to a different file of the same path (closest match changes) is not covered; it is not an outside decision.
- Found, not fixed: with `com/thirdp/Invoice.java` present, `Use.java`'s edges go to `com/acme/Invoice.java`, not to the imported project class (name lookup does not follow a Java import to its file; not this task's cause).
