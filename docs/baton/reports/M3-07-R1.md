# M3-07-R1 — Framework detection keeps its folder scope when package.json files are indexed

Date: 2026-10-31. Base: `develop@00407d6` plus the integrator's P1 remediation patch (`base4.patch`). Owner: lane-vue-p2. Iteration: `docs/baton/iterations/M3-07-R1.md`.

## Root cause

`hasPackageJsonDependency` and `hasComposerDependency` (`src/frameworks/utils.ts`) read every manifest in the scanned file list and fell back to the repo root's only when the list held none. Manifests are excluded by default, so M3-07 only ever exercised the fallback. With the `package.json` exclude dropped, `frontend/package.json` reached `VueRouterDetector.detect()`, which returned true. The registry then activated vue-router for the whole repo, so the folder scope from `findNestedManifestScopes` was never used.

Reproduced on the baseline with the new e2e test: `backend/tools/routes.js → backend/tools/AdminPanel.vue` route edge, in both worker and main-thread scans. `detect()` returned true for a file list holding only nested manifests.

## Delivered

- **`src/frameworks/utils.ts`.** Both helpers read only `<projectRoot>/package.json` / `<projectRoot>/composer.json`, through the existing `readManifestDependencies`. The `files` parameter stays (now `_files`, unused), so no detector changes. A nested manifest activates a detector only through the registry's folder-scoped path (M3-07).
- **`src/frameworks/framework-registry.ts`.** The doc comment of `detectActiveFrameworks` now states that contract (comment only).
- **Side effect, intended.** The helpers no longer join the repo root with workspace-relative paths (wrong in multi-repo workspaces).
- **Tests.**
  - `tests/vue-sfc.test.ts`: e2e "keeps Vue scoped to frontend/ when package.json files are indexed" (worker threads, `--no-parallel`), and a unit test "detect() reads only the repo-root manifest, whatever manifests the file list holds" (Vue Router and Symfony, with no root manifest, a root manifest without the dependency, and one with it).
  - `tests/framework-detectors.test.ts` (outside `affectedFiles`, see below): nine "monorepo" tests asserted the defect itself, `detect(tmp, ['apps/x/package.json']) === true`. Eight now assert `detect()` is false and the registry activates the detector with scope `apps/x`. The Express one asserts Express is not activated by a nested manifest (it has no folder-scoped activation).

The scanner's Vue app boundary (`vueScope`, M3-08-R1) is untouched. It reads detection scopes only through `vueRouterActive`, which now gets the folder scope in this setup.

## Files outside `affectedFiles`

- `tests/framework-detectors.test.ts`: its nine nested-manifest tests encoded the defect (`detect()` true from a nested manifest). They had to change with the fix. They now assert the folder-scoped contract through `FrameworkRegistry.detectActiveFrameworks`.

## Limitations

- **Express.** A nested Express manifest no longer activates Express in any setup. Before, it did so repo-wide, but only when manifests were indexed (or a unit caller passed one). This matches the M3-07 report's stated root-only Express.
- **Laravel.** `detect()` is unchanged in practice: nested apps up to three folders down are found on disk (`findLaravelRoots`). A Laravel `composer.json` deeper than that, with manifests indexed, no longer activates it.

## Findings outside this task

- `SvelteKitDetector.detect()` returns true for a `svelte.config.js` anywhere in the file list. `svelte.config.js` is not excluded by default, so a nested SvelteKit app activates SvelteKit for the whole repo instead of its folder. `SymfonyDetector` does the same for a nested `symfony.lock`. This is the same class of leak as this task, through a different file. Not fixed: it would need `sveltekit.ts` / `symfony.ts`.

Changelog: A `package.json` or `composer.json` in a sub-folder activates its framework detector for that folder only, also when your filters index manifest files; before, indexing them turned the detector on for the whole repo (M3-07-R1).

## Independent review
