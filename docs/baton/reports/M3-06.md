# M3-06 — Vue Router navigation edges

Date: 2026-10-31. Base: `develop@9594f0a` (rebased onto M3-05 and M3-04). Owner: lane-vue-router. Iteration: `docs/baton/iterations/M3-06.md`.

## Delivered

Edge-contract rule 9 (`docs/baton/iterations/M3-01.md`, "Edge contract") and the vue-router detector defect recorded in M3-01:

- **`navigate` `ReferenceType`** (`src/types.ts`). It is a client-side navigation, not a `route`.
- **`src/parsers/languages/vue-navigation.ts` (new).** Pure text analysis in three parts.
  - **Parser side, `navigationReferences(source)`:**
    - in `<script>` blocks: `push` / `replace` called on `this.$router` (or any `$router`), on a local bound to `useRouter()` or `this.$router`, on `useRouter()` itself, or on the router module's import (`import router from '@/router'`);
    - in the template: `<router-link>` / `<RouterLink>` with `to="/path"`, `:to` / `v-bind:to` holding a path literal or `{ name }` / `{ path }`, and `$router.push(…)` inside template expressions. HTML comments are masked;
    - targets: a string `name` (which wins over `path`, as in Vue Router), or an absolute path with query and hash dropped. In a template literal each `${}` stands for a dynamic segment part. Computed targets (`ROUTES.X`, `'/x/' + id`, variables) give no reference;
    - the reference has no owner; M3-02's `assignOwners` (rule 2) gives it the enclosing member or the component symbol.
  - **Route records, `routeRecords(text)`:** every `routes: [ … ]` / `const routes = [ … ]` array, including typed `const routes: RouteRecordRaw[] = [`. Records need a string `path`. For each record it reads:
    - the full path, with parent `children` prefixes;
    - the `name`;
    - the component: `component: X` through X's import or `const X = () => import(…)`, or an inline `() => import('…')` / `require('…')`, or the `default` view of `components: {}`;
    - a `redirect`;
    - whether it has children.
  - **Matching, `matchRoute(target, table, caller)`:**
    - a name matches by exact string only;
    - a path matches a literal record path, else the most specific `:param` pattern. Catch-all records (`*`, `/:pathMatch(.*)*`) are never targets;
    - a parent yields to its empty-path child at the same path;
    - a redirect-only record is followed, up to 4 hops;
    - when several router files define the target, the one nearest to the caller wins. Records that still disagree give no edge.
  - `withSrcAlias` resolves Vue CLI / Vite's `@/` from a JS/TS router file against the nearest `src/` folder (the scanner's resolver only maps `@/` for `.vue` importers).
- **`src/parsers/languages/vue.ts`:** a two-line hook pushes `navigationReferences(source)` before `assignOwners`.
- **`src/parsers/languages/vue-template.ts`:** exports `maskBlocks`, `templateRange`, `templateNodes` and their types. There is no behaviour change, and `router-link` stays a non-render built-in.
- **`src/core/scanner.ts`:** a `navigate` reference resolves only through `resolveNavigation`:
  - it uses a per-repo route table, built lazily once per resolution phase (reset with the other per-phase caches);
  - the edge goes to the component `.vue` file, with `target_symbol` = its component symbol and `metadata.route = { file, name, path }` beside the parser's `metadata.navigate`;
  - a `:param` pattern match is `inferred`; a name or literal path match is `verified`;
  - the detector context gets the new optional `ScanContext.resolveImport`.
- **`src/frameworks/detectors/vue-router.ts` (defect fix):**
  - `component: X` now resolves through the router file's import of X (or its lazy constant), and lazy `import()` / `require()` specifiers resolve through the scanner's import resolver (aliases, missing extensions);
  - a `.vue` handler's symbol is its component symbol;
  - a binding that is not imported keeps the old name lookup. An import that resolves nowhere (a package component such as `RouterView`) keeps the old fallback, the router file;
  - also fixed, found by the e2e test: a parent record took its children's lazy imports and named views as its own components. Component patterns are now matched on the record without its `children` array.
- **Survives a scan:** `navigate` is not in `deleteFrameworkEdgesForRepo` / `dropFrameworkEdgesForRepo` (both unchanged), so the detect phase, which runs after resolution, keeps it. The route registry, the source of `mapx routes` / `mapx_routes`, only ever receives detector routes.
- **Docs:** the Vue rows in `README.md` and `docs/getting-started.md`, and the Vue Router row in `docs/framework-integration.md`. The CLI and MCP options are unchanged, so `cli-reference.md` and `mcp-integration.md` need no change.

## Limitations and not done

- **Navigation from plain `.js` / `.ts` modules** (stores, guards, composables) is not read. Only `.vue` files go through the hook. This is outside rule 9's fixture; it is a follow-up if wanted.
- **Not targets (fail closed):**
  - named-route constants (`{ name: ROUTES.HOME }`), string concatenation, destructured `const { push } = useRouter()`, and a receiver named `router` that is not bound as described;
  - catch-all routes;
  - routes declared as `export default [ … ]` without a `routes` name;
  - components re-exported through barrel files (the route resolves to `index.js`, not a `.vue`).
- **Route table scope:**
  - the table is per repo; several router files are told apart by directory nearness to the caller, not by M3-07's manifest scopes;
  - building it reads (and caches for the phase) every JS/TS file of the repo once, the first time a `navigate` reference is resolved, and only when one is.
- **`sync`:** editing only the router file (renaming a route) does not re-resolve unchanged `.vue` files, so their `navigate` edges stay as they were until those files are re-parsed. This is the same limitation as M3-02's global registry, now tracked as M3-08.
- **Detector fallbacks:**
  - an imported component that resolves nowhere still points at the router file, as before; dropping it would drop the route from `mapx routes`;
  - `@/` is mapped to the nearest `src/` only; other `vite.config` / `tsconfig` aliases are not read.
- **Not added to `trace`:** `navigate` is not in the flow tracer's `DATA_BEARING_EDGES`.
- **No independent review agent was run in this lane.** The review is left to `baton-review`.

## Findings outside this task

- **The scanner's `resolveImportPath` maps `@/` → `src/` only when the importer is a `.vue` file, and only at the repo root.** `@/` imports in `main.js`, stores or routers do not resolve through it; M3-02's global registry is affected too.
  - `withSrcAlias` works around this for route components only.
  - M3-04's `resolveAliasBySuffix` is another local workaround, for composables.
  - M3-09 (import aliases) is the place to unify them. Its resolver should then replace `withSrcAlias` in `resolveNavigation` and in the detector context.
- **`resolveSymbolToFile` falls back to case-insensitive name lookup.** This made `component: Cart` resolve to `CartView.vue` through `const cart` there. Any detector that uses name lookup can hit look-alikes this way.

Changelog: Vue Router navigation (`router.push` / `replace`, `this.$router.push`, `<router-link :to>`) now gives `navigate` edges to the component of the route it reaches, and Vue Router routes resolve statically imported components to their `.vue` file instead of the router file (M3-06).
