# M7-05 report: GitHub Pages deploy workflow and CI build check

Delivered 2026-11-07. Spec: `docs/baton/iterations/M7-05.md`.

GitHub Actions cannot run here. Nothing below was executed by Actions: the workflows are checked statically against what the repository really contains, and the build they run is run locally. The first real run is the owner's push to `main`.

## Delivered

- **`.github/workflows/pages.yml`:** triggers are a push to `main` and manual dispatch. The `build` job installs the root and `site/` dependencies, runs `npm run site:build` and uploads `site/.vitepress/dist`. The `deploy` job deploys it in the `github-pages` environment. Only official `actions/*` actions, each pinned to a major version; Node 20 as in `ci.yml`.
- **Least privilege:** the workflow grants `contents: read`. The build job, which runs `npm ci` lifecycle scripts and the repository's code, has nothing more. Only the deploy job, which runs no repository code, has `pages: write` and `id-token: write`.
- **Main only:** the deploy job runs only for `refs/heads/main`. A manual run from another branch builds the site as a dry run and stops.
- **No cancelled deploys:** `concurrency: pages` with `cancel-in-progress: false`.
- **`site` job in `ci.yml`:** it runs on every CI run (the landing page reads `src/` and `README.md`, so a path filter would miss real breakage, and the alternative needs a third-party action). It installs both dependency trees and Chromium, runs `npx vitest run tests/site-` with `REQUIRE_SITE=1` (a missing install becomes a failure, not a skip), runs the site Playwright config and uploads its results on failure.
- **`yaml` 2.9.1 (ISC)** as an exact dev dependency, to parse the workflows in tests (19 lockfile lines, nothing else changed).

## Independent review

A fresh reviewer, given the criteria and the diff, found no P0 and no P1.

- **P2, fixed:** `pages: write` and `id-token: write` were granted to the build job as well. They are now the deploy job's alone, and `actions/configure-pages` (not needed for VitePress, and the reason Pages permissions would have stayed in the build job) was removed.
- **P2, fixed:** "deploy from main only" was only a trigger; a manual run from `develop` could have published `develop`. The deploy job now carries a `main` guard.
- **P2, fixed:** the upload path was checked by matching text in the configuration. A test now builds as the workflow does (no `SITE_OUT`) and finds the output where the upload step looks.
- **P2, fixed:** the "drift" test claimed more than it proved (offline, a drifted manifest can fail because npm cannot fetch what is new, not because it rejected the lockfile). Its name and comment now say what it shows. The vitest-filter test could only be true; it now lists the files the filter would really select and expects exactly the four site test files. `require('node:fs')` became an import.
- **Not changed, owner decision:** a push to `main` starts CI and Pages in parallel, and Pages does not wait for the Site job. The owner decided on 2026-11-07 that the `Site` check should not be required for `main`, so the live site can be published without the site tests having passed. The Pages build still fails on a broken site; only the browser and link tests are not a gate.

## Limitations

- The workflow has never run. Likely first-run failures are on the platform side: Pages not set to "GitHub Actions" (the deploy job fails), or the `github-pages` environment restricting branches.
- `npm ci --dry-run` does not check that tarballs exist or match their integrity hashes.
