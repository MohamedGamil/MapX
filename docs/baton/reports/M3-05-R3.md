# M3-05-R3 — Store-library gate follows package.json changes and monorepo roots

Date: 2026-11-03. Base: `develop@8cdf580`. The first delivery (e78d742) was rebased onto `develop@f0fc004`. The review fixes are rebased onto `develop@2c69e3d`, where the registered commands were rerun. Iteration: `docs/baton/iterations/M3-05-R3.md`. Source: `docs/baton/reports/M3-05-R2.md` (Limitations).

## Delivered

- **Monorepo roots lend their store libraries** (`src/parsers/languages/vue-stores.ts`, `storeDependencies`).
  - The gate is still the nearest package.json that declares dependencies.
  - When that package lacks `vuex` or `pinia`, the search goes up to its workspace root: the first folder above it whose globs list the package's folder. Globs come from a package.json `workspaces` (an npm/yarn array, or yarn's `{ packages }`) or a `pnpm-workspace.yaml` `packages` list.
  - That root lends the libraries it declares (`dependencies`, `devDependencies`, `peerDependencies`). A root that lists the package but declares neither library lends nothing.
  - Roots whose globs do not list the package are passed: a nested `workspaces` for other folders, or a `pnpm-workspace.yaml` with settings or catalogs only.
  - Globs are matched with picomatch, already a runtime dependency. `!` globs exclude.
  - `pnpm-workspace.yaml` is read by a small parser. It takes the top-level `packages` key, quoted or not, as a block list (indented or not) or a flow sequence (on one line or more). It drops comments and quotes, and adds no dependency.
- **The search is bounded** (`workspaceSearchEnd`): at the repository root (the nearest folder holding `.git`), else at the MapX workspace root (`.mapx`), else at the package itself. Each folder's `.git` / `.mapx` check is cached per process.
- **Sync follows every manifest the search reads** (`src/core/scanner.ts`, `configReferrers`, the existing M0-02-R8 config tracking).
  - **Inside the workspace:** the tracking already hashes every package.json above an indexed JS/TS/Vue/Svelte/Python file, and re-parses the files below a changed one, on the git and hash sync paths. Criterion 1 held on develop through it. `pnpm-workspace.yaml` is now hashed with each folder's package.json and bundler configs.
  - **Above the workspace root** (MapX initialised in a package, the monorepo root above it; review finding 1): the folders up to the same end the parse uses (`workspaceSearchEnd`) get their package.json and `pnpm-workspace.yaml` hashed, keyed `^<relative path>`. A change to one re-parses every source.
  - Both edits sit in `configReferrers` and its import line, nowhere near `resolveSymbolToFile`.
- **`EXTRACTOR_VERSION` 13 → 14**, with its comment line (`src/core/extractor-version.ts`; develop took 13 for M5-25-R2). A package in a monorepo whose root declares pinia or vuex now indexes differently without any file changing.

## Tests (`tests/vue-stores.test.ts`: 38 tests, 13 of them new)

All new tests are e2e (real `init` + `scan` / `sync` / `scan --force`) or call `storeDependencies` on a real temp workspace, and assert identities.

- **"a git sync / a hash sync after pinia is added to or removed from package.json"** (`describe.each`, 2 × 2 tests).
  - **Links the hook call once pinia is listed, and drops it once it is removed, as scan --force does** (criterion 1).
    - Add `pinia`, then sync: the edges equal `scan --force`'s (every edge, all columns), and `addOne → src/stores/wish.ts#add`. The nested package `packages/admin`, with its own dependencies, gets no Pinia edge.
    - Remove `pinia`, then sync: again equal to `scan --force`, and the edge is gone.
  - **Lends the root store library to a package once pnpm-workspace.yaml lists it, as scan --force does:** after adding `pnpm-workspace.yaml`, the sync equals `scan --force`, and `packages/admin` links to its own store.
- **"a git sync / a hash sync of a package below its monorepo root"** (2 tests, review finding 1). The root holds `workspaces: ['packages/*']` and pinia; MapX is initialised in `packages/app`.
  - Remove pinia from the root, then add it back. Each sync equals `scan --force`, and the edge goes and comes back.
  - The hash variant's `.git` is an empty folder: git does not read it, so the sync takes the hash path (asserted with `isGitRepo`), while the search still stops there.
- **"a store library declared at a monorepo root"** (7 tests).
  - **Gives a workspace package the Pinia handling** (criterion 2): `workspaces: ['packages/*', '!packages/legacy']` and pinia at the root; `packages/app` lists only vue.
  - **Lends nothing to a package the workspace globs do not list:** `tools/cli` (outside the globs) and `packages/legacy` (excluded).
  - **Looks for the workspace root only up to the repository root:** a package holding its own `.git` gets nothing.
  - **Reads yarn's `workspaces.packages` and a root's `devDependencies`.**
  - **Reads pnpm-workspace.yaml in flow and block style, quoted or not, with comments** (review finding 2): 7 forms give `pinia: true`, including multi-line flow, `"packages":`, unindented items and a catalog before the key. A list without the package gives `false`.
  - **Walks past a workspace root that does not list the package, to the root that does** (review finding 3): a settings-only `pnpm-workspace.yaml` at the root or in `packages/`, and a nested `workspaces: ['other/*']`. A listing root without the library decides, giving `false`.
  - **Looks for the workspace root only up to the MapX workspace when no repository holds it** (review finding 4): `.mapx` in the package gives `false`, `.mapx` at the root gives `true`, and neither gives `false`.

## Limitations

- **The re-parse is broader than the integration owner's "narrow" constraint.** The M0-02-R8 tracking re-parses every JS/TS/Vue/Svelte/Python file below a changed package.json on any edit, including nested packages with their own manifests. That predates this task. The manifests above the workspace root that this task adds follow the same rule and re-parse every source. Narrowing package.json signatures to the fields resolution reads would touch M0-17-R4, M3-09-R1 and the alias tracking; that would be a separate task.
- **Workspace roots:** only package.json `workspaces` and `pnpm-workspace.yaml` count, not `lerna.json`, `rush.json` or Nx/Turbo. The pnpm parser covers the subset above, not YAML anchors or multi-document files.
- **Boundaries:**
  - A package that is its own repository (a submodule, its own `.git`) gets nothing from the monorepo root above it.
  - Outside any repository, a root above the MapX workspace is not consulted.
  - The `.git` / `.mapx` lookups are cached for the process's life. A long-running `mapx serve` does not see a `.git` created after it started.
- **Gate not counted from code.** A `defineStore` / `createStore` elsewhere in the repo still does not count as the gate (M3-05-R2's alternative).
- **Changelog:** root `CHANGELOG.md` (in `affectedFiles`) is left to the integration owner, per the lane brief. The line is below.

## Findings outside this task

- **The M3-05-R2 report's limitation "A `package.json` edit does not re-parse files" is inaccurate** for sync. `configReferrers` has re-parsed below a changed package.json since M0-02-R8.
- **Disk:** the `/` volume (which holds `/tmp`) ran out of space during the first delivery. This lane's temporary copies (benchmark workspaces, probe output) were deleted.

Changelog: In monorepos, a Pinia or Vuex library declared at the workspace root (package.json `workspaces` or pnpm-workspace.yaml) now counts for the packages it lists, also when MapX is initialised in a package, and sync follows changes to those roots (M3-05-R3).
