# M4-20 — Dashboard performance on large workspaces

Decision D027. The targets come from the M4-16 baseline. One baseline was re-measured, as described below.

## Baselines

| Measure | M4-16 audit | Re-measured 2026-11-02 |
| --- | --- | --- |
| Initial JavaScript, gzipped | `main.js` 690,763 bytes | — |
| Full Codebase, 2,000 files, until the main thread settles | 9,768–10,636 ms | 7,059 / 7,132 / 8,414 ms (median **7,132 ms**) |
| `/api/graph`, 2,000 files, on the wire | 998 KB, uncompressed | — |

**Re-measurement method:** a worktree at `fa31104` (M4-16) ran its own audit three times on this machine (`scripts/ui/audit.ts --sizes 2000`), at a load average of about 11.
- The fresh median is lower than M4-16's own figures, so it is the stricter baseline, and the targets below use it.
- In that baseline the layout was a single main-thread task of about 6 s.

## Delivered

**Lazy layout engines (criterion 1)**
- **Build:** `scripts/build-ui.ts` builds ES modules with code splitting. Its entry points are `main.ts` and the new `layout-worker.ts`, chunks go under `dist/ui/chunks/`, and stale chunks are deleted on each build.
- **On demand:** `main.ts` registers only fCoSE up front. ELK, Dagre and Cola load through `import()` the first time they are chosen (`ensureLayout`); `runLayout` waits for the engine and then runs.
- **`scripts/check-package.ts`:**
  - It measures the *initial* JavaScript: `main.js` plus the chunks it imports statically.
  - It fails above the old ceiling, and also when the initial JavaScript is not 30% below the M4-16 baseline.
  - It also fails when a built chunk or the worker is missing from the package.
  - The binary packaging copies `dist/ui` whole, so the chunks ship there too.

**Large graphs (criterion 2)**
- **`src/ui/layout-worker.ts`:** runs fCoSE on a headless cytoscape inside a module worker and posts the positions back.
- **Mode switch:** above 600 elements, switching view (`updateGraphDisplay` → `prelayoutInWorker`) sends the *new* elements to the worker before they are drawn. They are then added once, already placed.
  - **Sizes:** node sizes are estimated from degree, cluster size and label length, as the style draws them. Measuring 2,000 labels on the canvas cost the main thread several hundred milliseconds.
  - **While waiting:** the canvas shows "Laying out the graph…" (CSS on `body[data-graph="layout"]`).
- **Other layouts:** a re-layout of drawn elements goes through `runLayoutInWorker`.
- **Stale and failed runs:** a sequence number discards stale results. A worker that fails to load or errors falls back to the main-thread layout.
- **fCoSE tuning:**
  - A CPU profile of fCoSE on the 2,000-file graph put about 60% of the time in repulsion, computed between nodes within a range proportional to the ideal edge length. `numIter` barely matters, because cose-base raises it to about 5 per node.
  - Above 1,500 elements the ideal edge length is 70 (was 180) and the repulsion 120,000 (was 250,000). Headless, the layout fell from 5.8 s to 3.2 s.
  - Overlaps in a 1-in-16 sample of node pairs went from 0–1 to 15. The screenshot shows the same organic shape.
  - Draft quality was rejected (11,902 overlaps).

**Compression (criterion 3)**
- `src/ui-server.ts` sends JSON responses of 1 KB or more compressed (`sendBody`): brotli at quality 5 when accepted, else gzip, with `Vary: Accept-Encoding` and `Content-Length`.
- Scripts, styles and HTML are compressed too, cached per file version.
- For the 2,000-file graph: 1,022,302 bytes raw → **42,851 brotli** / 63,259 gzip, in about 6 ms. That is 96% and 94% less than the 998 KB baseline.

**Also:**
- **Docs:** `docs/cli-reference.md` (`mapx ui`) and the CHANGELOG.
- **Diagnostics:** the dashboard records the worker's time on `<body data-layout-ms>` and the marks `mapx:layout-posted` and `mapx:layout-received`.

## Results against the targets

| Criterion | Target | Result |
| --- | --- | --- |
| 1 Initial JavaScript | ≤ 70% of 690,763 bytes | **200,610 bytes, 71% smaller** (`check-package`). ELK (444 KB gzipped), Dagre and Cola load on demand. |
| 2 Full Codebase, 2,000 files | ≤ 70% of 7,132 ms = 4,992 ms; no main-thread task over 800 ms (the baseline: one task of about 6 s) | median **3,675 ms** (runs 3,675 / 4,146 / 3,675); longest task median **363 ms** (`perf-large.spec.ts`). Earlier runs on a busier machine: 4,253–4,369 ms, longest tasks 481–512 ms. |
| 3 `/api/graph`, 2,000 files | compressed, ≤ 70% of 998 KB on the wire | brotli 42,851 bytes, gzip 63,259 bytes, decoding to the same JSON (`tests/ui-server-compression.test.ts`) |

Without the worker but with the tuning, the same view is ready in about 3.9 s, but in one 3.3 s task. The worker costs about 400 ms and in exchange keeps the page responsive.

## Limitations

- The budgets are absolute times on this machine; CI scales them (`MAPX_UI_PERF_SCALE=2`).
- The tuning is fitted to the generated fixture. A real 2,000-file project may lay out differently, but the worker keeps the page responsive either way.
- The worker estimates label sizes instead of measuring them, so on dense graphs labels can overlap slightly more than with the main-thread layout.
