# M3-09-R1 — JS/TS aliases stop at the app's own boundary

Date: 2026-10-31. Base: `develop@00407d6`. Iteration: `docs/baton/iterations/M3-09-R1.md`.

## Delivered

- **App boundary (`src/core/js-aliases.ts`).** `jsAliasTargets` no longer walks upwards until *any* config declares a matching alias.
  - **App root.** This is the nearest folder, from the importing file upwards, that holds a `package.json` or a bundler config. Bundler aliases (vite / vue-cli / webpack / Laravel Mix) come from that folder only. An app root with only a `package.json` declares no bundler aliases, so its `@/` falls back to its own `src/`.
  - **Compiler `paths`.** They come from the nearest folder holding a tsconfig/jsconfig, with the relative `extends` chain and `references` as before. The lookup goes no further than the app root. The nearest config decides even without `paths`, as in TypeScript.
  - **A tsconfig alone is not an app root.** A `tests/tsconfig.json` that extends the root config still gets the root's bundler aliases.
  - `dirAliases` now reports per folder whether a tsconfig/jsconfig exists (`compiler`, null without one) and whether the folder is an app root (`bundler`, null when it is not). The per-file-set, per-folder cache is unchanged.
- **Chained `.set()`.** `config.resolve.alias.set('@', a).set('assets', b)` registers both aliases. Before, only the first call was read.
- **Backslash segments.** `path.resolve(__dirname, 'resources\\js')` gives `resources/js`. Before, the backslash was kept, so the path never matched an indexed file.
- **Corrected test.** "skips non-literal aliases; tsconfig paths come before a bundler alias; the nearest config decides" in `tests/legacy-imports.test.ts` expected the root `vite.config.js`'s `~` to apply to `web/ts/a.ts`.
  - `web/` has its own `vite.config.js` (and tsconfig), so it is its own app. Vite resolves `web/`'s imports with `web/vite.config.js` alone, and the root config is a different project's.
  - The expectation is now `[]`, with a comment saying so. The case's other assertions are kept: `web/`'s tsconfig `@` beats `web/vite.config.js`, and the root `@` applies outside `web/`.
- **Docs.**
  - `docs/framework-integration.md` gains a new "Import aliases (JS / TS)" section (app root, `paths`, bundler forms, order, fallback, what is not read). The Vue Router row now links to that section. This lane did not edit the "How It Works" paragraph.
  - `docs/getting-started.md`: the Imports bullet.
- **Scanner.** `src/core/scanner.ts` is unchanged. Import, render, route-component and navigate edges all reach the resolver through `Scanner.resolveImportPath`. The e2e test shows that the resolver change alone fixes each of the four edge kinds. The HTTP pass (`client-calls.ts` `resolveImport`) is fixed by the same change.

## Limitations

- **What makes an app root.**
  - A `package.json` makes an app root even when it is only a `{"type": "module"}` marker in a sub-folder. Aliases from above it are then not applied.
  - A root `tsconfig.json`'s `paths` no longer reach a workspace package that has its own `package.json` but no tsconfig of its own. TypeScript's editor lookup would still use the root config there.
  - This trade-off is deliberate. A Laravel root `jsconfig.json` with `@/*` → `resources/js/*` is common, and it must not reach a nested Vue CLI app, which builds with its own `@` → `src`.
- **Unchanged from M3-09:**
  - tsconfig `include` / `files` are not read;
  - `extends` from npm packages are not followed;
  - `package.json` `imports`, Nuxt / SvelteKit / Quasar configs, runtime aliases and RegExp `find` keys are not read.
- **Cost.** A folder's tsconfig is now read once to check that it exists and once to parse it. The result is cached per folder per phase, as before.

## Independent review and fixes

Reviewer G reproduced one P1 in this task:

- **P1-4.** Root tsconfig `paths` no longer reached a monorepo package that has a `package.json` but no tsconfig (tsc uses the root's). A `{"type": "module"}` marker inside an app cut off the app's vite alias.
- **Fix (integrator).** Manifests are classified:
  - **app:** a separately built app, with a bundler config or a build tool among its dependencies;
  - **package:** any other manifest with a name or dependencies;
  - **none:** a marker such as `{"type": "module"}`.

  Compiler `paths` come from the nearest tsconfig/jsconfig above the file, as tsc finds it, but not from above an app root. Bundler aliases come from the nearest package root, and a marker is no boundary.
- **Test change.** The lane's unit fixture had a `{}` `frontend/package.json`. It now has a realistic Vue CLI manifest.
- **New test cases**, in "paths come from the nearest tsconfig/jsconfig…":
  - the reviewer's monorepo package resolves `@shared/util` through the root tsconfig;
  - the marker keeps the app's `~` alias;
  - a vite app does not take the root's paths.
- **Results.** All alias, Vue and HTTP tests pass. The edges and HTTP scorers are unchanged.
