# M5-07-R2 — CI reporters: baselines outside the repository and submodule workspaces

Date: 2026-11-03. Base: `develop@0628819` plus this lane's M5-23-R1 and M5-21-R1 commits. Owner: lane agent. Iteration: `docs/baton/iterations/M5-07-R2.md`. Source: `reports/M5-07-R1.md` (Limitations: "A baseline outside the repository" and "Submodules").

## Delivered

- **A file outside the repository is not a SARIF location** (`src/arch/reporters/sarif.ts`, `src/arch/reporters/context.ts`).
  - `outsideRoot(path)` holds for a path from the repository root (or from the workspace, outside git) that is `..`, starts with `../`, or is absolute (on Windows, a file on another drive).
  - For such a location (a stale entry of `--baseline ../../outside/bl.json` from `repo/sub`), **every CI format** locates the finding on the configuration file instead, at the line of its `"baseline"` key, or line 1 when `--baseline` names the file (review: GitHub requires a location in the repository on every result).
  - The message ends `(in ../outside/bl.json, outside the repository)`. SARIF also carries the path in `properties.outsideRoot`. The outside path never appears as a location.
  - No SARIF `uri` therefore leaves `%SRCROOT%`, and every result has a physical location.
  - Why not an absolute `file://` URI: the output stays byte-stable and machine-independent, which the header promises ("No … absolute paths"), and it leaks no CI runner path.
- **An absolute path is never prefixed** (`repoPath`). Before, a Windows baseline on another drive (`D:/ci/bl.json`) became `sub/D:/ci/bl.json` in every CI format. It now stays as written, and SARIF treats it as outside.
- **Every other location is unchanged.** The goldens hold byte for byte, and so do the workspace's own files under `sub/` and a baseline inside the repository (`../bl.json` from `repo/sub` is `bl.json`).
- **Submodules: decision, no option.** A workspace inside a git submodule keeps paths relative to the submodule's root (git's `--show-prefix` view). No superproject-relative prefix is added. The reasons:
  - The files belong to the submodule's repository. GitHub code scanning and GitLab look a path up in the repository and commit the upload names.
  - The superproject only records the submodule's commit (a gitlink). A `mods/lib/sub/app/…` path would therefore point at no file in either repository: code scanning in the superproject cannot open files inside a submodule, and the submodule's own repository has no `mods/lib/` folder.
  - An option would only produce paths that no consumer resolves. A test pins the behaviour.
- **Docs:** `docs/cli-reference.md` (CI formats: outside-the-repository SARIF results, submodules) and `docs/architecture-rules.md` (CI reports: the same two points).

No CLI or MCP option changed. Only the SARIF output changed, and only for a location outside the repository. No schema change. No new dependency.

Files beyond `affectedFiles` (`src/arch/reporters/**`, `tests/arch-reporters.test.ts`): the two docs files.

## Limitations

- **The location is the configuration**, not the baseline itself: the configuration line that names the baseline when there is one, else line 1.
- **A Windows path on another drive** is never prefixed. It is an outside location, so it appears only as message text (and in SARIF's `outsideRoot`).
- **Submodules:** no superproject prefix, by decision. A user who uploads from the superproject must upload the submodule's results to the submodule's repository.
