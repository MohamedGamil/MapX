# M3-07 — Framework detection from package.json files below the repo root

Date: 2026-10-31. Base: `develop@eb9c2a7`, rebased over M3-03.

## Root cause

`package.json` and `composer.json` are in the default `excludePatterns` (`src/core/config.ts`), so they never reach the scanned file list. `hasPackageJsonDependency` / `hasComposerDependency` look for manifests in that list. Finding none, they fall back to the repo root's file, so only the root manifest was ever read. One scan of `tests/fixtures/vue-sfc/` (no root `package.json`) wrote no `frameworks.json`, and Vue detection never ran.

## Delivered

- **Contract** (`src/types.ts`): `FrameworkDetector.manifestDependencies?: { manifest: 'package.json' | 'composer.json'; names }`.
- **Detection** (`src/frameworks/framework-registry.ts`, `src/frameworks/utils.ts`):
  - `detectActiveFrameworks(projectRoot, files, { workspaceRoot, scopes })` still returns the active detectors.
  - A detector whose `detect()` is true is active for the whole repo, as before.
  - Otherwise, a manifest below the repo root that lists one of its names activates it. The manifest's folder is reported in `scopes` (workspace-relative).
  - `findNestedManifestScopes` takes its candidate folders from the scanned files and their ancestors below the repo root. Excluded folders (`node_modules/`, `vendor/`) are never read, and no extra directory walk is made.
  - Manifests are parsed once per detection pass and shared across detectors. A folder inside another matched folder is dropped.
  - The change is strictly additive: a repo whose root manifest already activated a detector behaves exactly as before.
- **Scoping** (`src/core/scanner.ts`, `src/parsers/ignored-symbols.ts`, `src/parsers/parse-worker.ts`). Activation has an effect in two places, and both now honour the scopes:
  1. **Framework ignore lists** (today only `vue-router`: `t`, `ref`, `computed`, …) apply only to files inside the scopes. `buildScopedIgnoredSymbols` and `ignoredSymbolsForFile` pick the set per file on the main thread and in the workers.
  2. **Route and hook extraction** (`scanFrameworkRoutesAndHooks`) runs a scoped detector only on files inside its folders.

  The `scanner.ts` diff is small: a cache of scopes beside the cached detectors, the three ignore-list call sites, the per-file set on the main thread, and the extraction filter.
- **Detectors given `manifestDependencies`:**
  - package.json: vue-router, nestjs, nextjs, react-router, tanstack-router, sveltekit;
  - composer.json: symfony, yii.

  Each `detect()` reuses the same names list.
- **Docs:** `docs/framework-integration.md` already claimed monorepo-aware detection, which was false. It now describes the per-folder behaviour accurately.

### Laravel and NestJS

- **NestJS** had the same root-only `package.json` check. It now gets nested activation, scoped to its folder, like Vue.
- **Laravel is not root-only and stays whole-repo.**
  - `detect()` already finds apps up to three folders down on disk (`findLaravelRoots`: `artisan`, or a `composer.json` requiring `laravel/framework`).
  - Its mount graph legitimately resolves route files outside the app folder (`loadRoutesFrom` of a sibling module), so scoping extraction to the app folder could drop real routes.
  - It has no ignore list, so whole-repo activation has no cross-language side effect.
  - The routes scorer is unchanged.
- **Express is not changed.** Its `detect()` also pre-scans files for `app.use('/prefix', router)` prefixes, but only when the root manifest matches. Activating it from a nested manifest without that pre-scan would give a half-working detector. Left for a follow-up if wanted.

## Mutation check

Each mutation was applied, the new tests were run, and the code was restored:

| Mutation | Result |
|---|---|
| Nested activation off (`if (!deps \|\| 1) continue;` in the registry) | Whole-fixture test fails (69 vs 78 edges). Both e2e runs fail. |
| Extraction scope filter off (`\|\| 1` in `matchingPaths`) | Both e2e runs fail with an extra `backend/tools/routes.js → backend/tools/AdminPanel.vue` route edge. |
| Ignore-list scope off (scopes forced to `['']`) | Both e2e runs (workers and main thread) fail: `backend/tools/i18n.js#t` is dropped. |

The e2e first asserted the ignore-list scoping only on a PHP `t()`, and passed under the third mutation. The PHP parser (`src/parsers/languages/php.ts`) never applies ignore lists, so a Vue sub-app could not drop PHP symbols even before this change. The JS `backend/tools/i18n.js` was added so that the assertion really covers the scoping.

## Limitations and notes

- `roots` in `tests/fixtures/vue-sfc/expected.json` is no longer needed, since criterion 2 shows identical results. It and `score-edges.ts` were left unchanged as instructed; dropping `roots` is the integration owner's call.
- Multi-repo workspaces: the new code resolves manifests against the workspace root, with `files` workspace-relative as the scanner passes them. Older detectors still join the repo root with workspace-relative paths (Express pre-scan, Rails Gemfiles). That is pre-existing and not touched here.
- `frameworks.json` stays a name list and an override. A framework forced on through it (or listed by an earlier scan but no longer detected) is whole-repo, as before.
- `buildIgnoredSymbols` is now unused by the scanner. It is kept as exported API.
- Finding outside the task: PHP files never honour framework ignore lists (see the mutation check). In this setup the PHP parser also produced no call edges for plain global-function calls (`t('Shop')` → `function t`, even within one file). Not investigated.

Changelog: A `package.json` or `composer.json` in a sub-folder now turns on Vue Router, NestJS, Next.js, React Router, TanStack Router, SvelteKit, Symfony or Yii detection for the files in that folder only, so a frontend sub-app is detected without affecting a backend beside it (M3-07).
