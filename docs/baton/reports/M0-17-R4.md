# M0-17-R4 — Calls on library and DOM receivers do not link to same-named project symbols

Date: 2026-10-31. Base: `develop@00407d6` plus the remediation in the working tree. Owner: maintainer. Iteration: `docs/baton/iterations/M0-17-R4.md`.

## Reproduction (before the fix)

A probe workspace (scratchpad `m017r4/`) had `src/lib.ts` declaring `create`, `remove`, `get`, `fetch` and `class Repo`, and `src/use.ts` calling them:

- `axios.create()` linked to `src/lib.ts#create`;
- the global `fetch('/x')` linked to `src/lib.ts#fetch`;
- `el.classList.remove()` and `_.get()` gave no edge (property chain, and a built-in method name).

## Delivered

- **`src/parsers/common-methods.ts`:** `JS_GLOBAL_FUNCTIONS`.
- **`src/parsers/generic-wasm-parser.ts`:** `metadata.receiver` on member calls.
- **`src/core/scanner.ts`:**
  - the library and global skip;
  - `jsImportBindings`;
  - `receiver` is removed from the stored metadata.

## Limitations

- Bindings are read with regular expressions over the file text: a dynamic `import()` or an import inside a string can mislead them.
- A package receiver re-exported through a project module counts as a project receiver.

## Independent review and fixes

Reviewer K (fresh agent) found two P1 regressions and several P2s. All the P1s and the in-scope P2s are fixed. Tests are in `tests/legacy-language-accuracy.test.ts` ("calls on library and DOM receivers"), and each is mutation-checked.

| Finding | Fix | Evidence |
| --- | --- | --- |
| P1: `this.x()`, `super.x()` and `a.b.x()` carried no receiver, so a method named like a global (`this.fetch()`, `this.confirm()`: mixins, Vuex/Pinia map helpers, base classes) was skipped as a global call | Every member call records a receiver (`<this>`, `<super>`, `<member_expression>`), and the skip never applies to Vue `this` or store references | "resolves this.x() named like a global, …"; mutation "receiver only for identifiers": fails |
| P1: any bare specifier the resolver could not resolve counted as an npm package, so workspace packages (`@acme/lib`) and Nuxt `~/` without paths lost their edges | `isNpmPackage`: listed with a registry version in an enclosing package.json (not `workspace:`, `file:` or `link:`), or installed in `node_modules`, and declared by no workspace package | the same test (workspace package and `~/`); mutation "any unresolved bare specifier is npm": fails |
| P2: a local `const api` shadowing an imported package lost its call edges | A file-level `const`/`let`/`var`/`function`/`class` declaration of the name keeps it out of `packages` (a `require` binding is the import itself) | the same test (shadow); mutation: fails |
| P2: `import fetch from 'node-fetch'; fetch()` still linked a project `fetch`, and a class method `fetch` made a global `fetch('/x')` count as declared | A bare call to an npm-imported name is skipped, and only top-level symbols count as the file's own | "gives no edge for a global name imported from an npm package, nor for a global call beside a same-named method"; mutations: each fails |
| P2: the test exercised the new skip only through `axios.create` and `qs.remove` | New cases above | — |

The self-scan figure above (2634 → 2632) is for the first version of this task. With M0-17-R4 reworked and M0-17-R5 applied, MapX's own sources go from 2634 to 2589 call edges; the breakdown is in `docs/baton/reports/M0-17-R5.md`.
