## Delivered

**`src/arch/baseline.ts` (new)**
- **`fingerprint`:** moved here from `report.ts`, which re-exports it, because it is the baseline's identity. Its inputs are given under Fingerprint below.
- **`parseBaseline`:**
  - `version: 1`;
  - `entries`, each with a `fingerprint`, or all four readable keys `rule`/`source`/`target`/`edgeType`, from which the fingerprint is computed. `sourceRepo`/`targetRepo` are added when an end is outside the root repo. When both a fingerprint and the keys are given, they must agree;
  - Deptrac's element pairs, `skip_violations: { source: [targets] }`.
  - Unknown keys, bad values, a wrong version, invalid JSON and a disagreeing fingerprint are each a `ConfigError` with a JSON pointer (exit 3). A UTF-8 BOM is accepted.
  - Repeated entries are de-duplicated.
- **`normalizeElement`:** a hand-written Windows path (`src\a.ts`, `src\b.ts#C`) becomes the store's POSIX form, while PHP names keep their backslashes.
- **`repoKey`:** the repo as fingerprints name it: its workspace-relative POSIX path, `''` for the root repo, and the name for a peer repo outside the workspace.
- **`baselineLocation` / `loadBaseline`:** the baseline comes from `--baseline`, else the configuration's `baseline` (relative to the workspace), else `.mapx/architecture.baseline.json` (`.mapx/architecture/<view>.baseline.json` for a view). A named file must exist; the default may be absent.
- **`BaselineMatcher`:**
  - a violation matches by fingerprint, or by an element pair (on the shown elements or on the fingerprint's ends), and every matching entry is marked;
  - `stale()` gives one `error` / `stale-baseline` finding per unmatched entry or pair, with its ends resolved to files in their repo.
- **`renderBaseline`:** violations only, one entry per fingerprint, keys in a fixed order, sorted by code units (never by locale), two-space JSON, a final newline and no timestamp.
- **`loadCompareReport`:** the fingerprints of a `mapx check --format json` report. It leaves out configuration and baseline errors, and refuses a base whose `selection` does not fit the head.

## Fingerprint

The first 16 hex characters of sha256 over `JSON.stringify([rule, source, target, edgeType])`. When either end is outside the root repo, it is taken over `[rule, source, target, edgeType, sourceRepo, targetRepo]` instead.

- **Symbol-level ends** are the reported element's qualified name, with a method lifted to its class. That is stable whatever else its file declares.
- **File-level ends are the file path.** These are an import's importing file and an import path's target file. Before review 2, such an end was named after the file's only top-level symbol, so adding a second symbol re-keyed it (review 2, P1-1). The report still shows the symbol; `identity` carries the file.
- **Repos are workspace-relative paths,** and the root repo is left out. So single-repo baselines never name a repo, which would be the folder's name and so machine-dependent. Two repos' `App\Domain\Order` are apart (review 2, P1-2).
- **Paths are POSIX:** the scanner stores every path with `/` (`relative(...).replace(/\\/g, '/')` throughout `src/core/scanner.ts` and `worker-pool.ts`), and hand-written entries are normalised the same way.
- **What it leaves out:** the line, the layer, absolute paths and time. So a moved line, a re-scan or another machine gives the same value.
- **What re-keys it (by design):**
  - renaming or moving a class;
  - moving a file, which re-keys its file-level ends, and every element in path-named languages (TS, JS: `src/a.ts#Order`);
  - another edge type.

The fixture baseline listed `App\Domain\Order → App\Infrastructure\SqlOrderRepository` as one edge-typed entry (`instantiation`). So the `import` between the same classes stayed a violation: the 26th reported violation.

The authors meant the dependency to be baselined, not one of its edge types:
- **M5-01 report:** "the Domain → Infrastructure row is `skipped`, matched by baseline entry 1". The same report labels the PHP rows "as `instantiation` (and `import` for cross-namespace ones)", one row per dependency.
- **M5-04 report:** php-07 is "the dependency the PHP baseline accepts".

So the entry is now a Deptrac pair (`skip_violations`), which covers both edges. The stale entry php-26 stays an edge-typed entry. No `expected-findings.json` label changed. Violation precision goes from 25/26 to 25/25.

## Limitations

- **CLI only:** M5-14 will need `--baseline`, `--generate-baseline` and `--compare` on the MCP check tool.
- **Fingerprints change from `1736b70`:** fingerprints of file-level ends and of non-root repos differ from those first delivered. Nothing outside this branch used them.
- **Regenerating drops Deptrac pairs:** `--generate-baseline` writes fingerprint entries only, so the `skip_violations` pairs of an existing baseline are not kept.
- **Moving a file re-keys its file-level entries,** and, in path-named languages (TS, JS and the rest), every entry of its elements.
- **Two findings can look alike:** a file-level and a symbol-level dependency between the same two declarations on the same edge type (top-level code in a file next to its one class) are two findings that show the same elements.
- **Base reports:**
  - `--compare` knows only the findings a base report lists, so it should be produced with `--report-skipped --report-uncovered` (documented);
  - a base report from before `selection` existed is not checked for view or filters.
- **Baselines in the workspace:** a baseline kept in the workspace outside `.mapx/` makes the index stale until the next scan. `--generate-baseline` warns about this.
- **Not covered:**
  - `--since <git-ref>` is deferred (REQ-ARCH-021);
  - there is no JSON Schema for the baseline file;
  - the extractor version is not bumped, because scans are unchanged.

Changelog: `mapx check` gains baselines (`--generate-baseline`, `--baseline`, Deptrac-style `skip_violations`; stale entries exit 3) and the `--compare <base-report.json>` ratchet, which fails only on violations new since the base revision (M5-06).
