## Delivered

- **Attribution columns filled** for every Composer candidate decided external: `package`, `origin`, `direct`, `dev` and `attribution`. This happens in the same end-of-run pass (`decideExternalRefs`) as npm, once per ecosystem, folder, name, name kind (class, function or constant) and facade target.
  - `origin` is `builtin` for a PHP built-in class, function or constant, and `package` otherwise.
  - `package` for a built-in is the defining extension's Composer platform name: `ext-date` (`DateTime`), `ext-pdo` (`PDO`), `ext-core` (`Exception`, `strlen`), `ext-standard` (`str_contains`), `ext-spl` (`RuntimeException`). It cannot collide with a `vendor/name` package. For a package it is the lowercase Composer name. It is null when no input names a package (see "unknown" below).
  - `direct` is 1 when a `composer.json` lists the package in `require` or `require-dev`. The manifests checked run from the file's folder up to its own repo's root, never above it and never into another repo (M5-20 P1). It is 0 when no manifest lists it. It is null for a built-in and when the package is unknown.
  - `dev`:
    - for a direct package, it comes from the nearest manifest that lists it, and `require` wins over `require-dev`;
    - for a transitive package, it comes from the lock: 1 if the package is in `packages-dev` only, 0 if it is in `packages`;
    - it is null when unknown and for a built-in.
  - `attribution` is `lock` when a readable `composer.lock` answered. It is `manifest` when the manifests answered instead, which is criterion 2's flag. That happens when the lock is missing or unreadable, or when the lock is stale and lacks a package composer.json requires. It is null for a built-in.
- **Class, function or constant → package** (`src/core/manifests/composer.ts`).
  - **With a lock:** the lock is the nearest `composer.lock`, from the file up to its repo's root. A lock that is present but cannot be read (corrupt, a folder, a file without permission) ends the walk: the manifests answer, never a parent folder's lock (review P2). MapX reads each locked package's `autoload` `psr-4` and `psr-0` prefixes (`packages` and `packages-dev`), and the longest prefix wins. Matching is case-insensitive, as PHP names are.
    - PSR-0 prefixes are plain string prefixes, so `Mustache` covers `Mustache_Engine`.
    - A namespaced function (or a constant from `use const`) is matched by the same prefixes, because packages define `files` functions in their own namespace by convention (`DeepCopy\deep_copy` → `myclabs/deep-copy`). A global function or constant is never matched by prefix.
    - **Sibling packages that register the same prefix** (review P1-1): `illuminate/support`, `illuminate/collections` and `illuminate/macroable` all register `Illuminate\Support\`, and `doctrine/common` and `doctrine/event-manager` both register `Doctrine\Common\`. The lock alone cannot tell which one loads a class, because the path is inside each package, under `vendor/`. So MapX takes the one composer.json requires for production, else the one it requires for dev. If several are listed at the same level, or none is, the package is **unknown** (null). It never picks one arbitrarily.
  - **`replace` and `provide`** (review P2): a locked package stands for the names it replaces or provides. laravel/framework, which replaces illuminate/support, is therefore direct when composer.json requires illuminate/support, and it satisfies that requirement in the stale check.
  - **A stale lock** (review P2): when composer.json requires a package that no locked package is or stands for, a name the lock does not cover is matched by naming convention against those missing packages, and the result is flagged `manifest` (`Acme\Widgets\Gear` → `acme/widgets`, direct). A name nothing matches is unknown and also flagged `manifest`.
  - **`classmap` and `files`** name paths, not classes. MapX reads no `vendor/`, just as M5-20 reads no `node_modules`. So a name that no prefix covers is matched by **Composer naming convention** against the lock's packages that load by `classmap`, `files` or an empty prefix (`PHPUnit\Framework\Assert` → `phpunit/phpunit`, whose autoload is a classmap).
    - Convention match: the namespace starts with the vendor and contains the package name (`psr/log` ↔ `Psr\Log\…`, `symfony/console` ↔ `Symfony\Component\Console\…`), or it starts with the package name (`nesbot/carbon` ↔ `Carbon\…`). The best score wins, and a tie or a global name gives none.
  - **Unknown or not locked.** If nothing matches, the package is null.
    - `direct` is null (**unknown**) when the lock has classmap, files or empty-prefix packages, because one of them may define the name. `collect()` is defined only by the `files` of `illuminate/support` and `illuminate/collections`.
    - `direct` is 0 (**not locked**) only when the lock is complete and every locked package loads by prefix, so the lock shows every name its packages load.
  - **Without a readable lock:** the same convention is applied to the manifests' requirements, flagged `manifest`. An unmatched name is unknown (package, direct and dev null).
- **Platform requirements** (`php`, `ext-*`, `lib-*`, `hhvm`, `composer-plugin-api`, …) are never packages. Only `vendor/name` requirements are read, and no platform name has a vendor.
- **Facades (decision).** Attribution uses the class the file names, which is the facade (`Illuminate\Support\Facades\DB`). The facade's target class (`metadata.facadeTarget`) decides only when the named class shows no package.
  - Why: the `use Illuminate\Support\Facades\DB;` row carries no target, so attributing the call by its target would split one class across two packages. In practice, laravel/framework (or `illuminate/support`, which holds every facade) is the package the file depends on.
  - The target matters for a global alias such as `DB::table()` in a non-namespaced routes file (`DB` → `Illuminate\Database\DatabaseManager` → `laravel/framework` or `illuminate/database`).
  - **`\Cache::get()` in a namespaced file** (my M5-19 finding, confirmed and fixed here). The parser now keeps the class the file names (`metadata.facadeClass`) when it rewrites a facade call to its target. The scanner stores that class, so `\Cache` is the global alias `Cache` (external, with its target) and no longer `App\Http\Cache` decided internal. This replaces the scanner's `phpNamed`, which rebuilt the name from the short alias and lost the leading `\`.
- **`use function` and `use const`** (review P1-2). The PHP parser marks these import references (`metadata.phpUse`).
  - A `use function` row is a function row (`phpCandidates: []`), so it is decided against workspace functions and attributed as a function: `use function sprintf` → `ext-standard`.
  - A `use const` row carries `phpConst` and is attributed as a constant: `use const PHP_EOL` → `ext-core`.
- **PHP built-ins** (`src/core/manifests/php-builtins.ts`, generated; `PHP_BUILTINS_SOURCE` records the source). This is a static list of every class, interface, trait, enum, function and constant of the extensions bundled with php-src, merged as a union of two sources:
  - reflection of PHP 8.1.34, 8.2.35 and 8.4.21 (Ubuntu packages on this machine);
  - php-src's own declarations, the `ext/<name>/*.stub.php` files of tags `php-8.3.0`, `php-8.4.14` and `php-8.5.0`, read with PHP's tokenizer and never executed (review P2: covers extensions no local build loads, such as gmp, pgsql, bz2, odbc, dba, enchant, snmp, tidy, imap, the pdo drivers, 8.4's `Dom\` and `mb_str_pad`, and 8.5's `Uri\` and `array_first`).
  - It holds 340 classes, 2448 functions and 3481 constants in 70 extensions. Constants are case-sensitive, as in PHP.
  - The stub reader agrees with 8.4 reflection for every loaded extension. The only differences are platform-conditional declarations (stub only) and constants registered at runtime (reflection only), and the union keeps both.
  - A name that moved between extensions belongs to the newest source's extension: `rand` moved from ext-standard in 8.1 to ext-random in 8.2.
  - PECL extensions (redis, imagick, memcached, apcu, igbinary, msgpack, xdebug) are excluded.
  - The generator is `scripts/gen-php-builtins.php`: `dump` per PHP binary, `stubs` per php-src tag, then `merge`. The list does not depend on the PHP that runs MapX. Tests check that the list covers every bundled name of whatever `php` is on the PATH (8.2 here; skipped when there is none), and that the stub reader handles braced and unbraced namespaces, methods and `::class`.
  - Built-ins win over packages: a polyfill (symfony/polyfill-*) only defines a name when PHP lacks it.
- **Inputs, skip, staleness, sync.** The composer attributor records every `composer.json` and `composer.lock` it read, or probed and found absent, in M5-20's `external_inputs` record (path → md5). As a result:
  - the next pass skips re-attribution when nothing changed;
  - Composer rows with no attribution (new rows, or an index M5-20 built) are still attributed;
  - `mapx status` and the `check`/`arch` gates report a lock-only or manifest-only change;
  - a sync re-attributes like `scan --force`.
- **Extractor version: bumped from 10 to 11** (review). The `use function`/`use const` and facade-class fixes change what a scan extracts from an unchanged PHP file (candidate metadata, a facade's specifier), so an index built before re-parses once. Attribution alone needed no bump.

## Limitations

- **No `vendor/`.** Classes loaded only by `classmap` and functions defined by `files` are attributed by naming convention or not at all. Global helper functions (`collect`, `app`, `dd`) and classes whose namespace does not follow the package name (`SebastianBergmann\…` of `sebastian/*`) are unknown. Reading `vendor/composer/installed.json` or `autoload_classmap.php` would answer them, but that changes M5-20's "no installed tree" policy, so it is left to the integration owner.
- **The naming convention is a heuristic.** It is used only where no autoload prefix tells, and only where a single package matches best. Its matches carry the same `lock` or `manifest` flag as other rows. Without a lock, laravel/framework (`Illuminate\`) and guzzlehttp/guzzle (`GuzzleHttp\`) do not match, so their rows are unknown rather than guessed.
- **Sibling packages that share a prefix** are told apart only by what composer.json requires. When none or several are required at the same level, the row is unknown even though the class is in one of them. Telling them apart would need the package paths under `vendor/`.
- **PECL extensions** (`Redis`, `Imagick`, `Memcached`) are not built-ins and no list ships for them. They are package rows of unknown package. `origin = 'ambient'` stays unused for PHP.
- **The built-in list** covers the bundled extensions of PHP 8.1 to 8.5: reflection of 8.1, 8.2 and 8.4, plus the stubs of 8.3.0, 8.4.14 and 8.5.0. The stubs include `oci8` and `pspell`, which left php-src in 8.4. Names that only PHP 8.0 or older had are not guaranteed. Windows-only `com_dotnet` is included. Only the `stubs` step of regeneration needs network access to php-src.
- **Dev-ness is name-level**, as in M5-20: a package in both `packages` and `packages-dev` is production.
- **Only `composer.lock`.** A `COMPOSER` environment variable naming another manifest is not honoured.

## Findings outside this task

- **M5-19 capture, fixed here at the integration owner's request (review).** A fully qualified facade alias in a namespaced file (`\Cache::get()` in `namespace App\Http;`) was stored as `App\Http\Cache` and decided internal. See "Facades" under Delivered; the test is the `app/Http/C.php` case of "a facade under a global alias is attributed by its target class".
- **M5-20, the same shape as review P2 "nested lock that cannot be read", not changed here.** `NpmAttributor.lockFor` treats a lockfile it cannot read (a folder, no permission) as absent. A nested unreadable `package-lock.json` therefore falls through to a parent folder's lockfile instead of giving manifest-only attribution. The fix is the same `exists` check the Composer attributor now uses. It is outside this task's ecosystem, so it is left to the integration owner.
