## Limitations

- PEP 420 namespace packages (directories without `__init__.py`) still act as roots, as before: they cannot be told from a script directory.
- A workspace whose root directory itself holds `__init__.py` gets no root-level absolute imports (its real `sys.path` entry is outside the workspace).
- `src/bin/*.rs` is recognised by path, without reading `Cargo.toml` (`[[bin]] path = …` targets elsewhere are not crate roots).

## Findings outside this task

- Cargo's other auto-discovered crate roots, `tests/*.rs`, `examples/*.rs` and `benches/*.rs`, have the same defect: `mod common;` in `tests/it.rs` (the usual `tests/common/mod.rs` pattern) looks under `tests/it/`. Not fixed here: it is outside the finding, and `tests/`, unlike `src/bin/`, is also a common module name inside `src/`, so it needs a `Cargo.toml` check.

Changelog: Python, Rust and Go import edges follow the language: `import json` inside a package is the standard library, not a sibling `json.py`; a comment inside a parenthesised `from … import (…)` no longer drops the next name; `src/bin/*.rs` is a crate root for `mod` and `crate::`; a quoted module path in `go.mod` is read (M0-12-R7).

## Independent review

Reviewer J checked the quoted go.mod, the from-import with a comment, the `src/bin/multi/main.rs` layout and `crate::` from a binary, and found them correct. Two findings:

- **Python namespace packages (P2, reproduced).** A namespace sub-package of a regular package (`pkg/data/` without `__init__.py`), or a namespace folder (`src/nsp/`), is still a search root, so `import json` / `import logging` link to a sibling file. Registered as M0-12-R9.
- **Every `src/bin/*.rs` treated as a crate root, including a module of another binary (P2).** Not changed. Cargo's auto-discovery builds each `src/bin/*.rs` as its own binary target, so `mod util;` in `src/bin/helper.rs` resolves as in a crate root. Treating that file as a module of `tool.rs` would contradict Cargo.
