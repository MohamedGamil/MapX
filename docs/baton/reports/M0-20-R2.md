# M0-20-R2 — NestJS class segmentation ignores comments, strings and generics

Date: 2026-10-31. P1 regression from M0-20-R1 (review `REVIEW-2026-10-31-fb75474ba377`), plus the P2 on GraphQL `name:`.

## Delivered

`src/frameworks/detectors/nestjs.ts`:

- **`maskCode()`** returns a same-length copy of the file. Comments and the contents of strings, templates (with nested `${…}`) and regex literals become spaces. Newlines and quote delimiters are kept, so offsets map 1:1 to the original. Every structural scan (class headers, brace matching, decorator lookup) runs on the masked copy. Values (paths, names) are read from the original at the same offsets.
- **`classBodyOpen()`** finds a class body's `{` after the name, skipping generics `<…>` (including `{ … }` object types and `=>`), `extends mixin(…)` calls and brackets. It replaces the `[^{]*\{` regex, which stopped at the first `{` inside a generic.
- **`decoratorCalls()`** now finds decorators in the masked text, so commented-out decorators are ignored. Every decorator read uses it: `@Controller`, route verbs, `@Use*`, `@Resolver`, GraphQL, message and websocket decorators. Arguments are read with balanced brackets.
- **`stringProp()`** matches `name:` / `path:` keys on the masked arguments, so a `name:` inside a description string no longer wins.
- **`implements` parsing** reads only the class header and removes nested generics before matching interface names.
- **`findMethodNameAfter()`** works on masked text and skips decorator arguments with `closingBracket`.
- The unused `fs`/`path` imports are removed. The `if/else` interface-hook chain becomes a lookup table, with the same output.

## Limitations

- `maskCode` is a lexer heuristic, not a parser. Whether a `/` starts a regex or a division is decided from the previous token. After `)` or `}` it is always treated as a division, so `if (x) /re/.test(s)` is masked wrongly. That is rare in NestJS sources.
- `stringProp` takes the first `name:` key outside strings, so a `name:` in a nested object literal of the same decorator (`{ args: { name: 'x' } }`) would still win. The same limitation existed before. No real GraphQL decorator option nests a `name` key there.
- Non-literal paths (`@Controller(PREFIX)`) keep the old behaviour: the raw text is used as the prefix.

Changelog: NestJS route and hook detection no longer loses or misattributes routes when comments or strings contain `class`, quotes or braces, or when classes use generics; GraphQL operation names ignore `name:` inside description strings (M0-20-R2)
