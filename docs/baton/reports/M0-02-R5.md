# M0-02-R5: git sync drops deleted untracked/staged files; blob ids for re-indexed files

Date: 2026-10-31. Source: the finding and limitation in `docs/baton/reports/M0-02-R4.md`. Built on develop `38b4fd4` (M0-02-R4 integrated as `e23d6c2`).

## Before (reproduced on the unchanged code)

The new tests were run against the unchanged `src/` (`-t "uncommitted files"`): exit 1, both failed.

- **Deleted untracked file.** `AuditService.php` was untracked, indexed by `sync`, then deleted, and `sync` was run again. Its row, symbols (`AuditService`, `run`) and its `param_type` edge into `UserService.php` were all still there. `git diff <last_scan_commit>` compares two trees, neither of which has the file, and `git ls-files --others` stops listing it once it is gone.
- **Deleted staged-only file.** `ReportService.php` was `git add`-ed, never committed, then deleted from the working tree. It was not removed: `git diff --cached` still lists it as added, and the scanner skipped the listed path because `getFileInfo` found no file.
- **Blob ids on sync.** After `sync` re-indexed an edited `MailService.php`, `git_blob_hash` was `null`. The M0-02-R4 skip could therefore never apply to files whose last indexing was a sync.

## Delivered (`src/core/scanner.ts`, `_scanIncrementalForRepo` only)

- **Indexed files git no longer reports.** Before the "no changes" early return, git sync reads HEAD's tree once, through `getGitBlobHashes(repoRoot, workspaceRoot)` (workspace-path keys since M0-02-R4). An indexed file of the repo is taken as removed when it is in neither HEAD's tree, nor the change list, nor on disk. Only uncommitted files are stat-ed: committed deletions already appear in the diff.
- **Listed but gone.** A listed change whose file no longer exists is removed rather than skipped. This covers the staged-only file that `git diff --cached` still lists.
- **Blob ids.** Git sync stores `gitBlobId` of the bytes it indexed, for listed files and for re-parsed referrers, where it used to store `null`. The skip compares the same in-process id, so a file is skipped only when its bytes are exactly the indexed ones. For example, committing an edit that an earlier sync indexed no longer re-parses it.
- **Docs:** `docs/cli-reference.md` (`sync`) and `docs/mcp-integration.md` (`mapx_sync`).

## Limitations

- **One extra `git ls-tree -r HEAD` per git sync and repo.** It runs even when nothing changed, because a deleted untracked file produces no change at all. Without commits (unborn HEAD), every indexed file is stat-ed.
- **The stored id is `git hash-object` without filters.** Under autocrlf or other filters, it differs from the id git stores. The only effect is that the file is not skipped; the skip itself stays exact.
- **The full scan keeps M0-02-R4's rule.** It stores HEAD's blob only for clean content, and `null` for a file modified in the working tree. So after a full scan of a dirty file, the first sync that lists it re-parses it once.

Changelog: `sync` now drops deleted files that were indexed while untracked or only staged, and records blob ids for the files it re-indexes, so committing an already synced edit no longer re-parses it (M0-02-R5).
