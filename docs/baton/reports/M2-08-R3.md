# M2-08-R3 report: names imported from an external module never link to a same-named project symbol

Found by M5-18. In MapX's own index, `join`/`resolve` from `node:path` resolved as `verified` calls to `src/core/import-resolvers.ts#join` (a module-private `const`) and `src/parsers/languages/lua.ts#LuaScopes`'s `resolve`. `Node` from web-tree-sitter resolved to `src/core/manifests/pypi.ts#Node`.

This report covers attempt 1 (`2f1a88e`) and its review fixes, amended into one commit (see Review).

## Delivered

The code is in `src/core/scanner.ts` (reference resolution) and `src/core/js-source.ts` (text helpers). `src/core/js-aliases.ts` adds `baseUrl`.

- **Outside the project (`outsideProject`).** A JS/TS specifier is outside only when it is positively so. No project file, alias or workspace package may satisfy it (`decideExternal`), and it must be one of these:
  - a Node built-in (`node:path`, `fs`, `fs/promises`; `nodeBuiltin` from M5-20);
  - a package an enclosing package.json lists with a registry version, or node_modules holds (`isNpmPackage`, M0-17-R4);
  - a package name that no project folder or file stem is called (`some-pkg`, an unlisted `web-tree-sitter`).

  Anything else is unknown and keeps name lookup, as before. Examples: `components/Button` beside a `components` folder, or `shared/money` under a webpack alias whose value MapX cannot read.
- **`baseUrl` (`jsBaseUrlTarget`).** A bare import is also probed under the `baseUrl` of the nearest tsconfig/jsconfig, after `paths`, as tsc does (the create-react-app jsconfig `{"baseUrl": "src"}`). It is not an alias: a package import probes it too, stays a package when no file is there, and is not recorded as an unresolved project import.
- **Import-bound externals (`boundOutside`).** This covers a JS/TS/Vue/Svelte reference of any kind except `import`/`require` whose bare name or receiver (`path.join`, `fs.readFileSync`) an import from outside the project binds.
  - It gets no edge and goes to `noteExternal`, the unchanged M5-19 path, which records the external-reference candidate.
  - The binding comes from M5-19's `jsExternalBindings`, so a name the file declares itself is not bound by it.
- **Names in an ES module (`globalScopeFilter`).** These apply to a bare name in a `.ts/.tsx/.js/.jsx/.mjs/.cjs/.mts/.cts` file:
  - **Bound outside the project, but declared too.** The file imports, or destructures from a dynamic import (`const { join } = await import('node:path')`, `import('node:path').then(({ resolve }) => …)`), a name from outside the project, and also declares it. An example is MapX's `src/arch/elements.ts`, with `const join = …` in one function and `join` from `node:path` called in another. Only the file itself may be picked: the call is the import or the file's own local.
  - **A global.** In an ES module, a name the file neither imports nor declares (the DOM `Node`) may resolve only to:
    - the caller itself;
    - a script, meaning a file with no top-level import or export (a global `.d.ts` among them);
    - a module whose `declare global { … }` block declares the name.

    Another module's declaration is never a candidate. `resolveSymbolToFile` gained an optional `allowFile` filter, applied after the memoised name candidates; only this call site passes one.
- **Module-ness (`hasModuleSyntax`).** Only a top-level `import`/`export` statement counts, as in TypeScript's `isExternalModule`. The scan tracks brace depth in the masked text, so an `export` inside `declare namespace`, `declare module '…' {}` or `namespace X {}` does not count, and neither does a dynamic `import(…)` or `import.meta`. If the scan cannot balance its braces, only a statement at a line start counts.
- **Barrels passing on outside names (`findExport`).** Through a project barrel, a call gets no edge for a name:
  - re-exported from outside the project (`export { join } from 'node:path'`);
  - imported from outside and passed on (`import { resolve } from 'node:path'; export { resolve }`);
  - absent from every project `export *` target while another star is outside the project (`export * from 'lodash'`).
- **Sync (`globalScopeReferrers`).** Each JS/TS parse records `globalScope` in the file's metadata: `s` for a script, else `m:` and its `declare global` names. When a changed file's value differs, the files with edges into it re-parse. A script that becomes a module therefore drops its by-name referrers' edges, as `scan --force` does.
- **Kept as before (no restriction):**
  - a name imported from a project module, or from one that may be one;
  - a name the file declares otherwise (`const { refresh } = useLocal()`; two Vue store tests rely on this);
  - a receiver call;
  - a script source;
  - a `.vue`/`.svelte` source (template expressions, SFC auto-imports; the import-bound gate still applies);
  - a source under a package.json depending on an auto-import tool (`nuxt`, `nuxt3`, `nuxt-edge`, `@nuxt/bridge`, `unplugin-auto-import`, `unimport`);
  - Vue references with `vueHint`, `this.x` or a store.
- **`EXTRACTOR_VERSION` 14 → 15**, with its comment line (develop `cb5fa73` is at 14).

### Decisions on the ambiguous cases

- **Vue/Svelte sources** are exempt from the global rule. All existing Vue tests pass.
- **`declare global`:** only the names inside the block are global (tested).
- **`.d.ts` files:** one without a top-level import or export is a script, whatever its `declare namespace`/`declare module` bodies export, so its declarations stay reachable by name (tested). A `.d.ts` that is a module behaves like any module.
- **TS namespace scripts:** two script files merging `namespace App { export function … }` still link by name (tested).
- **Locals the index does not hold, such as parameters** (`function f(cb) { cb() }`), get no edge to another module. Names the file declares with `const`/`let`/`var`/`function`/`class` keep the old lookup, per the brief's definition of a global.

## Limitations

- **Sync, newly global names:** a module that becomes a script, or gains `declare global` names, does not re-parse files that may now reach those names by name. A new declaration in any file does not either; `scan --force` does. The stale direction (script → module, fewer global names) is covered.
- **Sync, other inputs:** a bare specifier becoming a workspace package, or a new file under `baseUrl` satisfying an import, is picked up at `scan --force`. M2-08-R2 records only relative and alias imports.
- **Through a barrel, only calls are followed** (`findExport` serves call resolution). A type reference to a name a barrel re-exports from outside keeps name lookup.
- **Unknown specifiers keep name lookup:** a package that no manifest lists and node_modules lacks, whose name matches a project folder or file stem (an unlisted `utils` beside a `utils/` folder), keeps today's behaviour.
- **Auto-import detection** reads package.json dependencies only.
- **Scripts and CommonJS keep name lookup**, outside the criteria.
- **Declared-name detection is textual** and over-inclusive, erring towards the old lookup.
- **Finding outside the task:** M5-18 restricted MapX's architecture check to `import`/`require` edges partly because of these false positives; the owner may revisit that.

Changelog: In JS/TS, a name imported from a package or a Node builtin (`import { join } from 'node:path'`) no longer links to a same-named project symbol, and a global an ES module neither imports nor declares (`Node`, `Request`) no longer links to another module's declaration; bare imports under a tsconfig/jsconfig `baseUrl` now resolve (M2-08-R3).
