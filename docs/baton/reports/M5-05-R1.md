# M5-05-R1 — Staleness in status, MCP and the other commands finds new files as check does

Planned in `iterations/M5-05-R1.md`. Source: `reports/M5-05.md` (limitation "Walk cost" and the P1 finding on new files outside a single git repo).

## Delivered

- **`src/core/staleness.ts`:**
  - `findStaleFiles(store, dir)` now finds new files by walking the workspace with the scanner's rules, for every caller. The git `ls-files --others` listing (`untrackedSourceFiles`) is gone, and so is the `{ walk: true }` option.
  - `{ newFiles: false }` checks only the indexed files, with no walk and no git call. `indexableChanges` uses it by default, because it reads only `changed` and `deleted`. This also covers the UI server's per-repo calls. `indexableChanges` takes an optional precomputed report, so a status walks once.
  - The walk no longer enters an unregistered nested git repository, because the scan walk skips one (`Scanner.discoverFiles`). Without this, once every command walks, such a repo's files would be reported `(new)` forever. Git used to list such a repo only as `lib/`, which was filtered out.
  - New: `unlistedStale(stale, dir, repoRoot, gitChanges)` returns the stale files a status shows besides its git changes.
- **`src/cli.ts`:**
  - `mapx status` computes one report and passes it to `indexableChanges`. After the git section it prints `── Other changes since last scan` (in a git repo) or `── Changes since last scan` (in a non-git workspace), with the `+`/`~`/`-` list, and the recommendation becomes `⚠ Index is stale`.
  - Before this change, a non-git workspace always printed `✓ Index is up to date`, even when files had been edited.
  - `status --all` gives each new file to the innermost registered repo that holds it. Before, every new file counted for the primary repo.
  - `mapx check` uses the default.
  - `checkAndPrintStaleness` is unchanged: the M5-26 older-index warning comes first, then one report.
- **`src/mcp.ts`:**
  - `getMcpStalenessWarning` builds one report per tool call. Before, it built two whenever something was stale: one for the count and one for the names.
  - `mapx_status` counts the git changes plus `unlistedStale`. In a non-git workspace it says `Not a git repository; N changed files since last scan  (⚠ stale)`.
- **Tests and fixture:**
  - `tests/legacy-impact-staleness.test.ts` has a new describe, "new files outside a single git repo are stale for status and the warnings".
  - `tests/fixtures/staleness/count-walks.mjs` is a synthetic preload that counts walks, i.e. `readdirSync(root, { withFileTypes: true })` on the workspace root. It works in a child CLI process and in-process (the same pattern as `hide-grammar.mjs`).
- **Docs:**
  - `docs/cli-reference.md`: the `mapx status` outputs, and "Staleness warning", which now covers the walk, unregistered nested repos and one walk per command.
  - `docs/mcp-integration.md`: `mapx_status`.

**After the independent review** (see "Independent review" below):
- The walk decides each folder once, as `scan` (index its files), `pass` (only a way to a registered repo below) or `skip`.
- Each repo's matcher is built once.
- A file is tested by name first: ignored or dot names, then its language by extension or filename (a set lookup), before any glob work.
- Registered repos below a pruned folder are reached.
- Unreadable files are skipped.

`isScannablePath` in `src/core/file-rules.ts` takes an optional prebuilt matcher.

**Files outside `affectedFiles`:** `tests/fixtures/staleness/count-walks.mjs`, `src/core/file-rules.ts` (the optional matcher parameter), `docs/cli-reference.md` and `docs/mcp-integration.md`. The brief asks for the fixture and for doc updates when the CLI or MCP surface changes. `CHANGELOG.md` is listed in `affectedFiles`, but under the lane brief it belongs to the integration owner, so the changelog line is at the end of this report and the file is untouched.

## Cost (≈10,000-file workspace, first delivery 98f17c1)

These figures are for the first delivery. The walk was reworked after the review; the "Independent review" section has the current figures.

The workspace is synthetic: 10,000 `.ts` files in 200 folders, plus 2,000 files under `node_modules`. It is a git repository and was scanned before the runs. The runs are interleaved before and after: before is develop at 5ed5e0b, copied to the scratchpad, and after is this branch. The load average was 7–10 on 16 cores. Medians are over 21 in-process rounds and over 9 CLI runs.

| Measure | Before | After |
| --- | --- | --- |
| `findStaleFiles`, default | 68.8 ms (mtime check + `git ls-files --others`) | 85.7 ms (mtime check + walk) |
| `findStaleFiles({ walk: true })` (old `check`) | 84.0 ms | — (now the default) |
| `findStaleFiles({ newFiles: false })` (`indexableChanges`) | — (it ran the full default, with git) | 60.7 ms |
| MCP warning per tool call, nothing stale | 71.2 ms | 85.1 ms |
| MCP warning per tool call, one new file | 148.9 ms (two reports) | 92.6 ms (one) |
| `mapx query f1_1`, wall time | 533 ms | 557 ms |
| `mapx status` | 623 ms | 635 ms |
| `mapx status --all` | 578 ms | 607 ms |

The walk costs about 25 ms here and the git listing about 8 ms. The mtime check of every indexed file, about 60 ms, dominates, and it is unchanged. Each command walks once.

**MCP cache: not added.** The per-call cost rises by about 14 ms when nothing is stale and falls by about 56 ms when something is. A cache keyed by directory and last scan time would hide edits made within its lifetime, so it was declined. If the integration owner wants one, it would go in `getMcpStalenessWarningForFiles`.

An earlier run on a heavily loaded machine (load average 30–53) gave noisy numbers (`query` 2.3–2.4 s on both sides). They are not used.

**Gitignored folders are not pruned.** The scan walk does not read `.gitignore`, and sync's `ignoredChanges` walks gitignored folders too, so the scan indexes source files in them. Pruning them would hide files the scan indexes. A folder of images there costs a listing and a name test per entry.

## Limitations

- **Cost.** Every command and MCP tool call now walks the workspace once. That is 8–15 ms per 10,000 files here, and about 70 ms for 100,000 gitignored images, which git used to hide. The scan's pruning rules apply (`node_modules`, `vendor`, dot-folders, excludes). Gitignored folders are walked because the scan indexes them.
- **Perf guard.** The bound (5 × a bare listing + 300 ms) is generous, to survive a loaded machine. It catches the old per-file glob cost (2.7 s against 0.37 s), but not small regressions.
- **Symlinked repos.** A registered repo reached through a symlinked folder is not entered by the walk, because it follows no symlinks and the scanner resolves the repo root. A new file there is missed. This is pre-existing (M5-05) and gives false negatives only.
- **User languages.** Files of user-defined languages (`getResolvedUserLanguages`) are not recognised as new by the staleness rules. This is pre-existing and gives false negatives only.
- **Gitignored files.** In a git repo, a new gitignored file that a scan would index (the scan walk does not read `.gitignore`) is now reported. Before, git hid it. This matches what a scan indexes.

Changelog: `mapx status`, the staleness warning of every command and the MCP tools' warning now find a new file in a workspace that is not a git repository, in a nested repo or in a registered repo below a skipped folder, as `mapx check` does, with one walk of the workspace per command that tests each file by name before any pattern (M5-05-R1).
