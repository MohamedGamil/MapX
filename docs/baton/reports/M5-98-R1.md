# M5-98-R1 — `mapx check --since <git-ref>`: judge only what changed (ratchet)

Date: 2026-11-04. Base: `develop@accf69f`. Iteration: `docs/baton/iterations/M5-98-R1.md`. Sources: `docs/baton/reports/M5-98.md` (REQ-ARCH-021 had no task), `M5-06.md` (baselines, `--compare`), `M5-08-R1.md` (git refs never reach a shell), `docs/research/deptrac/05-requirements.md`.

## Delivered

- `mapx check --since <ref>` (CLI) and `since` of `mapx_arch_check` (MCP) share one filter, `sinceFindings` in `src/arch/check.ts`: a finding is kept when its **source file** is in the set of changed files, and the counts are recomputed. Findings without a source (an empty layer, an unsupported selector) are dropped. Configuration and baseline errors always stay, so exit 3 still wins.
- **"Changed"** (revised in the review below) is `changedSince(…, { branchPoint: true })` (`src/arch/introspect.ts`) over `getChangedFilesSinceBranchPoint` (`src/core/git-tracker.ts`): the working tree against `git merge-base <ref> HEAD` (committed, staged and unstaged; both paths of a rename), plus untracked files git does not ignore. `.mapx/` is never source. A workspace whose root is no repository works through its registered repos. As first delivered it was `git diff <ref>` (two-dot), which the review found wrong.
- **Decision, documented: a dependency counts when its source file changed; a changed target alone does not.** A dependency is written in its source file, so editing a class does not re-judge every importer, and the source of a new import is always a changed file. This narrows the MCP filter, which used to match either end; MCP and CLI now agree (the existing `mcp-arch` test, which touches a source file, passes unchanged).
- **Combinations.** The filter runs after the baseline and `--compare` have skipped what they know, then `--layer`, `--rule`, `--fail-on` and `--fail-on-uncovered` apply. Every `--format` renders the filtered report. A stale baseline entry stays an error (exit 3). `--generate-baseline` with `--since` is exit 3. `--compare` refuses a base report that was itself made with `--since` (it lacks findings). The JSON report's `selection.since` names the ref (schema `schemas/arch-report.schema.json` and `Selection` gained an optional `since`; reports without `--since` are byte-identical to before).
- **Git safety.** The ref is validated once, before the index is read, by `revisionProblem` (shared by the CLI and the MCP tool): empty, a leading `-`, whitespace, quotes, shell metacharacters or control characters are exit 3. `changedSince` also refuses an empty or `-` ref for every caller. Git is run only through `execFileSync` argument arrays (`revision()` in `git-tracker.ts` refuses a leading `-` too). An unknown ref or a workspace in no git repository is exit 3 with a message (and a `config` error report for the CI formats, as a missing configuration gives).
- Docs: `docs/architecture-rules.md` (new section "`--since`: the ratchet over the files changed", `selection`, `--compare` like-with-like), `docs/cli-reference.md` (synopsis, option, `--generate-baseline`, example), `docs/mcp-integration.md` (`since`).

## Limitations

- The index is the working tree's, not the ref's: the check does not re-scan the ref (REQ-ARCH-021 as worded asked for a second scan; this delivers the ratchet the task objective names, from git alone). The index must be current (exit 4, or `--sync`).
- A change to the configuration or to layer membership is not a changed file, so old code is not re-judged under new rules: run a full `mapx check` on the default branch as well.
- MCP has no `baseline` or `compare` argument, so only the configuration's baseline composes there (as before).
- `mapx arch changed --since` keeps its looser ref check (whitespace allowed, as git allows it); only `check --since` and the MCP tool apply `revisionProblem`.

Changelog: `mapx check --since <git-ref>` reports and judges only the dependencies written in files changed since the ref, so CI can ratchet without a baseline (M5-98-R1).
