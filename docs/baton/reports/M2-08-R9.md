# M2-08-R9 report: sync follows new global declarations

Found by M2-08-R4 (Limitations, and its independent review): "a new declaration in any file, and a rename or move into a script do not re-parse the files that name it; `scan --force` does".

## Cause

`globalScopeReferrers` compares the recorded global-scope key of a file already indexed. A **new file** has no recorded key, so it was skipped; a **script that stays a script** keeps the key `s`, so it was skipped though it gained a declaration. The modules that named the new global (`files.metadata.globalNameRefs`, M2-08-R4) were never looked up.

Probe on `develop@773e2a1` (real CLI, `scan` then edit then `sync`, hash and git modes alike; `/tmp/claude-1001/.../scratchpad/M2-08-R9/probe.sh`): (a) a new script `lib/new.ts` declaring `newScriptFn`, (b) `lib/g.ts` renamed to `lib/h.ts` with `export` dropped (`movedFn`), (c) `lib/s.ts` gaining `addedFn`, (d) a new `types/decl.ts` with `declare global { class LateDecl {} }`. `sync` said "Updated 6 files … 1 edges updated" and left four edges that `scan --force` then gave (`a1 call lib/new.ts#newScriptFn`, `c1 call lib/s.ts#addedFn`, `D::constructor param_type types/decl.ts#LateDecl`, `e1 call lib/h.ts#movedFn`). The same probe on the fixed code: no diff between sync and `scan --force`.

## Delivered

- `src/core/scanner.ts`:
  - `reindexGlobalRecorders` runs after the first batch of a sync is written, in the incremental scan, git sync and hash sync. The names a new or edited script declares are read from the parse the sync runs anyway: the symbols its parse found that it did not declare before as a script (`globalScopeBefore` captures the stored key and symbol names before the rows are replaced; `globalScopeWritten` notes each file's new key as it is written). A new module contributes its `declare global` names. The modules recording a gained name (`globalNameRefs`) that the first batch did not parse are re-indexed in a second batch through the normal parse path (worker pool included), queued in `pending_referrers` until written, as M0-02-R11 does.
  - `globalNameRecords` (one pass over the metadata) is kept for the sync, so R4's lookup and this one share it; `startDeferredConsumption` drops it at the start of each sync.
  - `globalScopeReferrers` stays as R4 left it for a module already indexed whose key changed; its comment no longer says the recorded names were "found nowhere" (`globalNameRefs` records every bare name that reached the global rule).
- `src/core/js-source.ts`: `gainedGlobalNames` returns a module's `declare global` names only and nothing for a script (R4 returned every word of a file turned script).
- `src/parsers/wasm-parser.ts`, `generic-wasm-parser.ts`, `languages/php.ts`, `parse-worker.ts` (review P2-2): `parseWithQueries` returns `dispose()`; the generic and PHP parsers call it in a `finally`; it frees the tree itself when a query throws; the worker's generic capture walk frees its tree on every exit. `vue-ast.ts` already freed its trees.
- `tests/import-bound-externals.test.ts`: `describe.each` git/hash, 11 tests each, plus an in-process test of the parse batches. `tests/parser-tree-release.test.ts` (5 tests): `Tree.delete` is called once per parse for TypeScript, JavaScript, PHP and Python, and when a query throws.
- `CHANGELOG.md` (two entries); `docs/baton/iterations/M2-08-R9.md`; TASKS.json planning fields. No status field touched.
- No `EXTRACTOR_VERSION` bump: parse results and unchanged files are the same, and no record is added.

### First design, dropped (review P2-1)

The first version parsed each changed script a second time on the main thread to learn its names (gated by the words of its text and the recorded names). The review measured it: 2,000 scripts of 8 KB edited, 58 s and 3.1 GB against HEAD's 23 s and 2.4 GB; a 400 to 800 KB script blocked the main thread for 10 to 37 s. The names now come from the sync's own parse, so no script is parsed twice and nothing parses on the main thread that did not before.

### Full-scan output

Cannot change: `scan --force` runs no second batch (`reparseAll`), and the parsers return the same results (only the tree is freed). Identity check: `scan --force` of a copy of the repo (committed and working files, so both runs read the same input) with HEAD's source (git worktree of `773e2a1`, removed afterwards) and with the change. A sorted dump of every edge (source file and symbol, type, target file and symbol, weight, verifiability) and every symbol (file, name, kind): 5,023 symbols and 8,183 edges, 13,207 lines each, `cmp` identical.

## Acceptance criteria

1. **Met.** "a new script declaring a name a module calls …": git and hash, `Updated 2 files` (the script and `a.ts`, not `bystander.ts`, which records `missingName`, a word the script uses); "a new script none of whose declarations a module names": `Updated 1 files`; synced edges equal `scan --force`'s.
2. **Met.** "a module renamed and turned script …": `git mv` in git mode, `mv` in hash mode, `Updated 2 files`, edge `e1 call lib/h.ts#movedFn`, equal to `scan --force`.
3. **Met.** "a function added to an existing script …": `Updated 2 files`. "a body edit of a script, with words other modules recorded …": `Updated 1 files`, and `o.ts`, which names `oldFn` (declared before), keeps its edge.
4. **Met.** "a new file with `declare global` …" and "a new global .d.ts declaration …": `Updated 2 files`, edge appears, equal to `scan --force`.
5. **Met.** "a module edited into a script re-parses only the modules that name what it declares, not what it uses": `Updated 2 files`.
6. **Met, no change needed.** "a global removed from a script …": `Updated 2 files` (the script and the module that had the edge, through `removedSymbolReferrers`); "a script removed …": `Updated 0 files`, since its edges are deleted with its rows. Both equal `scan --force`. These passed on HEAD; they pin the existing behaviour.
7. **Met (in-process test, review fixes).** "a sync parses each file once, the recorders of a gained name in a second batch": a body edit parses `[lib/s.ts]` and nothing else; a declared name gives batches `[lib/s.ts]` then `[use/a.ts]` (not `b.ts`); a module and a script gaining a function in one sync parse in one batch with the module that names the module's `declare global` name; a module edited in the same sync that names a gained name is parsed once (first batch); the metadata of the recorded names is read once per sync; `pending_referrers` is `[]` afterwards. Git and hash sync and the incremental scan are each exercised by the git/hash tests and the "rescan without --force" test.
8. **Met (review).** `tests/parser-tree-release.test.ts`: `Tree.delete` once per parse for TypeScript, JavaScript, PHP, Python, and when a query throws. Memory: table above.
9. **Met.** `npm run eval` unchanged; self-scan dump byte-identical.

## Limitations

- **Callers that are not ES modules** (a script calling a name a new script declares, a Vue or Svelte file) are not followed: `globalNameRefs` is written for ES modules only, and the global rule does not restrict a script's names, so no record names them. `scan --force` links them. Recording every bare name of every script would add a record per script; no task owns it.
- **Removing one of two same-named declarations** (a script, or a global of a script) while the other stays: the module's edge goes with the file and is not re-linked to the remaining one, which `scan --force` does. Probe: `dupFn` declared in `lib/dup1.ts` and `lib/dup2.ts`, `use/dup.ts` calls it, `lib/dup1.ts` removed: sync leaves no edge, `scan --force` gives `lib/dup2.ts#dupFn`. This is the general "removed target while another declares the name" gap of M0-02 (not specific to globals): not fixed.
- **A script that gains a same-named member** (`class B { area() {} }` beside `class A { area() {} }`): `area` is not new to the file, so the callers of `area()` are not re-parsed. The same gap exists for any file adding a same-named symbol.
- **A `.vue` or `.svelte` file** with `declare global`, a name reached through a base class in another file, and the M2-08-R3 sync inputs (a bare specifier turning workspace package, a file under `baseUrl`): unchanged.
- **Cost:** a sync that gains a global name parses the modules that named it in a second batch (e.g. 60 recorders for one name 60 modules record). A name that many modules record (a common word) re-parses all of them; that is what `scan --force` links, and it is bounded by the recorders of the names the sync's files declare.
- **Kill between batches:** the recorders are queued in `pending_referrers` before the second batch and removed when it is written, so a sync killed in between leaves them for the next one; the first batch's files are already indexed.
- **Not run:** `mapx impact` on the changed symbols (the repo's own index predates the code); the spec records a grep of the callers instead.

## Re-review of the redesign, and the integration owner's fix (2026-11-04)

A second independent review covered the redesign and the tree disposal. It found no P0 and no P1:
- **Tree disposal:** byte-identical full dumps against HEAD on 11 corpora, including a 72k-line PHP app and a TS/JS repo. The full vitest suite passes, and no consumer keeps a node after `dispose()`.
- **Memory:** 1,500 main-thread parses grew RSS from 150 MB to 2,284 MB on HEAD (aborting), and from 168 MB to 210 MB here.
- **Sync ≡ force:** byte for byte in every spec scenario, in git (committed and uncommitted), hash and plain scan modes. A random differential (100 seed and mode runs) shows no divergence for ES-module callers beyond the documented M0-02 gap.
- **One follow-up pass is enough.**

One P2 was found. The recorders were queued only after the first batch committed, behind the `globalNameRecords()` metadata scan and the recorders' file reads, and an abort returned before queueing. A sync killed or aborted in that window left the recorders unlinked until `scan --force`. The reviewer's repro was a SIGKILL on entry to `globalNameRecords`; the next sync then said "Updated 0 files" and 3 edges were missing.

The integration owner fixed it in `src/core/scanner.ts`:
- `globalScopeBefore` reads the recorded names before any write.
- `reindexGlobalRecorders` queues the recorders as soon as they are known, before reading files.
- An abort still computes and queues them, and skips only the second batch's parse. The three call sites now always call it.

Checked by hand with the reviewer's preload:
- **Kill at `globalNameRecords`:** the next sync updates 4 files and equals `scan --force` (3 edges). Before the fix it updated 0 files with 3 edges missing.
- **Kill at the queue write itself:** this is after the commit with only in-memory work before it. The next sync still misses the edges. This microsecond window remains, and closing it needs the queue written in the first batch's transaction (Limitations).

Re-run after the fix:
- `npx vitest run tests/import-bound-externals.test.ts tests/parser-tree-release.test.ts`: exit 0, 174 passed.
- `npm run eval`: exit 0, all floors hold.
- `npm run check`: exit 0, 158 files, 3443 passed, 4 skipped.

Limitation added: a SIGKILL between the first batch's commit and the queue write, which has only in-memory work in between, loses the recorders until `scan --force`.
